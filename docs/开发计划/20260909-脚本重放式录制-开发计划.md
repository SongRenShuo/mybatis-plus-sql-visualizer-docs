# 脚本重放式 GIF 录制开发计划

- 立项时间：2026-09-09（修订一：脚本重放 + 帧稳定采样。修订二：放大表现力改用「瞬时特写切镜」方案 B——脚本重放会丢真实鼠标轨迹，故补贝塞尔轨迹插值；auto-zoom 的推近观感不靠过渡动画、改全景/特写两段拼切，避开 15fps 缩放过渡卡顿）
- 目标：解决 ZCode 逐步操作带来的「操作间隔长、成片不连贯」问题，用**脚本重放 + 帧稳定采样**替代逐动作录制，让 GIF 的演示节奏不受 ZCode 每步之间的通信/等待延迟影响，同时消化 IDEA 偶发的弹窗加载不稳（平时 1s、偶发 3s）；并在不引入 15fps 缩放过渡卡顿的前提下，保留「放大强调关键结果」的表演力（修订二，见 2.4）。
- 关系：本计划是 `20260907-1138-文档站演示图GIF化补齐与替换-开发计划.md` 的录制手段升级，只替换「怎么录」这一环，不改动 8 张 GIF 的**分镜、主题、构图、清晰度、兜底图**等既有验收标准——所有成品仍需过原计划的四、整体验收标准。

## 一、问题与根因

1. **ZCode 逐步操作不连贯**：主智能体每发一个动作（移动鼠标/点击/输入）都要等 tool 返回再发下一个，中间的网络与确认时延叠加成「动作后停顿」，录进 GIF 就是一顿一顿的空窗。
2. **IDEA 加载时间不稳定**：同一窗口平时 1s 打开，偶发 3s（GC、索引、首次解析、沙盒 VM 抖动）。固定等待值要么录进烂尾白屏、要么浪费成片时长。

两者本质是同类问题：**成片的「时间轴」不该由「等待界面的实时时钟」决定，而该由「画面是否稳定」决定。**

## 二、录制架构：脚本重放 + 帧稳定采样

整体思路：**把「动作」写成确定性脚本一次性重放，用「画面稳定」作为节奏锚点，而不是靠 wall-clock 定时。**

```
一次性脚本重放（动作序列）
        │
        ▼
桌面录屏（连续抓帧，不剪时间轴）
        │
        ▼
帧稳定性采样（相邻帧 diff 低于阈值才算「稳定」，稳定持续 N 帧才推进下一步）
        │
        ▼
动作-结果帧一一对应、空白等待被自动「压缩」掉
        │
        ▼
ffmpeg 按结果帧切段 → 15fps → 调色板 → GIF
```

### 2.1 方案 A(主)：动作脚本重放（消除 ZCode 延迟）

不再用 computer-use 逐步操作。改为在沙盒桌面外驱动：用 `pyautogui` / Windows UIA / 键盘宏，把每个分镜的完整动作序列写成一个脚本，一次性按脚本里的**即时**间隔重放（脚本内部动作间隔就是 200~400ms 的真实演示节奏，不受 ZCode 往返影响）。ZCode 只负责「启动脚本、检查录屏产物」，不参与逐帧控制。

重放脚本要素：
- 鼠标移动：**不直接用 `pyautogui.moveTo` 的直线**，改用贝塞尔曲线插值生成中间点，逐点 `moveTo` 推进：起手慢、中间快、落点前减速，每个中间点加微小随机抖动，模拟真实人手轨迹（修订二——脚本驱动的匀速直线轨迹观感失真，这是脚本方案唯一要补的真实感短板）
- 点击/双击/右键：`click` / `doubleClick` / `rightClick`，点击时配合 Recordly 渲染层的点击涟漪/光标高亮叠加（该叠加不依赖鼠标怎么动，脚本坐标照常触发）
- 键盘输入与快捷键：`write` / `hotkey('ctrl','space')` 等
- 动作间隔：**每步之间显式写 `sleep(0.3~0.6)`**，这是演示节奏，不是等待界面
- 关键结果（SQL 弹窗出现、代码生成完）后的「定格 1.5~2 秒」用 `sleep(1.5~2)` 表达

### 2.2 方案 B(兜底)：帧稳定采样 + 等待上限（消化 IDEA 偶发 3s）

即使脚本重放，仍要给每个关键结果一个「等画面稳定」的兜底，处理 IDEA 偶发卡 3s：

- 对每个触发后应立即出现结果的节点，重放脚本在触发动作后进入 `wait_stable()`，而非盲 sleep
- `wait_stable()` 逻辑：连续抓桌面帧，相邻帧像素 diff 低于阈值视为稳定；**稳定持续 ≥ 8 帧（约 0.5s）**判为该屏内容已就绪
- 同时设**硬上限**：正常窗口预期 1s，上限设 4s（覆盖 3s 偶发 + 余量）；到上限还没稳定，按 `fallback` 处理（重试该动作一次，仍失败则标记该分镜、跳过录制品、换手动补录）
- 结果帧就绪后，再补一个固定的「演示定格 1.5s」再继续下一动作——保证成品里关键结果停留时长恒定，不随加载时长漂移

帧稳定采样用 `mss` 抓屏 + `PIL` 算差异即可，不引入重依赖；阈值在首条 GIF（annotation-preview）标定一次，后续七张复用。

### 2.3 方案 C(辅助)：空白压缩

对个别「必须真实等待、且等待过程无画面价值」的片段（如首次编译、索引、runIde 启动），录制时不按实时时间轴剪，而是在采样阶段把「连续稳定段」压缩到最小展示时长——静止是本演示的常态、不必完整保留每一秒。C 是 A/B 未能完全消除空白时的补充，不作为主手段。

### 2.4 方案 B(放大表现力)：瞬时特写切镜（修订二）

auto-zoom 的「推近关键结果」是官方表现力主要来源，但它在 15fps GIF 里缩放过渡会一卡一卡（修订七已为流畅性关闭它）。改用**瞬时特写切镜**保留放大感、避开过渡卡顿：

- 每个分镜的「关键结果」（SQL 弹窗、生成代码）出现后，用**第二段特写录制**：同一画面把框选区域拉到弹窗/代码的紧致特写，即「全景投放 — 切镜到特写 — 切回全景」的瞬时切换，中间**无缩放过渡动画**
- 实现：录制时同一分镜出「全景段 + 特写段」两段稳定素材，后期按「全景动作 → 瞬时切特写定格 → 切回全景收尾」的顺序用 ffmpeg 直接 concat（切镜点即硬切，无交叉淡化）
- 特写段按 2.2 的帧稳定采样定格，保证切镜前后画面内容一致、循环首尾无缝
- 适用范围：GIF 核心表演点（SQL 弹窗、形态切换结果）配特写切镜；纯动作段（鼠标点 gutter、滚动、输入补全）保持全景。不每一帧都切，避免碎
- 收益：脚本重放 + 特写切镜 = 既无 ZCode 延迟、无缩放过渡卡顿，又保留官方「强调关键结果」的放大表现力

兜底图顺带受益：poster 直接取「特写切镜那帧」，比全景抽帧更能聚焦关键内容。

## 三、与既有计划的衔接

- **分镜**：8 张 GIF 的 T1~T8 分镜不变（原计划 186~245 行），逐条翻译成重放脚本，一条分镜对应脚本里一段动作序列
- **主题/构图/清晰度三件套**：不变，仍在 2026.2 沙盒、官方暗色主题、UI 150% + 编辑器 18pt + 紧致框选
- **15fps + 1.5~2× + 关 auto-zoom + 单段不拼接**：修订七的流畅性口径不变；重放脚本天然「动作紧凑、单段连贯」，把这四点贯彻得比手工更到位。其中的「关 auto-zoom」现在由 2.4 的特写切镜承接放大表现力——关闭过渡动画、保留放大强调，两者不冲突
- **兜底图**：每个 GIF 仍抽「关键结果定格帧」作同名 .png；优先取 2.4 的特写切镜帧（比全景抽帧更聚焦），抽帧逻辑仍是「从最终稳定帧抽」
- **体积 4~6MB**：重放出来的成片更紧凑，预计略低于预算，仍按下限不缩宽

### R1~R8 各张重放录制

对应原计划 T1~T8，每张产出 `/demo/<功能名>.gif` + `/demo/<功能名>.png`：

- 每张写一个重放脚本（动作序列 + 贝塞尔轨迹映射 + wait_stable 锚点 + 定格时长）
- 录制分「全景段 + 特写段」两段稳定素材，后期按 2.4 镜位表硬切 concat（切镜点硬切、无交叉淡化）
- 录屏抓帧 → 帧稳定采样 → 切段/拼镜 → ffmpeg 15fps → 调色板 → GIF
- 抽特写切镜的关键结果定格帧作 poster
- 验收沿用原计划各任务的验收项（分镜完整、文字锐利、兜底图与 GIF 内容一致），另核对 2.4 的镜位表是否覆盖到该张的核心表演点
