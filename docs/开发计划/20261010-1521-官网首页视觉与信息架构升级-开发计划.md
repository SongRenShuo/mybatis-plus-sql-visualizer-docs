## 一、背景

调研报告从目标页提取出三件结构性的事——长页面要有页内导航、要有章节节奏、要有明暗分区。这三件在当前官网首页都是空缺：

- 首页 10018px、九个区块，**没有任何页内导航**。`NavHeader.vue` 只有「功能详解 / 使用指南 / 需求池 / 关于」四个站点级路由，全首页组件里 grep 不到一个 `href="#..."`。
- **没有滚动揭示动画**。除 `NavHeader.vue` 的 `scrollY > 50` 吸顶判断外，首页所有组件都没有 `IntersectionObserver` 或滚动监听。
- **明暗节奏弱**。`#f9fafb` 与 `#ffffff` 交替（`style.css:17`、`:53`），两档明度差极小。
- **章节感缺失**。每节只有一个小 pill 徽章。

另有一项与视觉升级解耦的缺陷：

- **首屏光斑配色与品牌色不符**。`HeroSection.vue:273` 与 `:280` 的模糊光斑写死为 `#f96a48c4`（橙）与 `#ec4899`（粉），而全站品牌色是蓝 `#2e6ae0d6`（`style.css:49`、`:101`）。这是 CoolRequest 模板的遗留，生产截图里表现为 logo 后方一团粉红暖光，与蓝色标识和蓝色 CTA 相互打架。

## 二、取舍原则

吸收结构，不吸收炫技。四条具体判据：

1. **产品截图是主角。** 当前官网每节都有真实截图或动图，视觉手法应当为截图服务。目标页那种大面积 ASCII 纹理铺底会与截图争夺注意力，不采用。
2. **不引入无谓动效。** 用户对「胶囊勾选块、自创渐变、无谓图标堆叠」这类 AI 味 UI 有明确反感。目标页的 Dock 高斯放大、打字机效果、故障抖动属于此类，不采用。
3. **不引入新依赖。** 全部效果用纯 CSS 加少量原生 JS 实现，不新增动画库、不新增字体文件。
4. **动画走 `data-*` 属性约定。** 脚本只切属性，动画全写在 CSS（沿用目标页 4.8 的模式）。这条作为后续所有动效的统一约定。

## 三、范围与决策

**本轮范围：中文首页**（`index.md` → `CoolHome.vue` 九组件树）。

英文首页是另一套实现（`en/index.md` 为 `layout: home` + VitePress 默认 hero + `EnHomeFeatures` + `EnFeatureMatrix`），结构不同，不会自动同步。是否跟进需用户决定，本计划不预设。

**一个实测约束直接决定 T1 的形态。** 实测首页容器 `max-width: 1280px`，1440 视口下容器左右边界为 73px 与 1353px，即单侧留白仅 73px。目标页的左侧导航栏宽 190px，且定位在 `left: max(20px, calc((100vw - 1440px) / 2 + 20px))`——它依赖 1440 内容列外侧的留白区。**当前官网没有这个空间**：1440 视口下放不下 190px 侧栏，按容器 1280 推算需视口宽 ≥ 1660px 才能容纳 190px 侧栏加间隙。

因此 T1 的形态改为**吸顶章节条**（方案见下），侧栏方案仅作为 ≥1660px 视口的渐进增强，不进本轮。

## 四、任务清单

优先级：**P0** 本轮必做；**P1** 建议同轮或紧随；**P2** 可延后。

### T1 首页吸顶章节导航（P0）

**动机**：首页零页内导航，用户滚到中段即失去方向，也无法跳转。

**落点**：新增 `.vitepress/theme/components/home/SectionNav.vue`，挂进 `CoolHome.vue` 的模板（第 16 至 27 行）；九个区块的 `<section>` 各加 `id`。

**做法**：

- 形态取**吸顶章节条**：一条位于主导航下方、随滚动出现的横向二级导航，出现时机复用 `NavHeader` 已有的 `scrollY > 50` 状态逻辑（`NavHeader.vue:23-26`）。滚动过首屏后出现，回到首屏顶部时收起。这样不依赖任何侧边留白，1440 与移动端同一套实现。
- 滚动联动用 `IntersectionObserver` 而非 scroll 阈值计算（目标页用的是后者，但本项目首页区块高度差异大，阈值线法需要维护一张区块高度表）。当前区块高亮，同时给章节条一条细进度线。
- 窄屏（<768px）降级为可横向滚动的同一条，不做下拉菜单——下拉需额外状态管理与可访问性处理，收益不成比例。
- 桌面端 ≥1660px 时可选做侧栏增强，本轮不做。

**锚点命名**（按现有区块语义，共九节）：

| # | 区块组件 | 类名 | 建议锚点 |
|---|---------|------|---------|
| 1 | `HeroSection` | `.hero-section` | 概览 |
| 2 | `SocialProof` | `.social-proof-section` | 技术栈 |
| 3 | `FeatureAlternate` | `.features-section` | 核心能力 |
| 4 | `DocsShowcase` | `.docs-showcase-section` | 文档 |
| 5 | `FeaturesGrid` | `.more-features-section` | 更多特性 |
| 6 | `WelfareCard` | `.welfare-section` | 开源福利 |
| 7 | `Testimonials` | `.testimonials-section` | 评价 |
| 8 | `PricingSection` | `.pricing-section` | 下载 |
| 9 | `CtaSection` | `.cta-section` | 开始使用 |

**验收判据**：

- 点击任一锚点，目标区块顶部落在视口顶下方 60 至 90px（为两级吸顶导航留位），误差不超过 10px。
- 滚动过程中任一时刻有且仅有一个锚点处于高亮态。
- 1440 视口下章节条不遮挡正文首行；375 视口下 `document.documentElement.scrollWidth === 375`（无横向溢出）。
- `prefers-reduced-motion: reduce` 下章节条只切换高亮，不做滚动平滑与过渡。
- 键盘可达：章节条可 Tab 聚焦，Enter 触发跳转，聚焦态可见。

**风险**：`CoolHome.vue:43` 的 `overflow-x: clip` 与吸顶定位的交互需实测确认；已知踩坑记录提示首页内层 `div.container` 会与 VitePress 全局 `.container` 的 24px 内边距叠加，375 视口下卡片内容曾只剩 279px，章节条不得复用 `div.container` 类名。

### T2 章节眉题体系（P0）

**动机**：章节感缺失，现每节只有一个小 pill 徽章，滚动时无法提供「进入新章节」的信号。

**落点**：九个区块组件各加一行；样式统一新增到 `.vitepress/theme/style.css` 的 `.section-eyebrow` 类，不散落在各组件 scoped 样式里。

**做法**：低对比色（`--text-muted`）、大字距（`letter-spacing: 0.2em` 起）、字号 `clamp(1.5rem, 4vw, 3rem)`、全大写英文。文案与区块语义一一对应，例如 `CORE CAPABILITIES`、`DOCUMENTATION`、`MORE FEATURES`、`OPEN SOURCE`、`TESTIMONIALS`、`GET STARTED`。

**明确不做**：不加图标、不加渐变文字、不加下划线装饰。眉题只是文字。

**验收判据**：

- 九节均有眉题，文案与区块语义对应。
- 暗色模式下眉题与背景对比度不低于 3:1（可读但不抢主标题）。
- 各区块垂直高度增幅不超过 15%（避免破坏现有截图与动图的比例）。
- 375 视口下眉题不换行溢出。

### T3 首屏光斑配色修正（P0，可独立先提交）

**动机**：模板遗留的橙粉光斑与品牌蓝冲突，属缺陷而非风格偏好。

**落点**：`HeroSection.vue` 的 `.blur-circle-1`、`.blur-circle-2`。

**做法**：改为品牌蓝同色系的不同透明度，或直接删除两团光斑改用 T4 的代码对照块承担视觉重量。若保留光斑，色值必须从 `--primary-color` 派生而非写死。

**验收判据**：生产截图确认 logo 后方无暖色光晕；亮色与暗色两种模式下均成立。

**说明**：本项与视觉升级解耦，建议单独先提交，使后续改动的截图对照有一个干净的基线。

### T4 首屏代码对照块（P1）

**动机**：首屏右侧目前只有一个 320px 宽的 logo 图，占 3/5 栅格（`HeroSection.vue:120-124` 的 `2fr 3fr`），信息密度明显偏低。目标页用一段代码字面量建立技术气质，本产品有更好的真实素材可用。

**落点**：`HeroSection.vue` 的 `.hero-visual` 区块。

**做法**：左侧三行 `LambdaQueryWrapper` 链（带语法高亮），右侧生成的 SQL，静态对照。**不做打字机动画**——移动端易出问题，且属无谓动效。

**素材要求**：代码内容必须与插件真实输出一致，取自 `features/wrapper-preview` 页同一组示例，不得编造。实施时用 `sqlv_render_sql` 工具对源片段核对生成结果。

**验收判据**：

- 代码片段与插件真实输出逐字一致（核对记录写进 §实施记录）。
- 1440 与 375 两档视口下均无横向溢出。
- 移动端降级为上下堆叠，代码块可读（字号不低于 12px）。

### T5 明暗分区节奏（P1）

**动机**：浅色打底、两档灰交替，区块边界几乎不可见。

**落点**：候选为 `DocsShowcase.vue`、`PricingSection.vue`、`CtaSection.vue`（实测 top 分别为 5450、8421、9354）。建议先做 `PricingSection` + `CtaSection` 两段，`DocsShowcase` 视效果再定。

**做法**：用 `--bg-primary` 的深色变体，不写死色值；`CoolHome.vue` 外层已有 `--bg-primary` 的背景过渡。

**验收判据**：

- 深色区块内所有文字对比度达 WCAG AA（4.5:1）。
- 暗色模式下不出现深色区块与深色页面糊成一片——暗色下深色区块需改用比页面底更浅的层次，或加描边区分。
- 区块交界处无 1px 缝或背景色跳变。

**风险**：这是本轮影响面最大的一项，暗色模式下的处理最容易返工。建议排在 T1、T2 之后单独一轮实施。

**与 T3 的耦合**：若首屏一并改深色，首页节奏将变为 深→浅→深→浅→深，可能过碎。深色首屏是否做、做到哪一段，需整体排一遍再定，本计划不预设。

### T6 滚动揭示统一入口（P1）

**动机**：全站无滚动揭示，长页面显得平淡。

**落点**：新增 `.vitepress/theme/composables/useReveal.ts`（现有 `composables/` 目录下已有 `usePluginVersion.js` 与 `useTracker.ts`，命名风格对齐）；各区块 `<section>` 绑定。

**做法**：`IntersectionObserver` 加 `is-visible` 类，CSS 负责 `opacity` 与 `translateY` 过渡；`reduced-motion` 下直出；动画只播一次。

**验收判据**：

- 首屏元素不参与揭示（避免影响 LCP）。
- 滚动到区块时动画只播一次，回滚再进入不重播。
- `prefers-reduced-motion: reduce` 下无动画、内容直接可见。
- 移动端用 CDP 量测确认真机表现（已知 Edge 旧 headless 截图有全站裁切假象，不能据此判断）。

### T7 功能卡语义色（P2）

**动机**：`FeaturesGrid.vue` 六张卡（多框架支持 / 极致性能 / 智能识别 / 广泛集成 / 安全防护 / 历史记录）是清一色白卡加同色图标块，无区分度。

**落点**：`FeaturesGrid.vue` + `.vitepress/theme/data/homeHighlights.js` 的 `coolCards`。

**做法**：仿目标页的 `--track-color` 变量加派生描边（`color-mix` 派生，纯色，不做渐变）。

**前置**：需先确认六张卡确实分属不同能力域，否则颜色只是噪音。

**验收判据**：六色可区分，且暗色模式下仍可辨。

### T8 跑马灯两端渐隐（P2）

**动机**：`SocialProof.vue` 的技术栈跑马灯两端是硬切边。

**做法**：`mask-image: linear-gradient(90deg, transparent, #000 10%, #000 90%, transparent)`。

**验收判据**：两端 logo 渐隐而非被切断。

## 五、不做清单

明确排除，理由见调研报告第六节 C 档：

- ASCII 骨骼生物动画（海豚/豹/龟）：成本极高，与 SQL 调试语境无关。
- 报名/登录多步表单向导：本产品无对应业务。
- 自定义数字字体：新增字体文件与授权问题，收益仅是数字观感。
- Dock 高斯放大：无谓动效，九个导航项时收益有限。
- 全站 ASCII 纹理铺底：会压过产品截图这个主角。
- 倒计时：无对应业务。
- 打字机动画：移动端风险，属无谓动效。

### 10.3 实施中发现并修掉的问题

1. **`onMounted` 里残留已删函数的调用**（真缺陷，由验证暴露）。把滚动联动从「缓存偏移量」重构为「每帧读元素矩形」时删掉了 `measure()`，但 `onMounted` 的调用漏删，导致 `onMounted` 抛 `ReferenceError`、滚动监听从未注册、初始 `update()` 也没跑——表现是章节条永不出现、高亮不联动。**这个缺陷在点击验收里看不出来**（点击高亮是 `onClick` 直接赋值，不依赖监听），只有「手动滚动后读高亮」这条路径才暴露。
2. **首屏代码块在 375 视口被裁切**。grid 项默认 `min-width:auto`，被代码块 `white-space:pre` 的 min-content（约 470px）撑破列宽，整块宽 472px 被 `overflow-x:clip` 裁掉右侧。给 `.hero-grid > *` 加 `min-width:0` 后列宽由轨道决定，超出部分交给代码块内部滚动。
3. **章节条按钮与明暗按钮观感不一致**：按用户口径统一为同一套「图标按钮 + 悬浮软底」。

### 10.4 环境限制（记录，不冒充验证）

内嵌 webview（IAB）有三项能力缺失，直接影响验证方式，均经对照实验确认：

1. **程序化滚动不派发 `scroll` 事件**：`window.scrollTo(0, 3000)` 后 `scrollY` 正确但滚动事件计数为 0。故滚动联动只能靠手动派发 `Event('scroll')` 驱动验证。
2. **`requestAnimationFrame` 完全不触发**：1.5s 超时未回调。因此 ① 滚动节流不能依赖 rAF（已改为直接调用 `update()`，滚动事件本身按帧合并，8 次 `getBoundingClientRect` 读取开销可接受）；② 自己写的逐帧滚动动画一帧都不会跑。
3. **原生平滑滚动落点不可信**：同一份布局下 `scrollIntoView({behavior:'smooth'})` 只避让 54px、瞬时分支避让 124px（后者才是 CSS 的 `scroll-margin-top`）；`scrollTo` 的 smooth 有时完全不动；`setTimeout` 被节流到约 1s 一帧。

据此 T1 的点击跳转改为「自己算落点 + 瞬时跳转」（`window.scrollTo(0, target)`），落点由 `--home-anchor-offset` 唯一决定，与宿主对 `scroll-margin` / 平滑的实现差异完全无关。**代价是页内跳转没有平滑动画**，这是刻意取舍：结果确定、不会出现「点了没反应」，且与「不引入无谓动效」的取舍原则一致。

另：截图在该宿主上会返回滞后帧（已多次遇到，表现为内容与 DOM 读数不符），本轮验收一律以 DOM 读数为准，截图仅作观感参考。

### 10.9 真实浏览器复验（puppeteer-core + 本机 Chrome，走 CDP）

用仓内已有依赖 `puppeteer-core@24.43.1` + 本机 Chrome（`C:/Program Files/Google/Chrome/Application/chrome.exe`）headless 复验，补掉 §10.4 里因内嵌 webview 能力缺失而验不到的项。临时脚本用完即删。

**先记一条方法论教训。** 此前「8 个锚点落点均 124px」是**合成 click**（`element.click()`）下的读数，它掩盖了一个真实缺陷：真实鼠标/键盘激活时，改 hash 会触发浏览器自己的「滚动到片段」，而它按约 54px 避让（不等于 CSS 的 `scroll-margin-top` 124px），且那次滚动排在我们的 `scrollTo` 之后才落地，把落点带偏 70px——章节标题会被两级吸顶导航（108px）遮住。插桩日志（patch `window.scrollTo` + 监听 `hashchange` / `focusin` / `scroll`）显示时序：`focusin` → `hashchange` → 我们的 `scrollTo(0, 8850)` → 浏览器 `scrollTo(0, 8920.0625)`（非整数，即浏览器自身滚动）→ 稳定在 8920。已排除滚动锚定（`overflow-anchor: none` 无效）。**修法**：改 hash 后在 100ms 后按 target 收口一次（偏差 ≤4px 不动手）。修后真实鼠标点击 8/8 落在 124px。
