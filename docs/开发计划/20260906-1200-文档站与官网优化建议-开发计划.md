# 文档站与官网优化建议 — 开发计划

> 创建：2026-09-06
> 性质：**仅分析与规划，本次不实施**。基于 dev 分支功能同步全流程（20260906-1000 计划）中对两站的逐页接触，按优先级列出可执行优化项。
> 现状基线：功能同步已上线（新 JPA 页、EXPLAIN/生成测试/最近执行/自动开窗/五 ORM 入档，中英双语），线上验证通过。

---

## 一、内容质量（P1——直接影响用户决策）

### 1.1 功能页真机截图补齐

- 现状：`public/demo/` 共 9 个 SVG 占位；`batch-operation`、`code-completion`、`jpa-preview` 三个功能页无真机截图，新 JPA 页本次只能引用占位图
- 方案：真机截取三页演示图（PNG，800×450 以上），替换 `<GifPlayer>` 的 src；有条件可录 GIF（组件已支持 gif 播放逻辑）
- 验收：三个功能页首图不再是「演示位占图，截图待补」

### 1.2 FAQ 覆盖新功能高频疑问

- 现状：FAQ 未涉及本次新能力，用户第一批疑问无官方答案
- 拟增条目（每条 2~3 句）：
  - EXPLAIN 点击报错？→ 未配数据源 / Oracle·SQL Server 不支持，均会面板内提示
  - gutter 右键「最近执行记录」为空？→ 日志捕获未开启或未捕获过该位置
  - 自动展开的日志窗怎么彻底关掉？→ 手动关闭本会话抑制；设置开关永久关
  - JPA `findAllById` 为什么没有预览？→ 第一批未含，路线图已列收尾项
- 验收：FAQ 中英各加 4 条，检索词覆盖（"EXPLAIN 报错""日志窗 关不掉"等）

### 1.3 快速开始页带一句新亮点

- 现状：`guide/getting-started` 的"5 分钟路径"未提 EXPLAIN / 生成测试，新用户首日感知不到最差异化的能力
- 方案：在"第一步预览"后加半段：看到 SQL 后可点 EXPLAIN 看真实执行计划（Ultimate + 数据源），或一键生成回归脚本

### 1.4 xml-preview 与 jpa-preview 入口表去重

- 现状：HQL/JPQL 触发面表在两页各维护一份，本次同步已出现双处修改成本
- 方案：xml-preview 只保留 3 行摘要 + 指向 jpa-preview 的链接，完整表只留一处

## 二、信息架构与双语一致性（P2——降低长期维护成本）

### 2.1 中英首页双体系收敛评估

- 现状：中文首页为 CoolHome 自定义组件（六卡片、光斑、看板），英文首页为 VitePress 默认 home layout（hero + features + Feature Matrix），宣传点更新需两处不同形态各改一遍
- 方案（二选一，先评估工作量）：
  - A：英文首页切 CoolHome，卡片文案字段中英双份数据源抽到共享 js
  - B：维持两套，但把"功能宣传点"（六卡片 + Feature Matrix 行）抽成单一数据文件，两首页各自渲染
- 建议先做 B（风险低），A 列入观察

### 2.2 英文功能页历史漂移盘点

- 现状：多轮同步基本只全量更新 wrapper-preview / sql-log / xml-preview 三页，annotation-preview / batch-operation / code-completion / sql-to-java 中英版本可能有历史细节漂移（如中文页有维护过的配置说明英文页没有）
- 方案：逐页 diff 中文版结构，列出漂移清单后一次性对齐

## 三、SEO 与 AI 分发（P2——低成本高杠杆）

### 3.1 llms.txt 排除内部文档

- 现状：构建产物 `llms.txt` 的目录含 23 条 `docs/开发计划`、`docs/发行说明` 内部文档，AI 检索入口被内部决策内容稀释，功能文档权重被压低
- 方案：vitepress-plugin-llms 支持 ignore 配置，排除 `docs/` 目录（内部文档页面仍可通过 URL 访问，只是不进 AI 索引）
- 验收：llms.txt 目录只含 features / guide / about 用户文档

### 3.2 结构化数据扩充

- 现状：`SoftwareApplication` JSON-LD 只有 name/description/version
- 方案：补 `featureList`（Wrapper 预览、EXPLAIN 执行计划、测试资产生成、SQL→Java、日志还原、JPA 支持等），有机会改善搜索引擎富摘要

## 四、体验与转化（P3——锦上添花）

### 4.1 功能页直达需求池深链

- 现状：功能文档读完想提需求，需自行点导航到反馈池再描述场景
- 方案：功能页底部加一行「对这个功能有建议？直达需求池」，链接带 `?feature=<功能名>` 预填归类（反馈池前端已支持分类参数，需核对参数名）

### 4.2 DynamicChangelog 失败态核查

- 现状：更新日志走生产 Functions 代理拉 Marketplace（当前 200 正常），但 Marketplace 偶发抽风时前端表现未知
- 方案：核查组件失败分支——若白屏或永久 loading，补一行「暂时无法加载，去 Gitee Releases 查看」兜底链接

## 五、明确不做

- 竞品对比页扩充（MybatisCodeHelperPro 等商业插件逐项对比）：话术风险高、维护成本大，comparison 维持"只陈述能力差异"的现有克制口径
- 中英日多语言扩展：英文版流量数据不足以支撑第三语言
- 首页改版：刚完成移动端适配与多轮打磨，无新证据支持重设计

## 六、建议实施顺序与工作量

| 批次 | 内容 | 预估 |
|------|------|------|
| 第一批 | 3.1 llms.txt 排除 + 1.2 FAQ + 1.4 表格去重 | 半天（纯文档/配置） |
| 第二批 | 1.1 真机截图（需真机配合）+ 1.3 快速开始 | 半天 + 真机时间 |
| 第三批 | 2.1-B 宣传点数据文件抽取 + 2.2 英文漂移对齐 | 一天 |
| 第四批 | 3.2 JSON-LD + 4.1 需求池深链 + 4.2 兜底核查 | 半天 |

每批独立可上线，批次间无依赖；第一批建议随插件下个发行版文档站更新一并带上。
