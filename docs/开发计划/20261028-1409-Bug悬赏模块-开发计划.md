## 一、需求理解

### 1.1 原话拆解

用户提出五件事：

1. 开一个 Bug 悬赏模块；
2. 奖励依据是「严重程度」和「有效性」；
3. 必须管理员审核通过后才能发放；
4. 邮箱是必填项（指**悬赏提交**时必填，需求池反馈保持选填）；
5. 可以和需求池关联，或者直接在需求池基础上改造。

### 1.2 必须满足的硬约束

| 约束 | 落地口径 |
|------|----------|
| 邮箱必填（**仅限悬赏提交**） | 只有悬赏提交接口强制必填：服务端校验，前端标 `*` 并阻断提交，空邮箱/格式错误一律 400；**需求池反馈的邮箱保持选填，不受影响** |
| 管理员审核后才能发放 | 两段式状态机：审核（定级 + 定有效性 + 核定金额）→ 待发放 → 发放登记；未审核记录不能进入发放队列 |
| 按严重程度和有效性发奖 | 等级 4 档（严重/高/中/低）× 有效性 4 档（有效/部分有效/无效/重复）；金额以「等级区间 × 有效性系数」给出建议值，管理员可调整，**单笔上限 ¥18.88** |
| 可发放 | 第一期只做**人工发放登记**（支付宝/微信转账后回填单号），不接支付接口；收款账号不落库，审核通过后由管理员邮件联系 |
| 与需求池关联 | 悬赏记录可关联已有 `FR-xxxx`；管理员可把悬赏报告一键转为公开需求池 Bug 帖；需求池提交 Bug 时可勾选「同时申请悬赏」跳转 |

### 1.3 本次不做（明确边界）

- 不做在线支付、自动打款、发票/税务处理；
- 不做悬赏任务榜（「悬赏 ¥18.88 修某个已知 Bug」），第二期再加 `bb_tasks`；
- 不做用户账号体系、邮箱验证码、提交人自助修改报告；
- 不做公开悬赏列表/致谢墙（涉及隐私与漏洞细节），第二期用「自愿公开」字段再加；
- 不改 `fb_posts` 主表语义，不改需求池现有 7 态状态机；
- 不改 IDE 插件仓；插件内「一键报告」入口的悬赏跳转列为第二期可选。

## 二、结论先行：独立模块 + 与需求池双向关联

### 2.1 三种方案对比

| 维度 | A. 独立 `bb_*` 模块（推荐） | B. 直接扩 `fb_posts` | C. 复用 `fb_posts` 作正文 + 关联表 |
|------|------------------------------|----------------------|-------------------------------------|
| 公开/私密数据隔离 | 天然隔离，悬赏表默认不公开 | 需要给列表/详情/统计/动态全部加过滤，漏一处就泄露 | 正文公开、审核私密，需两套读写口径 |
| 状态机 | 独立 7 态，语义清晰 | 与需求池「待审/评估中/已规划/进行中/已完成」冲突 | 独立，但正文状态仍要兼顾需求池 |
| 邮箱必填范围 | 只对**悬赏表单**强制必填 | `fb_posts.submitter_email` 与需求池校验保持选填不变（改必填会误伤普通反馈） | 同 A |
| 发放字段 | 金额/方式/单号/审核人齐全 | 要往帖子表塞 10 余个财务字段 | 同 A |
| 改动面 | 新增表、路由、页面，不动存量 | 改 4 个前端组件 + 多个统计/通知查询 | 新增表 + 改详情读写 |
| 回归风险 | 低 | 高（需求池是线上主功能） | 中 |
| 与需求池关联 | 通过 `post_no` 双向关联 | 天然同表 | 同 A |

**结论：选 A。** 悬赏记录里同时存在「公开可讨论的 Bug 描述」和「绝不能公开的邮箱、定级、金额、发放单号」，把两类数据塞进同一张公开表，后续每个查询都要记得加过滤条件；需求池已经被双站隔离、隐藏帖、软删、投票、统计等多套规则穿过，再叠一层悬赏语义，回归面不可控。

### 2.2 与需求池的关联点（不是各做各的）

1. **提交时关联**：悬赏表单有可选的「关联需求池编号」，填 `FR-xxxx` 后服务端校验存在、未删除、同站点。
2. **需求池侧引导**：需求池提交 Bug 时出现「同时申请 Bug 悬赏」勾选框，**勾选不改变需求池表单的必填规则（邮箱仍选填）**；提交成功后沿用池内编号 toast，勾选时 toast 追加「继续申请悬赏」链接，带 `postNo` 与标题跳到悬赏页，邮箱必填只在悬赏表单里生效。
3. **管理员转公开帖**：悬赏详情提供「转为需求池 Bug 帖」，创建 `fb_posts`（`type=2`、默认隐藏、`source='bounty'`、`extra_data` 记录 `BB-xxxx`），并把 `post_no` 回写到悬赏记录。
4. **公开页互相跳转**：悬赏查询结果展示关联的 `FR-xxxx`；需求池详情在有关联悬赏时展示一枚「Bug 悬赏」徽标（第二期，需公开详情接口补一个布尔字段）。
5. **同一套通知与审计**：复用 `fb_notifications`、`sys_audit_logs`、PushPlus 邮件通道，不另起一套。

### 2.3 备选：如果坚持在需求池上改造

如果产品上认为「悬赏只是 Bug 反馈的一个标记」，可以走这条路径，但要把代价写清楚：

1. `fb_posts` 增加 `is_bounty`、`bounty_status`、`bounty_validity`、`bounty_severity`、`bounty_reward`、`bounty_reviewer`、`bounty_paid_at` 等字段，或建一张 1:1 的 `fb_bounty_reviews` 表按 `post_id` 关联；
2. 公开列表/详情/统计/动态/看板全部加过滤：未审核通过的悬赏帖不能出现在公开池，否则邮箱虽不公开，但「未定级的悬赏报告」会污染需求池排序与统计；
3. 需求池的 7 态状态机与悬赏的审核/发放状态并存，前端要同时展示两套状态，管理端改状态时要判断改的是哪一套；
4. 邮箱必填只对 `is_bounty=1` 生效，普通反馈仍然选填，校验分支要写清楚；
5. 投票、评论、合并、隐藏、软删、双站隔离、CSV 导出都要逐项确认对悬赏记录的行为。

这条路径的代码量不一定更小，但会让需求池的每个查询都多一个「是不是悬赏」的分支；一旦漏加过滤，泄露的是未审核的漏洞细节或统计污染。除非明确要「悬赏帖和普通 Bug 帖在同一个列表里混排」，否则不建议。

## 四、总体设计

### 4.1 架构

```
官网 /about/bounty（VitePress + Vue）
        │  同域 /api/v1/bounty/*
        ▼
Cloudflare Pages Function 反代（functions/api/v1/[[path]].ts）
        │  x-site-origin: plugin、x-client-ip、cf-ipcountry
        ▼
Cloudflare Worker（sql-visualizer-admin）
  ├─ modules/bounty/routes.ts        公开：policy / submissions / lookup / stats
  ├─ modules/admin/bounty.ts         管理：list / detail / review / payout / link / promote / export
  ├─ modules/admin/index.ts          既有 /admin/attachments/*（悬赏附件直接复用）
  ├─ services/bounty-policy.ts       策略 JSON 读写与校验
  ├─ services/pushplus.ts            新增审核/发放邮件函数（复用现有发送、siteBrand 与链接引导）
  └─ D1：bb_submissions / bb_attachments / bb_status_logs
        │
        ├─ R2：附件（复用 feed/ 前缀）
        ├─ PushPlus：管理员通知 + 提交人邮件
        └─ fb_posts：关联 FR / 转为公开帖
```

### 4.2 数据流

1. 用户打开 `/about/bounty`，前端拉 `GET /api/v1/bounty/policy` 与 `GET /api/v1/bounty/stats`。
2. 填写表单，附件先走 `POST /api/v1/feedback/upload` 拿到 R2 key，再连同正文 `POST /api/v1/bounty/submissions`。
3. Worker 校验邮箱、正文、关联 FR、附件元数据，写 `bb_submissions` + `bb_attachments` + `bb_status_logs`，异步通知管理员。
4. 管理员在 `/bounty` 列表打开详情，选有效性、终评等级、金额、说明，提交审核。
5. Worker 写状态日志与审计，给提交人发审核结果邮件；有效且金额大于 0 进入「待发放」。
6. 超管在详情里登记发放方式与单号，状态转「已发放」，发确认邮件。
7. 用户凭 `BB-xxxx + 邮箱` 在悬赏页查询进度。

### 4.3 公开面与管理面

| 面 | 入口 | 能看什么 |
|----|------|----------|
| 公开 | `/about/bounty` | 规则、等级金额表、聚合统计、提交表单、凭编号+邮箱查询自己的记录 |
| 管理 | `/bounty`（管理后台） | 全部记录、完整邮箱、IP/UA、附件、状态时间线、审核与发放操作、策略配置、CSV 导出 |

公开接口永不返回 `reporter_email`、`ip`、`user_agent`、`fingerprint`、`internal_note`、`paid_ref`。

## 五、数据模型

### 5.1 迁移 `0022_bounty.sql`

```sql
-- 0022: Bug 悬赏模块（20261028-1409 计划）
-- 三张表：提交记录、附件、状态日志。策略 JSON 存 sys_settings.bounty.policy。

CREATE TABLE IF NOT EXISTS bb_submissions (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    submission_no     TEXT    NOT NULL UNIQUE,          -- BB-0001，全局序列
    site              TEXT    NOT NULL DEFAULT 'plugin',-- plugin | tools
    post_no           TEXT,                             -- 关联需求池 FR-xxxx，可空
    title             TEXT    NOT NULL,
    description       TEXT    NOT NULL,                 -- 问题描述
    reproduce_steps   TEXT    NOT NULL DEFAULT '',      -- 复现步骤（必填，API 层校验）
    expected_behavior TEXT,
    actual_behavior   TEXT,
    category          TEXT,                             -- 复用需求池分类 slug
    severity_self     INTEGER NOT NULL DEFAULT 0,       -- 0 不确定 1 严重 2 高 3 中 4 低
    plugin_version    TEXT,
    ide_version       TEXT,
    os_info           TEXT,
    jdk_version       TEXT,
    reporter_name     TEXT,
    reporter_email    TEXT,                             -- 悬赏提交接口强制必填；清理任务可置空
    contact_purged    INTEGER NOT NULL DEFAULT 0,       -- 1=联系方式已按保留策略清除
    status            INTEGER NOT NULL DEFAULT 1,       -- 1 待审核 2 审核中 3 待发放 4 已发放 5 未通过 6 重复 7 已撤回
    validity          INTEGER NOT NULL DEFAULT 0,       -- 0 未判定 1 有效 2 部分有效 3 无效 4 重复
    severity_final    INTEGER NOT NULL DEFAULT 0,       -- 0 未定级 1 严重 2 高 3 中 4 低
    reward_amount     INTEGER NOT NULL DEFAULT 0,       -- 分（CNY），整数
    review_note       TEXT,                             -- 对提交人可见
    internal_note     TEXT,                             -- 仅管理端可见
    reviewer          TEXT,
    reviewed_at       TEXT,
    paid_at           TEXT,
    paid_method       TEXT,                             -- alipay | wechat | other
    paid_ref          TEXT,                             -- 转账单号/备注
    paid_note         TEXT,
    paid_by           TEXT,
    is_sensitive      INTEGER NOT NULL DEFAULT 0,       -- 安全类报告：禁止默认转公开帖
    content_hash      TEXT,                             -- 归一化正文 SHA-256，用于重复检测
    source            TEXT    NOT NULL DEFAULT 'web',   -- web | feedback | ide
    ip                TEXT,
    country           TEXT,
    user_agent        TEXT,
    fingerprint       TEXT,
    is_deleted        INTEGER NOT NULL DEFAULT 0,
    created_at        TEXT    NOT NULL DEFAULT (datetime('now')),
    updated_at        TEXT    NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX IF NOT EXISTS idx_bb_status  ON bb_submissions(status, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_bb_site    ON bb_submissions(site, status, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_bb_email   ON bb_submissions(reporter_email, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_bb_post    ON bb_submissions(post_no);
CREATE INDEX IF NOT EXISTS idx_bb_hash    ON bb_submissions(content_hash, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_bb_ip      ON bb_submissions(ip, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_bb_paid    ON bb_submissions(paid_at);

CREATE TABLE IF NOT EXISTS bb_attachments (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    submission_id INTEGER NOT NULL,
    object_key    TEXT    NOT NULL,
    file_name     TEXT    NOT NULL,
    mime_type     TEXT    NOT NULL,
    file_size     INTEGER NOT NULL,
    created_at    TEXT    NOT NULL DEFAULT (datetime('now')),
    FOREIGN KEY (submission_id) REFERENCES bb_submissions(id)
);

CREATE INDEX IF NOT EXISTS idx_bb_att_sub ON bb_attachments(submission_id);
CREATE INDEX IF NOT EXISTS idx_bb_att_key ON bb_attachments(object_key);

CREATE TABLE IF NOT EXISTS bb_status_logs (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    submission_id INTEGER NOT NULL,
    from_status   INTEGER NOT NULL,
    to_status     INTEGER NOT NULL,
    action        TEXT    NOT NULL,                     -- submit | start | review | payout | reopen | withdraw | promote | link | note
    note          TEXT,
    operator      TEXT    NOT NULL,                     -- 管理员用户名或 system
    created_at    TEXT    NOT NULL DEFAULT (datetime('now')),
    FOREIGN KEY (submission_id) REFERENCES bb_submissions(id)
);

CREATE INDEX IF NOT EXISTS idx_bb_log_sub ON bb_status_logs(submission_id, created_at);
```

默认策略写入（`INSERT OR IGNORE`，管理员可在后台改）：

```sql
INSERT OR IGNORE INTO sys_settings (key, value, description)
VALUES (
  'bounty.policy',
  '{"enabled":false,"currency":"CNY","reviewSlaHours":72,"maxReward":1888,"tiers":[{"severity":1,"label":"严重","min":1200,"max":1888,"desc":"崩溃、数据损坏、安全问题、核心功能完全不可用"},{"severity":2,"label":"高","min":800,"max":1200,"desc":"主要功能失效，存在绕过方式"},{"severity":3,"label":"中","min":400,"max":800,"desc":"边界场景错误或明显体验缺陷"},{"severity":4,"label":"低","min":100,"max":300,"desc":"文案、样式、建议类问题"}],"validityFactors":{"1":1,"2":0.5,"3":0,"4":0}}',
  'Bug 悬赏等级与奖励策略（JSON；enabled 控制计划开关）'
);
```

> 默认 `enabled=false`：迁移和部署先落地，管理员在后台确认金额与文案后再开启，避免页面一上线就收报告。

### 5.2 表职责

| 表 | 职责 | 关键约定 |
|----|------|----------|
| `bb_submissions` | 一次悬赏申报的正文、环境、联系方式、审核与发放结果 | `submission_no` 全局唯一；`site` 与需求池同口径；软删用 `is_deleted`；编号按 `BB-` + `MAX(id)+1` 生成，撞唯一约束重试一次 |
| `bb_attachments` | 附件元数据，文件本体在 R2 | `object_key` 复用 `feed/` 前缀；公开查询不返回 key |
| `bb_status_logs` | 状态时间线与操作留痕 | 每次状态变化必须写一条；关联/备注等非状态变化动作 `from_status=to_status`，提交动作 `from_status=0`；公开查询只回 `action`、`to_status`、`note`、`created_at` |

### 5.3 枚举

**状态 `status`**

| 值 | 名称 | 含义 | 公开可见 |
|----|------|------|----------|
| 1 | 待审核 | 已提交，未处理 | 是 |
| 2 | 审核中 | 管理员已受理，可能等待补充信息 | 是 |
| 3 | 待发放 | 审核通过、金额已核定，等待转账 | 是 |
| 4 | 已发放 | 已登记转账 | 是 |
| 5 | 未通过 | 无效或有效但不予奖励 | 是 |
| 6 | 重复 | 与已有报告重复 | 是 |
| 7 | 已撤回 | 管理员关闭 | 是 |

**有效性 `validity`**

| 值 | 名称 | 说明 | 金额系数 |
|----|------|------|----------|
| 0 | 未判定 | 初始值 | - |
| 1 | 有效 | 可复现、属于插件问题、非重复 | 1.0 |
| 2 | 部分有效 | 问题成立但信息不全/影响有限 | 0.5 |
| 3 | 无效 | 无法复现、环境问题、非插件问题 | 0 |
| 4 | 重复 | 已有同问题记录 | 0 |

**严重程度 `severity`（自评与终评共用）**

| 值 | 名称 | 判定参考 |
|----|------|----------|
| 1 | 严重 | 崩溃、数据损坏、安全问题、核心功能完全不可用 |
| 2 | 高 | 主要功能失效，存在临时绕过方式 |
| 3 | 中 | 边界场景错误、明显体验缺陷 |
| 4 | 低 | 文案、样式、建议类问题 |

### 5.4 策略配置

`sys_settings` 键 `bounty.policy`，结构：

```json
{
  "enabled": false,
  "currency": "CNY",
  "reviewSlaHours": 72,
  "maxReward": 1888,
  "tiers": [
    { "severity": 1, "label": "严重", "min": 1200, "max": 1888, "desc": "..." },
    { "severity": 2, "label": "高", "min": 800, "max": 1200, "desc": "..." },
    { "severity": 3, "label": "中", "min": 400, "max": 800, "desc": "..." },
    { "severity": 4, "label": "低", "min": 100, "max": 300, "desc": "..." }
  ],
  "validityFactors": { "1": 1, "2": 0.5, "3": 0, "4": 0 }
}
```

金额统一用「分」存储，避免浮点误差；展示层转元。`maxReward` 是硬上限（默认 1888 分 = ¥18.88），任何审核金额不得超过它。`GET /admin/settings` 的 SQL 需要加 `AND key NOT LIKE 'bounty.%'`，避免策略 JSON 以原始文本框出现在通用设置页。

### 5.5 容量与索引

- 悬赏量级远低于需求池，D1 免费额度足够；单条记录正文上限 5000 字符，附件最多 3 个、单个 5MB。
- 金额上限 ¥18.88 是产品定调的小额奖励，量级决定了第一期不接自动化支付：人工转账 + 登记足够，也避免支付通道的资质问题。
- 索引覆盖管理端最常用的四种查询：状态、站点+状态、邮箱、关联 FR；`content_hash` 用于重复检测。
- `paid_at` 索引支撑月度发放统计与导出。

## 六、奖励规则

### 6.1 建议金额公式

金额上限 ¥18.88，落在「小额象征性奖励」的量级，公式取整到角：

```
tierMid   = (tier.min + tier.max) / 2          // 单位：分
suggested = round(tierMid * validityFactor / 10) * 10   // 取整到角（10 分）
```

- 有效（1.0）：取等级区间中值；
- 部分有效（0.5）：取中值一半；
- 无效/重复（0）：0，不进入发放队列；
- 管理员可在 0 到 `maxReward`（1888 分）之间调整；超出该等级区间时前端提示「高于/低于该等级区间」，要求填写审核说明。

### 6.2 示例

| 等级（默认区间） | 有效性 | 建议金额 | 说明 |
|------|--------|----------|------|
| 严重（¥12.00–18.88） | 有效 | ¥15.40 | 中值取整到角 |
| 严重（¥12.00–18.88） | 部分有效 | ¥7.70 | 中值 × 0.5 |
| 高（¥8.00–12.00） | 有效 | ¥10.00 | 中值 |
| 高（¥8.00–12.00） | 部分有效 | ¥5.00 | 中值 × 0.5 |
| 中（¥4.00–8.00） | 有效 | ¥6.00 | 中值 |
| 低（¥1.00–3.00） | 有效 | ¥2.00 | 中值 |
| 任意 | 无效/重复 | ¥0 | 状态直接进未通过/重复 |

> 区间为默认值，管理员可在策略里改；`maxReward` 是硬上限，改等级区间也不能超过 ¥18.88。

### 6.3 审核规则

- 有效性 1/2 且金额 > 0：状态转 3（待发放）。
- 有效性 1/2 但金额 = 0：状态转 5（未通过），`review_note` 必填，用于说明「问题有效但本次不奖励」。
- 有效性 3：状态转 5，`review_note` 必填。
- 有效性 4：状态转 6，`review_note` 必填，建议填写重复的 `FR-xxxx` 或 `BB-xxxx`。
- 终评等级在有效性 1/2 时必填；3/4 时可留 0。
- 金额上限 `maxReward`，服务端强制；等级区间只做前端提示，不做硬拦。

## 七、状态机

```
                    ┌──────────────┐
                    │ 1 待审核      │
                    └──────┬───────┘
                           │ 开始审核（可选）
                           ▼
                    ┌──────────────┐
              ┌─────│ 2 审核中      │─────┐
              │     └──────┬───────┘     │
     请求补充 │            │ 审核        │ 撤回
              └────────────┘             ▼
                           │        ┌──────────────┐
                           │        │ 7 已撤回      │
                           ▼        └──────────────┘
              ┌────────────────────────┐
              │ 3 待发放（有效+金额>0） │
              └───────────┬────────────┘
                          │ 超管登记发放
                          ▼
              ┌────────────────────────┐
              │ 4 已发放                │
              └────────────────────────┘

   审核为无效/金额 0 → 5 未通过
   审核为重复        → 6 重复
   5/6 可「重新打开」→ 1 待审核（保留历史日志）
```

| 当前 | 动作 | 权限 | 结果 | 副作用 |
|------|------|------|------|--------|
| 1 | 开始审核 | 可编辑 | 2 | 记录 `reviewer`；可选邮件告知「已受理」 |
| 1/2 | 审核通过（有效/部分有效，金额>0） | 可编辑 | 3 | 写 `validity`、`severity_final`、`reward_amount`、`review_note`、`reviewed_at`；发审核结果邮件 |
| 1/2 | 审核不通过（无效/重复/金额 0） | 可编辑 | 5 或 6 | 同上；重复时 `review_note` 必填 |
| 2 | 请求补充 | 可编辑 | 2 | 只写日志与 `review_note`，发邮件；不改变状态 |
| 3 | 发放登记 | **仅超管** | 4 | 写 `paid_at`、`paid_method`、`paid_ref`、`paid_by`；发发放确认邮件；审计 |
| 3 | 撤销通过 | 仅超管 | 2 | 仅当尚未发放；写日志与审计 |
| 5/6 | 重新打开 | 可编辑 | 1 | 清空 `validity`、`severity_final`、`reward_amount`、`reviewed_at`；保留历史日志 |
| 任意（未发放） | 撤回 | 可编辑 | 7 | 写日志与审计；不删附件，按保留策略清理 |

**并发与幂等**：审核与发放都用「当前状态必须匹配」的条件更新（`UPDATE ... WHERE status = ?`），受影响行数为 0 时返回 409，避免两个管理员同时操作把状态覆盖。每次状态变化同时写 `bb_status_logs` 和 `sys_audit_logs`。

## 八、API 契约

统一响应格式沿用现有 Worker：`{ code, message, data }`；HTTP 状态码与 `code` 一致。公开接口走 `/api/v1/bounty`，管理接口走 `/api/v1/admin/bounty`。

### 8.1 公开接口

#### `GET /api/v1/bounty/policy`

返回当前策略，供页面渲染等级表和开关：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "enabled": false,
    "currency": "CNY",
    "reviewSlaHours": 72,
    "maxReward": 1888,
    "tiers": [
      { "severity": 1, "label": "严重", "min": 1200, "max": 1888, "desc": "..." }

    "validityFactors": { "1": 1, "2": 0.5, "3": 0, "4": 0 }

```

- 不返回 `internal_note` 等管理字段；
- 读 `sys_settings.bounty.policy`，缺失/损坏时回落到代码内默认值；
- 可加 `Cache-Control: public, max-age=300`，减少 D1 读。

**审核请求示例**：

```json
{
  "validity": 1,
  "severity": 2,
  "rewardAmount": 1000,
  "reviewNote": "已复现，按高等级有效处理",
  "internalNote": "与 FR-0123 同一处 JOIN 解析问题"
}
```

`rewardAmount` 单位是分。服务端校验：`validity` 1..4；`severity` 0..4；`rewardAmount` 0..`maxReward`；`validity=1/2` 时 `severity` 必须 1..4；`validity=3/4` 或金额 0 时 `reviewNote` 必填。

**发放请求示例**：

```json
{ "method": "alipay", "ref": "20261030-123456", "note": "已转账并截图留档" }
```

**转公开帖规则**：

- 已关联 `post_no` 时返回 409，先解除关联或直接使用已有帖；
- `publish` 缺省 `false`，创建隐藏帖（`is_hidden=1`）；传 `true` 时直接公开（`is_hidden=0`），该分支仅超管可用；
- `is_sensitive=1` 时默认拒绝转帖；即使超管也要显式传 `publish` 并填写 `internalNote`，避免安全细节误公开；
- 创建 `fb_posts`：`type=2`、`status=1`、`source='bounty'`、`submitter_name` 取 `reporter_name` 或「匿名」、`submitter_email` 取 `reporter_email`、`category` 取悬赏分类、`site` 同悬赏记录、`extra_data={"bountySubmissionNo":"BB-0001"}`；
- 正文由服务端拼装：问题描述 + 复现步骤 + 期望/实际 + 环境，绝不包含邮箱、金额、审核备注；
- 回写 `bb_submissions.post_no`，写状态日志 `action=promote` 与审计。

### 8.3 校验规则

| 字段 | 规则 | 错误文案示例 |
|------|------|--------------|
| `title` | 5–200 字符 | 标题长度需在 5-200 字符之间 |
| `description` | 20–5000 字符 | 问题描述至少 20 个字符 |
| `reproduceSteps` | 10–5000 字符，必填 | 请填写复现步骤（至少 10 个字符） |
| `expectedBehavior` / `actualBehavior` | 0–2000 字符 | 期望结果不能超过 2000 字符 |
| `category` | 必须在当前站点分类集合内 | 无效的分类 |
| `severitySelf` | 0–4 | 无效的自评等级 |
| `reporterEmail` | 必填、≤120、正则 `^[^\s@]+@[^\s@]+\.[^\s@]+$`（**只校验悬赏提交；需求池 `submitterEmail` 保持选填**） | 邮箱为必填项 / 邮箱格式不正确 |
| `reporterName` | 0–50 | 昵称不能超过 50 个字符 |
| `pluginVersion` / `ideVersion` | 0–32，拒绝控制字符 | 版本号不能超过 32 个字符 |
| `osInfo` | 0–100 | 系统信息不能超过 100 个字符 |
| `jdkVersion` | 0–32 | JDK 版本不能超过 32 个字符 |
| `postNo` | `^FR-\d{1,6}$`，存在、未删除、同站点 | 关联的需求编号不存在 |
| `source` | `web` / `feedback` / `ide`，缺省 `web` | 无效的来源 |
| `attachments` | 最多 3 个；字段完整；文件名/类型/大小合法 | 每帖最多 3 个附件 |
| `website` | 必须为空 | （静默拒绝或 400） |
| 请求体 | UTF-8；含 `\uFFFD` 直接 400 | 请求体编码错误：请使用 UTF-8 编码提交 |

正文统一做控制字符清洗（保留换行与制表符），长度按字符计。

### 8.4 错误码

| HTTP | `code` | 场景 |
|------|--------|------|
| 400 | 400 | 参数校验失败、状态不变、非法操作 |
| 403 | 403 | 只读管理员执行写操作、非超管发放、计划已关闭 |
| 404 | 404 | 编号不存在、邮箱不匹配、附件不存在 |
| 409 | 409 | 状态冲突（并发操作、已关联、已发放） |
| 429 | 429 | 限流 |
| 500 | 500 | 未捕获异常 |

### 8.5 限流与反滥用

- `POST /api/v1/bounty/submissions`：KV 规则 3 次/小时/IP（新增 `RATE_LIMITS` 条目）；另用 D1 计数做 10 次/天/IP、5 次/天/邮箱，避免换 IP 刷。
- `POST /api/v1/bounty/lookup`：20 次/小时/IP，防编号枚举。
- 限流 429 同时触发预警规则 `bounty_flood`（在 `services/alert.ts` 的 `AlertRule` 与 `ALERT_RULES` 中新增，label「悬赏灌水」）。
- 重复检测：提交时计算 `content_hash`（归一化标题+描述+步骤，去空白与标点后 SHA-256），管理端列表对 30 天内相同 hash 的记录显示「疑似重复」标记；不自动拒绝。
- 同一邮箱 24 小时内最多 5 封通知（复用 `checkEmailRateLimit`）。
- 上传接口沿用现有进程内限流与类型/大小校验；悬赏不新增上传端点。

### 9.2 页面结构

1. 顶部：标题、一句话说明、两个按钮（提交报告 / 查看奖励标准）、聚合统计条（累计收到、已发放、平均响应）。
2. 奖励标准：四档等级卡片或表格，金额从 `/policy` 读取；旁边写清「最终金额以审核为准」。
3. 流程：提交 → 初审（72 小时内）→ 定级核定 → 转账发放，四步横向/纵向步骤条。

6. 规则与边界：哪些算有效、哪些不算、重复怎么处理、安全问题怎么报、隐私说明。
7. 常见问题：`::: details` 折叠，避免页面过长。

第 1~6 块由 `BountyPage.vue` 及其子组件渲染；第 7 块与「规则与边界」的静态段落写在 `about/bounty.md` / `en/about/bounty.md`，便于直接改文案。

### 9.3 表单设计

字段分组，避免一屏堆太多：

- 问题信息：标题、问题描述、复现步骤、期望结果、实际结果；
- 环境：插件版本、IDE 版本、操作系统、JDK 版本（版本选择复用 `VersionSelect`）；
- 分类与自评：功能分类（复用 `FilterSelect`）、自评严重程度（四选一，可「不确定」）；
- 联系方式：昵称（选填）、邮箱（必填，说明「仅用于审核与发放联系，不公开」）；
- 关联需求：可选 `FR-xxxx`，从需求池跳转时自动带入；
- 附件：最多 3 个，复用现有上传逻辑；提交前 trim 标题/描述/步骤，上传中禁用提交，上传失败展示后端 message，缩略图用 object URL 预览并回收（沿用 T9–T13 的交互标准）；
- 安全类：勾选「这是安全问题，请勿公开细节」；
- 提交按钮与校验提示。

**邮箱必填的交互**：标签带 `*`；失焦即校验；提交按钮在邮箱为空或格式错误时禁用，并在按钮上方显示具体原因。服务端仍做最终校验。

悬赏表单是页内内联（不是弹窗），提交成功后可以显示常驻成功卡；这与需求池「弹窗关闭 + 池内 toast」的场景不同，不要照搬 toast。

**与需求池的跳转**：

- 需求池表单在 `type === 2`（Bug）时显示「同时申请 Bug 悬赏」勾选框；
- 勾选只表示「有意申请悬赏」，需求池表单的校验规则不变（邮箱仍选填、按钮禁用条件不变）；
- 成功反馈沿用 T13/T14 的池内编号 toast（弹窗会立刻关闭，表单内成功块看不到，**不再新增「成功页」**）；`FeedbackForm` 的 `done` 事件扩展为 `done(postNo, { bountyIntent })`，`FeedbackPool` 与 `FeedbackPage` 两个入口都透传；
- 勾选悬赏时，`FeedbackPool.notifySubmitted(postNo, { bountyIntent })` 把 toast 延长到 15s 并追加「继续申请悬赏」链接，指向 `/about/bounty?postNo=FR-xxxx&title=<encodeURIComponent(title)>`；不做自动跳转，避免打断用户；未勾选时保持现有 6s 纯文本 toast；
- 昵称与邮箱通过 `sessionStorage` 一次性传递（键 `bounty:prefill`），悬赏表单读取后立即删除，避免邮箱进入 URL；跳转用同标签页导航，保证 `sessionStorage` 可读；
- 悬赏页收到 `postNo` 时展示「已关联需求 FR-xxxx」并锁定该字段（可点「取消关联」）。

## 十二、安全、隐私与合规

### 12.1 邮箱与 PII

- 悬赏提交必填邮箱，但邮箱只在管理端可见：公开接口与公开页面都不出现，仅管理端详情和导出 CSV 可见；需求池反馈的邮箱仍为选填，两套校验互不影响；
- 查询必须「编号 + 邮箱」双匹配，错误统一 404，不泄露编号是否存在；
- 收款账号不在表单收集、不落 D1；审核通过后管理员用邮箱联系，线下确认；
- 未通过/重复/撤回记录 90 天后清除 `reporter_email`、`reporter_name`、`ip`、`user_agent`，置 `contact_purged=1`；已发放记录保留 365 天后同样清除；
- 管理端导出 CSV 含邮箱，属于敏感操作，必须写审计；导出要求可编辑权限，只读管理员不开放批量导出。

### 12.2 反滥用

- 限流三层：KV 每小时、D1 每天按 IP、D1 每天按邮箱；
- honeypot 字段；
- 正文长度与字符校验，拒绝控制字符与替换符；
- 重复 hash 标记；
- 上传类型白名单与 5MB 上限；
- 发现灌水可复用现有 IP 封禁与预警体系，不另造一套。

### 12.3 附件

- 复用 `POST /api/v1/feedback/upload`，扩展名白名单与 MIME 校验沿用；
- `bb_attachments` 只存元数据；公开查询不返回 key；
- 管理端下载复用 T8 的 `GET /admin/attachments/*`（JWT + `feed/` 前缀）；该端点不按 `bb_attachments` 归属校验，key 不公开，与需求池附件同口径；
- 图片 `inline`，其他类型 `attachment`，统一 `nosniff`；
- 附件清理：悬赏记录被软删或联系方式清除后，按保留策略删除 R2 对象与 `bb_attachments` 行；孤儿上传（上传后未提交）暂不处理，作为已知限制记录。

### 12.4 审计

- 审核、发放、重新打开、撤回、关联、转帖、策略修改、导出全部落 `sys_audit_logs`；
- 审计 detail 不含完整邮箱（用打码或记录 submission_no 即可），避免审计表成为第二个 PII 仓库；
- 状态日志 `bb_status_logs` 与审计双写：前者给公开时间线用，后者给管理追责用。

### 12.5 数据保留
