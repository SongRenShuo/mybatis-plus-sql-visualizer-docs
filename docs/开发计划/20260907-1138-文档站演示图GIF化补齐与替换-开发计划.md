## 二、录制规范

统一约定一次到位，避免录完返工：

### 2.1 工具选型：Recordly（用户指定，已确认本机安装）

用 **Recordly** 替代最初设想的 PixPin。理由：

- 原生 GIF 导出（mp4 / looping GIF 二选一），省去外部转码环节
- 内置自动缩放（auto-zoom）、动态模糊光标、循环光标路径，成片演示力明显强于 PixPin 裸录
- 免费开源，本机已装（用户 2026-09-07 确认）

分工约定：

- **Recordly**：负责 T1~T8 八个 GIF 的录制与导出
- **PixPin**：仍保留，负责补镜头级别的截图与快速局部捕捉（例如分镜首尾帧核对、突发异常取证），不做主录制
- 首次使用注意：确认 Recordly 的自动缩放效果在文档站容器里观感是否合适，不合适则关掉该项，用固定区域录制兜底

### 2.2 站点实际显示宽度与清晰度基准（硬性）

清晰度以「页面上的真实显示宽度」为准。已核实两处投放位的显示尺寸：

| 投放位 | 显示宽度 |
|--------|---------|
| 功能页 GifPlayer（正文列，VitePress 默认，含右侧 aside） | 约 688px |
| 首页 DocsShowcase（max-width 90rem 双栏，视频列约 60% 宽） | 约 1000~1100px，object-fit: cover（16:10 裁切） |
| 首页 FeatureAlternate（object-fit: cover, min-height 300px） | 约 550~600px |

由此定两条铁律：

- **录制源宽 1600px 左右**（源码区缩放后换算到站点显示有约 1.6~2.3 倍余量），GIF 导出统一 **缩放到宽 1280px**——覆盖最宽的 DocsShowcase，在功能页 688px 列里是超采样，文字必然锐利。**唯一例外：wrapper-preview 因首页 DocsShowcase 共用，导出宽度升到 1440px**（见 2.7 的超采样结论），其余七张维持 1280
- **缩放比不低于 0.85 且导出后逐张人眼核对**：文字像素感重或发虚即调大 UI 重录，不以「能看清」为最低线，以「像原生截图一样锐利」为验收线

### 2.3 环境：2026.2 沙盒（硬性）+ 清晰度三件套

**沙盒版本（硬性）**：录制（Recordly）与截图（PixPin 补拍、poster 抽帧源画面）一律在插件仓库的 **2026.2 runIde 沙盒**里做，不用日常 IDE，也不用 2024.3 默认沙盒。切换按插件仓库 `docs/架构设计/03-开发与测试指南.md` 2.1 执行：临时改插件仓库 `build.gradle.kts:64` 为 `intellijIdeaUltimate("2026.2.1")` → `./gradlew runIde`（跑前先查并行登记表）→ 全部录制结束 `git checkout build.gradle.kts` 还原。三个注意：

1. 2026.2 沙盒 Ultimate 激活：优先尝试**主 IDE 激活信息复制**方案——把 `%APPDATA%\JetBrains\IntelliJIdea2026.2\idea.key`（UTF-16 的 certificate-key）复制为沙盒 `IU-2026.2.1/config/idea.key`。**2026-09-09 实测无效**：直接复制不生效，将其转码后以 Activation code 方式手动激活也报 Key is invalid（证书绑定主 IDE 安装，不可迁移）。结论：沙盒以**免费评估/非商业授权**模式运行即可满足录制需要（实测全部 Ultimate 功能可用，仅标题栏有 Start Free Trial 入口）；如未来评估到期受阻，再由用户手动登录 JetBrains 账号激活。约 2GB 发行版下载走 gradle.properties 已配代理，一次性成本放在 T0 前置完成；
2. `-PplatformVersion` 命令行参数当前未接线，不可用，只能改 build.gradle.kts；
3. 本任务不跑 testDatabase，无 jdbc-drivers 版本耦合，无需关心该任务的 2024.3 路径写死问题。

沙盒按版本分目录、与日常 IDE 完全隔离，但设置全新——下述三件套参数要在 2026.2 沙盒里重新设一遍。

**主题**：录制前手动切换到 **IDEA 官方演示同款暗色主题**（Settings > Appearance & Behavior > Appearance > Theme，选 Dark/Islands Dark 一类官方暗色基准；2026-09-09 修订六确认官方演示为暗色，此前「沙盒默认即官方同款浅色」的理解作废）。设置一次后整个录制周期不再改动，不做暗色双版本、也不录浅色版本。

清晰度靠「窗口构图 + IDE 缩放 + 字号」三者配合，不是单一开关：

1. **IDEA UI 缩放（首选手段）**：`Settings > Appearance & Behavior > Appearance`，Windows 下调到 **150%**（大显示器可试 175%）。UI 缩放等比放大全部界面（含 gutter 图标、弹窗、面板），是提高「每像素信息密度」最直接的方式
2. **编辑器字号 18pt 起**：`Settings > Editor > Font`。录制分镜里出现整段 Wrapper 链 + 弹窗 SQL 的场景较多，18pt 保证代码区在 150% 缩放下依然读得清
3. **窗口构图代替缩小窗口**：不推荐为凑比例硬缩 IDEA 窗口——窗口缩小后内容等比变小、文字反而更糊。正确做法是 UI 缩放放大后，把 IDEA 窗口开到接近全屏，**只框选编辑器 + 弹窗/工具窗口的紧致区域**录制，把「画面物理像素」全花在有效内容上

辅线：IDEA 界面字体（`Appearance > Use custom font`）建议 15pt 起，弹窗标题、面板按钮等非代码文字同样清晰。

### 2.4 画面与节奏

本节各项约定以「对齐 JetBrains 官方 whatsnew 演示视频风格」为总纲，2.7 是逐帧分析得出的官方风格基准，两者对照执行：

- **左侧项目目录树窗口保持关闭（修订九硬性项）**：录制前确认 Project 工具窗已隐藏（面板 ✕ 或 Shift+Esc），全片任何帧不得出现目录树；每张 take 开机后先抓帧自查一眼，若被 IDE 自动打开（如打开新工程触发）先关掉再录
- 只录编辑器加相关弹窗/工具窗口，不要带桌面杂项；**画面里严禁出现 Windows 任务栏**（2026-09-09 修订六：只允许出现 IDE 页面本身）——Recordly 选屏幕全屏采集时，成片必须经 ffmpeg 裁掉底栏与 Recordly HUD 区域再出 GIF，或改用窗口采集模式（对应官方「全窗口构图、主体内容占 70%+、留白少而均匀」）
- 节奏模拟真实用户，鼠标移动与点击之间留自然停顿，关键结果（SQL 出现、代码生成）停留 1~2 秒再动（对应官方「动静反差节奏」：长静止 + 动作瞬间爆发，静止是常态不必抢节奏）
- 操作演示以单条主线走完为限，不做多轮反复操作（官方每支视频只演示一个功能点）；**录制时就把操作动线排紧凑、整体控制在 6~15 秒，尽量单段直出、不依赖后期裁剪拼接**（2026-09-09 修订七：多段裁剪会引入无过渡跳切，被感知为卡顿）
- 光标仅在有操作时出现/移动，移动平滑带动态模糊（Recordly 光标选项开启），静止段光标不乱晃；**本机 Recordly 不支持原生捕获，平滑光标实际未生效**（录制后提示「无法渲染动画光标叠加层」），光标为真实采样点瞬移，转低帧 GIF 需靠高帧率+低提速缓解，见 2.4 结尾帧率条目
- 时长单个 6~15 秒，首尾帧尽量一致，循环不跳（对应官方 mp4 loop 无缝循环、无淡入淡出）
- 主题一律官方演示同款**暗色**（2026-09-09 修订六，见 2.3），录制前手动切换、录制中不手动改主题；不做暗色双版本，也不录浅色版本
- **auto-zoom 关闭（修订七）**：2026-09-09 实测 1.5× 自动缩放在低帧 GIF 下过渡台阶明显，改用**固定构图**拍摄——靠 2.3 的紧致框选把有效内容拍满，不做局部自动放大；官方表现力回归构图与节奏本身
- **GIF 帧率 15fps、录制素材不做 3× 提速（修订七）**：2026-09-09 首轮成品 10fps 全部卡顿（两轮丢帧叠加：Recordly 3× 提速丢了 2/3 + ffmpeg fps=10 再抽一层，叠加后逐帧 100ms 位移跳变明显，且光标平滑未生效放大跳感）。修订后帧率固定 **15fps**、提速降到 **1.5~2×**、尽量单段不拼接，三者配合消除卡顿。体积优先保证流畅与清晰，1280 宽底线不动，超 3MB 接受落在 4~6MB 区间（见 2.5 修订七口径）

### 2.5 体积控制与静态兜底（强制）

GIF 体积随画面复杂度波动大，规范如下：

- **帧率基准 15fps（修订七，2026-09-09）**：为保证光标移动、弹窗/缩放过渡在 GIF 下流畅，放弃此前 fps=12 的体积优先口径。逐张实测体积——15fps 下预计单张 4~6MB，**缩放不许低于 1280 宽**（2.2 的清晰度底线优先于体积；流畅+锐利优先于压到 3MB 以内，允许 4~6MB，靠 poster 兜底承担加载风险）
- **每个 GIF 必须配套一张静态兜底图**（poster）：取 GIF 关键内容帧（如 SQL 已渲染完成的弹窗画面，即各分镜里「停 2 秒」的那一帧），通过 ffmpeg 抽帧或 Recordly 时间线导出，命名为 `/demo/<功能名>.png`，与 GIF 同名不同后缀
- 抽帧后如需微调，用 PixPin 补拍同角度静态图也可
- 兜底图是硬性要求，不是可选项——弱网、动图加载失败、低性能设备三种场景都靠它

### 2.6 命名

沿用现有约定 `/demo/<功能名>.gif` 与 `/demo/<功能名>.png`，与 features/*.md 一一对应。

GifPlayer.vue 需小幅改造：props 增加 `poster`（已存在，无需加）之外，img 分支默认渲染逻辑改为「GIF 加载完成前优先展示 poster，加载后切 GIF」，并接受 poster 可选（兼容旧调用）。具体改造见 T9 前置任务 T9a。

### 2.7 官方演示视频调研结论（JetBrains whatsnew 2026.2）

为回答「官方录制效果好在哪、有什么可吸收」，抽取了 IDEA 2026.2 whatsnew 页 8 支官方功能演示视频中的 2 支完整样本逐帧分析：DB_migration（66s）与 Spring_Security（91s），均为 h264 1920×1080@30fps、码率 4.8~5.5Mbps、单支 45~54MB；页面 video 元素显示 732×412，即官方以约 2.6 倍超采样投放（其余样本因网络多次截断下载损坏，样本量足够，不再补下）。

**可直接吸收（已并入本计划各处）**：

1. **官网示例主题 + 超大编辑器字号**：官方帧里代码字号观感达 20px+（1080p 下），主题为官方暗色（2026-09-09 修订六修正：官方演示同款为暗色主题，非浅色）——本计划的主题约定（2.3）与官方同源；印证 2.3 三件套的 150% 缩放 + 18pt 方向正确，可再试 20pt 对比
2. **全窗口构图但不塞满**：官方保留完整 IDE 窗口（项目树 + 编辑器 + 工具窗），主体内容占画面 70% 以上，四周留白少而均匀——与 2.3「框选紧致区域」同构，录制时保持该比例
3. **动静反差节奏**：场景检测显示官方视频静动分布极不均匀——Spring_Security 91 秒里仅 9 个画面突变点（8~53 秒连续 45 秒近乎静止），静止段画面零变化、动作瞬间集中爆发。印证 2.4 的「关键结果停留 1~2 秒」，且静止是演示的常态，不必抢节奏
4. **首尾帧一致、无缝循环**：官方 mp4 带 loop 属性直接循环，无淡入淡出，与 2.4 约定一致
5. **视频 + 同帧 poster 结构**：官方每支视频配同帧 PNG poster，「动图 + 静态兜底」方案得到官方背书，2.5 的强制兜底要求维持

**Recordly 能力项（录制时按需开启）**：auto-zoom（官方表现力的主要来源，操作时自动放大局部区域）、平滑光标移动、点击涟漪。首条 GIF 先验证 auto-zoom 观感（风险备注已有此约定），生硬则关掉用固定区域兜底。

**坚持 GIF 导出相对官方 mp4 的损失（确认接受，不再纠结）**：

- 帧率 30fps → 15fps：光标移动与缩放过渡比官方 30fps 少一半采样点。缓解：帧率固定 15fps + 提速降到 1.5~2× + 关闭 auto-zoom 用固定构图（修订七），配合「录制时操作排紧凑、单段不拼接」消除卡顿（官方是 30fps 平滑动画 + 手动播放，本计划以 GIF 自动循环换取冷启动即播的便捷，不用 mp4 点击播放）
- 256 色调色板：IDE 界面抗锯齿边缘有轻微色带风险。缓解：暗色低饱和主题下基本不可见，无需特殊处理；如个别张深色大面积渐变处出现可见色带，改 stats_mode=diff + 局部提高 max_colors 重压
- 无法 mp4/webm 双源自适应、无 h264 压缩效率：由 2.5 的同名 PNG 兜底承担加载风险，这正是兜底图存在的意义

**规格确认**：官方 1920 源 / 732 显示 = 2.6 倍超采样；本计划功能页 1280 / 688 = 1.86 倍、FeatureAlternate 1280 / 550 = 2.3 倍，均在官方同量级；唯一低于量级的是首页 DocsShowcase（1280 / 1100 ≈ 1.16 倍），故 wrapper-preview（首页共用）导出宽度升到 **1440**（1.31 倍）。T11 清晰度抽查时 DocsShowcase 处重点核对该张；体积方面按 2.5 修订七口径，全八张统一接受 4~6MB、不计较 3MB 上限。

T9c 弱网加载体验优化（修订八新增）：

- **问题**：当前 GifPlayer「GIF 未就绪时 poster 占位」依赖 poster 先加载成功，而 GIF 与 poster 同处弱网加载竞态——用户先看到的是空白/骨架，等 poster 请求响应才出图，再等 GIF 下载完成才切换动图，全程「空白→静态→动图」两段等待，弱网体验差。
- **目标**：改为「**先快速出 poster 静态图 → GIF 加载完成后淡入覆盖**」，弱网/低性能场景第一时间有内容可看，动图作为增强层平滑衔入。
- **GifPlayer.vue 改造**：
  1. poster 从一开始就以 `position: static`（或绝对定位在上层）稳定渲染，不再依赖 GIF 状态切换撑高——容器高度由 poster（或 padding-box 比例）固定，避免 GIF 未到时布局抖动；
  2. GIF img 绝对定位叠在 poster 之上，初始 `opacity: 0`，`onload` 后加过渡 `fade in` 到 `opacity: 1`；GIF `onerror` 时保持 poster 展示（永久回落）；
  3. poster 自身 `@load` 后也可做轻量淡入，避免海报图请求期间的生硬。
- **首页原生 img 同步补齐（DocsShowcase / FeatureAlternate）**：这两个地方是原生 `<img>` 不是 GifPlayer，需同样实现「poster 先出 + GIF 淡入覆盖」——最小方式是用容器包裹 poster 与 GIF 两枚绝对定位 img（poster 在下常驻、GIF 在上 onload 淡入、onerror 撤下），不引新依赖。
- **验收**：Chrome DevTools Network 限速（Slow 3G）下，功能页与首页两处都是「先见静态图，几秒后动图淡入」，无空白闪烁、无布局跳动；正常网速下淡入过渡不突兀；GIF 彻底加载失败（断网）时 poster 常驻不消失；亮暗色各过一遍。
