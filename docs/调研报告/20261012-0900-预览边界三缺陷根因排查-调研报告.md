## 缺陷一：无动态条件的 JOIN 链拿不到「JOIN 图」Tab

**根因**
- `ui/SqlPreviewPanelResultView.kt:196-198`：`updateDiagramTab` 唯一判据 `result.previewModel?.statement`，null 即 `removeDiagramTab()`。
- `ui/SqlPreviewServiceEnhancements.kt:282,321`：`previewModel = if (views.isEmpty()) null else SqlPreviewModel(...)`。
- `ui/SqlPreviewService.kt:1241-1245`：`collectConditionViews` 只收 `statement.conditions`，**joins 不产生 ConditionView** → `selectFill` 链（selectAll+leftJoin+fill，无 eq/like）views 空 → previewModel=null → 无 Tab；`selectJoinList`（带 eq/like）有 Tab。与录屏现象完全吻合。
- JOIN 图确实**依赖 previewModel**：`PreviewResult` 里 statement 只存在于 previewModel.statement，`result.sql` 是纯文本，面板无从判断 JOIN（`ui/SqlPreviewPanelSqlView.kt:180-244` 的旧文本路径四分支核对）。

**判定**：缺陷（判据载体选择错误）。**已修**（`0c7a5d6`）。

**最小修复面**：不改 previewModel 构造条件（放宽会把无条件链从旧文本路径切进模型级重生成，破坏性能语义）。在 `PreviewResult` 增独立字段 `diagramStatement: SelectStatement?`，两处构造赋 `(statement as? SelectStatement)?.takeIf { it.joins.isNotEmpty() }`（JPA 的 `buildJpaPreviewResult` :272-286 同改——JPA 联表派生查询有同款缺口）；`updateDiagramTab` :197 改 `previewModel?.statement ?: result.diagramStatement`。旧渲染路径零改动。

**佐证**：`ui/SqlPreviewPanelTest.kt:122`（T-F8 既有测试即以带 previewModel 的结果驱动该入口）；demo 语料 `UserServiceImpl.java:182-208` 三段 fill 链均无条件。

## 缺陷二：开多租户注入后参数回填失效

**根因**——不是占位符错位（回填按 source 匹配非序号），是**参数历史缓存键漂移**：
- 注入点 `SqlPreviewServiceEnhancements.kt:431-436`（发生在 buildPreviewResult 之前，`SqlPreviewService.kt:328`）→ `result.sql` 文本多出 `AND tenant_id = ?`。
- 跨预览参数持久化只靠 ParamHistoryCache；键 = `tableName:SHA-256(SQL全文)`（`ui/SqlPreviewPanelParamPanel.kt:1211-1216`、`ParamHistoryCache.kt:703-706`）→ **SQL 文本一变键就变** → `recallFromHistory`（ParamPanel.kt:1229-1231）miss → 已回填的 `status=41` 退回占位符；500ms 防抖后新键还会以空值覆盖落库。关掉开关即复原——与「同帧退回」现象闭环。逻辑删除开关（字面量也改 SQL 文本）同理受影响。

**判定**：缺陷（回填持久化对拦截器注入的 SQL 后处理不稳定）。**已修**（`0c7a5d6`）。

**最小修复面**：历史键指纹种子改用**注入前的稳定 SQL**——`SqlPreviewService.kt` 在 :314 注入前 `SqlGenerator.generate(statement, compact=true)` 出 `historyKeySeedSql`，经 `PreviewResult` 新字段透传；`historyCacheKey()` 优先用它，缺席回落 `result.sql`（存量行为零变化）。

## 缺陷三：`deleteAllInBatch()` 声明行不出预览

**根因**——声明行光标落入两条识别通道的缝隙：
- `psi/jpa/DerivedMethodLocator.kt:113-124`：`deleteAllInBatch` 不含 `By`；`isNoBySubjectForm`（:133-138）只放行 `*All` 词干与裸 `count`，`InBatch` 结尾不匹配 → 派生路 false。对照 `deleteById` 含 `By` → 正常。同族 `deleteAllByIdInBatch` 含 `By` 反而能走。
- `converter/jpa/JpaCrudOperationConverter.kt:201-216,289`：CRUD 转换入口只收 **PsiMethodCallExpression**（调用处），接口声明行没有调用表达式永不认领；`SqlPreviewService.kt:366-369` 向上找调用点也只找 PsiMethodCallExpression。
- 兜底链全 false（HQL 需方法体 / 无 @Query / 无调用点 / body=null）。**排除**「确认弹窗/危险闸门」与「runCatching 吞异常」两假设：全链无 Messages 框，BLOCK_ATTACK 只是 warning 文案且该路径进不去。
- 「连通知都没见」的残余差异：静态链路预测**应弹**「未在光标处找到可预览的 SQL 源」（右下 balloon，录制易漏拍）；需真机复核但无论通知与否，「bulk DELETE 形态在声明行光标下零可达路径」确凿。

**判定**：缺陷（覆盖缺口）。**已修**（`0c7a5d6`）。转换层能力完整在（`JpaCrudOperationConverter.kt:389-402` bulk DELETE 模板），只服务调用处光标。

**最小修复面**：`ConvertToSqlAction.tryJpaFallback` 加声明级分支——containingClass 是 Repository 接口且方法名在 CRUD 锚点名单时派发；receiver 实体用 `DerivedMethodLocator.resolveEntityClass(repositoryInterface)`（:169-176 现成）解析，复用 convertRepositoryCall 模板。配套 `DerivedMethodLocatorTest` 补 `deleteAllInBatch` 负例断言固化边界。

**既有测试互证**：`JpaDemoEntityResolverAndCrudTest.kt:249-254` 已注释「DerivedMethodLocator 不识别；转换层仍产出全表 DELETE」——转换能力在、定位通道断；`SqlPreviewServiceJpaCrudTest.kt:368-429` 只覆盖调用处形态。
