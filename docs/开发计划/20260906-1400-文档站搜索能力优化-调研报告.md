# 文档站搜索能力优化 — 调研报告

> 调研：2026-09-06（子智能体实测 + 主会话独立复核）
> 对象：本仓库 VitePress 文档站（实际安装 vitepress 1.6.4，minisearch 7.2.0）
> 结论先行：**站点搜索从未生效**——search 配置写在 `locales.*.themeConfig`，而 VitePress 编译期只认顶层 `themeConfig`，生产与本地均无搜索按钮、无索引、无快捷键。其次为中文分词漏召回与 docs/ 内部页污染。推荐两步走：P0 修复配置 + CJK bigram 分词（当天可上线）；P1 引入 Pagefind 替换（体验升级）。

---

## 一、现状盘点

### 1.1 当前 search 配置全貌

`.vitepress/config.mts` 中 search 配置出现在两处 locale 内：root（182-194 行）与 en（262-274 行），内容均为 `provider: 'local'` + 仅 `translations` 文案，没有 `miniSearch`、`detailedView` 等任何功能性配置。而全局共享的 `themeConfig`（280-287 行）只有 `logo / socialLinks / externalLinkIcon`，**没有 search 键**。这个细节是本次调研最重要发现的根源（见 1.4）。

### 1.2 local search 的实现机制（源码级）

索引生成（构建期，`node_modules/vitepress/dist/node/chunk-D3CUZ4fa.js`）：

- 40426-40428 行：`localSearchPlugin` 只有当 `site.themeConfig?.search?.provider === 'local'` 时才真正工作，否则返回空壳插件（不产索引）。
- 40462-40470 行：**按 locale 分索引**，`indexByLocales` Map，每个 locale 一个 MiniSearch 实例；字段 `fields: ['title','titles','text']`、`storeFields: ['title','titles']`，可与用户 `options.miniSearch?.options` 合并（40469 行）。
- 40508-40525 行：每个页面先经 markdown 渲染，再按标题切成节；每节 `id = 页面路径#锚点`、`title = titles.at(-1)`（该节最深层标题）、`titles = 上层标题路径`、`text = 该节纯文本`。索引是"节"粒度，标题和标题层级都进索引且运行时有权重。
- 40588-40618 行：默认切分器 `splitPageIntoSections` 用正则 `<h(\d*)...>` 按 h1-h6 切 HTML。
- 40447-40449 行：页面 frontmatter 写 `search: false` 可让该页整页不进索引。
- 40585-40599 行：产物形态是每个 locale 一个独立懒加载 chunk（`import('@localSearchIndex' + locale)`），zh/en 索引物理分开。

运行时查询（`node_modules/vitepress/dist/client/theme-default/components/VPLocalSearchBox.vue`）：

- 70-88 行：按当前 `localeIndex` 懒加载对应 locale 的索引（73 行），`MiniSearch.loadJSON` 时附加搜索参数 `fuzzy: 0.2, prefix: true, boost: { title: 4, text: 2, titles: 1 }`（77-81 行），用户 `miniSearch.searchOptions` 可覆盖。
- 163-165 行：查询结果最多取 16 条。默认视图只有标题+路径，无正文摘要；`detailedView` 开启时才加载页面模块提取原文并用 mark.js 高亮（169-176 行）。
- 用户配置 `miniSearch.options`（含 tokenize）同时作用于构建期（40469 行）与运行时（84-85 行）；VitePress 会把 themeConfig 里的函数序列化进客户端（chunk-D3CUZ4fa.js:36821 `serializeFunctions`、44986-44987 行），所以**在 config.mts 里定义自定义 tokenize 函数对两侧同时生效，官方类型明确支持**（`types/default-theme.d.ts:416-427`）。

MiniSearch 分词行为（`node_modules/minisearch/dist/es/index.js`）：

- 1940 行：默认 `tokenize: (text) => text.split(SPACE_OR_PUNCTUATION)`；2002 行：`SPACE_OR_PUNCTUATION = /[\n\r\p{Z}\p{P}]+/u`。即**只按空白和标点切**。
- 中文汉字既不是 `\p{Z}` 也不是 `\p{P}`，所以两个标点之间的整段中文会成为一个长 token。VitePress 层没有任何 CJK 特殊处理。
- 查询侧 `prefix: true` 是**左锚定前缀匹配**（radix tree，index.js 291-293 行；77-83 行为 Levenshtein 模糊实现），"逻辑删除"能命中以"逻辑删除"开头的 token，但"删除"命中不了"逻辑删除"——词中间的子串完全漏召回。

### 1.3 构建产物中的索引形态

`npm run build` 成功（7.87s，约 40 个 HTML 页面）。在 `.vitepress/dist/assets` 全量 grep `MiniSearch`、`localSearchIndex`、`documentCount` 等特征串：**零命中**。dist 里不存在任何搜索索引 chunk，也没有搜索框组件代码。

### 1.4 决定性发现：搜索当前在本地构建和生产环境都没有启用

编译期标志取自**顶层** themeConfig（chunk-D3CUZ4fa.js:44943）：

```js
__VP_LOCAL_SEARCH__: site.themeConfig?.search?.provider === "local"
```

而本站 search 只配置在 `locales.root.themeConfig` 和 `locales.en.themeConfig` 里，顶层没有。由此产生三个可复验事实：

1. `__VP_LOCAL_SEARCH__` 为 false，`localSearchPlugin` 走空壳分支，不生成任何索引 chunk（1.3 节实测零命中）。
2. `VPNavBarSearch.vue:129` 计算出 `provider = ''`，模板两个分支（134-155 行）都不渲染。puppeteer 实测：en 首页 `.VPNavBarSearch` 的 innerHTML 是空注释 `<!---->`，`#local-search` 按钮不存在；中文首页同样没有该按钮。**搜索框在整个站点上不出现，Ctrl/Cmd+K 与 '/' 快捷键（VPNavBarSearch.vue:113-125）也不会生效。**
3. 产物内联 `window.__VP_SITE_DATA__` 里顶层 `themeConfig` 为 `{"logo":"/logo.svg","socialLinks":[],"externalLinkIcon":true}`（dist/index.html 实测）；locale 层的 `search.provider:"local"` 虽在数据中，但只在运行时合并、不影响编译期判定。

用 curl 拉取线上 `https://sql-visualizer.jvtools.cn/`（HTTP 200，52061 字节），与本地 `dist/index.html` 逐字节 diff **完全一致**——生产环境同样处于"无搜索"状态。

> 主会话独立复核（2026-09-06）：`grep -rl localSearchIndex .vitepress/dist/assets/` = 0 个文件；线上首页 HTML `local-search` 出现 0 次。结论成立。

## 二、真实体验实测

### 2.1 测试环境

- `npm run build` 重新构建；`npx vitepress preview --port 4601` 起服务（curl 返回 200）。
- puppeteer-core 24.43.1 + 系统 Chrome headless 实测浏览器行为。
- 由于搜索框未渲染无法直接键入，另做离线仿真：用 VitePress 自己的 `createMarkdownRenderer` 渲染全部 40 个 md、复刻同款 `splitPageIntoSections` 正则、用仓库内 minisearch 7.2.0 以 VitePress 同款参数建索引并查询——即"如果配置位置修对，local search 会返回什么"的精确复现。

### 2.2 查询实测结果（zh 索引，默认 tokenizer = 修复配置后将得到的行为）

token 形态证据：zh 索引去重 8387 个 token，其中含中文的 5917 个；最长的中文 token 是整句，例如"插件从本次会话捕获的日志条目里反查这个位置附近的执行记录"（25 字）。**中文整句成为单 token 的假设被实测证实。**

| 查询 | 命中数 | 结果质量 |
|---|---|---|
| 逻辑删除 | 4 | 尚可。top2 为 configuration「SQL 预览」、wrapper-preview「逻辑删除注入」。能命中是因为"逻辑删除"恰是若干 token 的前缀 |
| 删除 | 6 | **严重漏召回**。命中全部来自 docs/ 内部开发计划页，用户页面 wrapper-preview「逻辑删除注入」、configuration、compatibility 全部落空——它们里的"删除"都在 token 中间 |
| EXPLAIN | 6 | 好。top2 为 wrapper-preview「EXPLAIN 真实执行计划」(score 52.4)、faq「EXPLAIN 点击失败」(46.7)，但 3-6 名被 docs/ 内部页占据 |
| 金仓 | 6 | 可命中（faq 方言分页、wrapper-preview 9 种方言），因"金仓"在文中恰处标点边界。后 4 名仍是 docs/ 内部页 |
| 补全 | 3 | 尚可，code-completion 两节居前，roadmap 第三 |
| 需求池 | 6 | **体验最差**。前 6 名全部是 docs/ 内部开发计划页；真正用户页面 about/feedback（需求反馈池）未进前 6——页面用语"需求反馈池"不匹配前缀"需求池" |
| 执行计划 | 6 | **严重漏召回+排序错乱**。top1 竟是 docs/ 内部页(14.4)，最该命中的 wrapper-preview「EXPLAIN 真实执行计划」不在前 6 |

| Pageable | 4 | 好。jpa-preview「分页与排序参数」居首。英文查询因按空白切分基本正常 |

en 索引验证：`Pageable`、`EXPLAIN`、`logical delete` 均命中且排序合理。zh/en 互扰问题：**不存在跨语言混入**——每 locale 独立索引、按 localeIndex 懒加载（VPLocalSearchBox.vue:73）；但 zh 索引把 docs/ 内部中文页和 README 页全部收录，形成实际污染。

### 2.3 对照组：自定义 CJK bigram tokenize 仿真

同一份内容、同款搜索参数，仅把 tokenize 换成"中文按双字切分（bigram）、英文按词切"：

| 查询 | 默认 tokenizer | bigram tokenize |
|---|---|---|
| 删除 | top6 全是 docs/ 内部页，核心页漏召回 | top1 变为 wrapper-preview「逻辑删除注入」(37.8) |
| 执行计划 | top1 是 docs/ 内部页，EXPLAIN 节不在前 6 | top1 为「EXPLAIN 真实执行计划」(336.2)，断层级领先 |
| 批量 | 前 2 名正确 | 前 4 名全部来自 batch-operation 正确章节，召回更全 |

bigram 方案在召回和排序上均有数量级改善，对 30 页的小站索引体积增长无感。

## 三、痛点清单（按影响排序）

1. **搜索整体未生效（最高优先级，阻断性）**。search 配置位置不符合 VitePress 编译期判定要求（只认顶层 themeConfig），生产站点没有搜索按钮、没有索引、没有快捷键。
2. **中文分词导致漏召回**。默认 tokenizer 按空白/标点切，中文整句成单 token；"删除"查不到"逻辑删除"、"执行计划"查不到"真实执行计划"。`prefix: true` 只救左前缀，`fuzzy: 0.2` 救不了词中子串。
3. **docs/ 内部页面污染结果**。开发计划/发行说明/开发笔记约 20 个内部页被编入 zh 索引且常以标题关键词碾压用户页面（"需求池"前 6 全为内部页）。
4. **权重与排序不稳**。boost 固定 title 4 / text 2 / titles 1，docs 页标题带编号关键词时容易压过真正的功能页；local search 不提供自定义静态权重手段。
5. **摘要与高亮弱**。默认结果列表只有标题+面包屑，无正文摘要；`detailedView` 才有 mark.js 高亮，且高亮依赖分词正确。
6. **搜索 UI 能力有限**。local search 是 modal 弹窗形态，无独立搜索页、无结果数展示、移动端触控体验一般。内置组件的固定形态，只能整体替换。
7. **zh/en 边界**。互扰本身不存在（分索引），但 root 索引混入 docs/、README 等非用户页面；en 站搜中文词必然空结果且无引导（推断，未实测空态文案）。

## 四、候选方案对比

| 维度 | A. local search 调优 | B. Pagefind | C. Algolia DocSearch | D. fuse.js / lunr / MeiliSearch |
|---|---|---|---|---|
| 中文召回质量 | bigram 调优后良好（2.3 实测） | 官方内置中日文分词策略，成熟 | 好，依赖其后台配置 | fuse 不适合全文检索；lunr 无中文分词；Meili 最好但需服务 |
| 双语支持 | zh/en 分索引天然支持 | 按 html lang 自动分语言索引 | Crawler 按页爬，需 dashboard 配置 | 需自处理双语 |
| 构建集成工作量 | 最低：仅改 config + frontmatter | 低：build 后追加 pagefind 命令 + 自定义主题插槽挂 UI | 低：审批通过后加三行配置 | 高：索引脚本 + 整套 UI 自研 |
| 运行时依赖 | 无 | 无（静态索引） | 外部 Algolia CDN（数据出境，国内延迟存疑） | fuse/lunr 无；Meili 需常驻服务 |
| Cloudflare Pages 兼容 | 完全兼容 | 完全兼容 | 兼容 | 静态方案兼容；Meili 需另找托管 |
| 长期维护成本 | 低（单文件改动） | 低-中（锁版本，升级验证插槽） | 中（审批、政策、合规自查） | 高 |
| 体验上限 | 中（弹窗 UI 固定、无摘要预览） | 较高（摘要高亮、分语言索引） | 高（打分/拼写容错/同义词成熟） | 理论最高，投入产出比最低 |

补充：Algolia DocSearch 对合格技术文档站免费，但属外部审批与外部服务，与零外部依赖偏好冲突；MeiliSearch 对 30 页站点与单人维护明显过重。pagefind 与 Algolia 的部分信息为公开资料推断，未逐一实测。

## 五、推荐与实施

### 推荐：两步走

**P0（已实施，见下）**：修复配置让 local search 真正启用 + CJK bigram tokenize + docs/ 内部页排除索引。
**P1（待决策）**：引入 Pagefind 替换 local search——纯静态、零运行成本、摘要高亮开箱即得，是"纯静态、双语、单人维护、零成本"约束下体验上限与维护成本的最优交点。P0 资产在 P1 后可整体移除，两者不冲突。

### P0 实施（2026-09-06 当天完成）

1. `.vitepress/config.mts`：`search: { provider: 'local' }` 提升到顶层 `themeConfig`；新增 `options.miniSearch.options.tokenize`（连续中文按双字滑动窗口切分、单字收尾、非中文段按原空白/标点切）；两个 locale 内保留 `translations`。
2. `docs/` 全部内部 md 与 `README.md` 批量加 frontmatter `search: false`，消除结果污染（27 个文件）。
3. `.vitepress/theme/index.ts`：客户端包装 `MiniSearch.loadJSON` 补查询分词（见下）。

#### 实施记录与对前文结论的一处重要修正

实施中发现 1.2 节结论需修正：**build 模式下 `serializeFunctions` 通道不生效**——客户端 `@siteData` 被直接替换为 `window.__VP_SITE_DATA__`（纯 JSON 内联，chunk-D3CUZ4fa.js 的 load 钩子在 build 非 ssr 分支 `return "export default window.__VP_SITE_DATA__"`，绕过 deserializeFunctions）。因此 config 里的 tokenize 函数只对**构建期索引**生效，**运行时查询分词拿不到函数**，退回默认整句切分——表现为 2 字查询（"删除"，恰为合法 bigram 词）可命中，4 字查询（"执行计划"、"逻辑删除"）空结果。

修复：主题入口顶层包装 `MiniSearch.loadJSON`，为每次索引加载补上同一份 bigram 分词函数（与 config.mts 的 `cjkTokenize` 逻辑一致，两处需同步维护）。已核实 dist 中主题 chunk 与 VPLocalSearchBox chunk 共享同一 minisearch 模块实例，patch 生效。

**验收实测（puppeteer，本地 preview）**：

| 查询 | 修复前 | 修复后 |
|------|--------|--------|
| 执行计划 | 默认分词下空结果 | top1 =「EXPLAIN 真实执行计划」，四字全高亮 |
| 逻辑删除 | 空结果 | top1 =「逻辑删除注入」 |
| 删除 | 全为 docs/ 内部页 | top1 =「逻辑删除注入」，内部页消失 |
| 批量 | 前 2 名正确 | 前几名全为 batch-operation 正确章节 |
| EXPLAIN | 正确但 3-6 名为内部页 | top2 精准，内部页消失 |
| 需求池 | 前 6 全为内部页 | fuzzy 兜底有结果但不精准——页面用语为"需求反馈池"，属内容用词差异，可在反馈页文案中自然带出"需求池"一词改善 |

搜索按钮、zh/en 双索引 chunk、Esc 关闭均正常。中英文首页为 `layout: false` 自绘顶栏，无 VPNavBar 搜索按钮（全部文档内页可用搜索）；首页入口随 P1 自研搜索 UI 一并解决。

### P1 实施要点（待立项）

1. devDependencies 加 `pagefind`（锁版本），build/deploy 脚本追加 `pagefind --site .vitepress/dist`。
2. 自定义主题入口利用 Layout 插槽（nav-bar-content-after / nav-screen-content-after）挂搜索按钮与 Pagefind 默认 UI，中文文案对齐现有 translations。
3. docs/ 内部页 `data-pagefind-ignore` 排除；zh/en 依 `<html lang>` 自动分索引。
4. 风险：自定义 UI 与默认主题样式适配约 0.5-1 天；升级 VitePress 时回归插槽名。

### P1 实施记录（20260906，已上线）

按上文要点实施，搜索整体从 VitePress local search 切换为 Pagefind 1.5.2：

1. **构建链**：devDependencies 加 `pagefind@1.5.2`；build/deploy 脚本在 `vitepress build` 后追加 `node scripts/prepare-pagefind.mjs && pagefind --site .vitepress/dist --exclude-selectors "..."`。
2. **UI**：`PagefindSearch.vue` 自研弹窗壳（胶囊按钮外观对齐 VPNavBarSearch），懒加载 CLI 产物自带的 `/pagefind/pagefind-ui.js|css`（官方 UI 随 CLI 输出，npm 上不存在独立的 pagefind-ui 包），`new PagefindUI({ bundlePath: '/pagefind/', showImages:false, showSubResults:true, excerptLength:40, processResult 去掉 .html 后缀, translations 中文文案 })`；Ctrl/Cmd+K、`/` 打开，Esc 关闭，路由跳转自动关。
3. **挂载三处**：默认主题 `nav-bar-content-after`、移动端 `nav-screen-content-after`（compact 圆形图标）、zh 首页自绘顶栏 `NavHeader.vue`（layout:false 无 VPNavBar，en 首页同样覆盖）。config.mts 的 `themeConfig.search` 与 cjkTokenize、主题里的 MiniSearch 补丁全部移除。
4. **内部页排除**：`scripts/prepare-pagefind.mjs` 遍历 dist 的 docs/** 与 README.html，给 `<body>` 加 `data-pagefind-ignore`（官方支持），41→40 页。

#### 踩坑记录（都实测复现过）

- **`.pagefindignore` 文件在 1.5.2 上不生效**：站根与 CWD 两种放法均零效果；改用 `data-pagefind-ignore` body 属性（最小实验：2 个 HTML 标 1 个 → "Indexed 1 page"）验证有效。
- **prepare 脚本跳过判断被正文反杀**：最初用 `html.includes('data-pagefind-ignore')` 判重，调研报告显示正文含该字符串本身，导致报告被跳过、body 永远没标上、内部页继续泄进结果；改为只匹配 body 标签的正则。
- **`bundlePath` 必须尾斜杠**：PagefindUI 内部拼 `` `${bundlePath}pagefind.js` ``，写 `/pagefind` 会 import `/pagefindpagefind.js` 404，报 "Cannot read properties of undefined (reading 'bundlePath')"。
- **llms 插件的隐藏 LLM 提示块泄进摘要**（"Are you an LLM? … Markdown format"）：该块 `display:none` 但 pagefind 不理会 hidden，须 `--exclude-selectors "[data-nosnippet]"` 显式排除。
- **顶栏/侧栏/页脚文本泄进摘要**（"English. Appearance. 搜索文档^K. Return to top."等）：SSR 把这些渲染进静态 HTML，pagefind 索引整个 body。追加排除 `.VPNav, .VPSidebar, .VPFooter, .VPBackToTop, .pf-trigger, .VPLocalNav, .VPSkipLink` 后摘要只含正文。
- **预览服务缓存文件清单**：sirv 启动时快照文件列表，手动重跑 pagefind 后必须杀掉 :4987 进程重启 preview，否则报 "invalid gzip data"/"WASM Error (No pointer)"。

#### 补丁（20260906 当日）：结果点击不跳转修复

上线后反馈"点击结果没有跳转到目标位置"。puppeteer 实测定位到三个叠加问题：

1. **官方 UI 只有标题行可点**：`<a class="pagefind-ui__result-link">` 只包标题 `<p>`，高亮摘要 `<p class="pagefind-ui__result-excerpt">` 在链接外——用户点最大的、最自然的摘要区域无任何反应。修复：组件对弹窗容器做点击委托，落点不在 `<a>` 内时找最近的 `.pagefind-ui__result-nested`（子结果优先）或 `.pagefind-ui__result-inner`，触发其标题链接，并给整卡加 `cursor: pointer`。
2. **SPA 导航后弹窗不关**：VitePress 链接拦截走 pushState（无 popstate），而 `<script setup>` 里 watch `route.data` 实测不回调。修复：点击命中即在下一个宏任务 `setTimeout(closeModal, 0)` 关窗（同步移除 `<a>` 会取消默认导航，不可行），popstate 仅作前进/后退兜底。
3. **守卫误杀键盘 Enter 导航**：Enter 在焦点链接上触发的合成 click 在**捕获阶段即 defaultPrevented=true**（导航照样发生），`if (e.defaultPrevented) return` 导致漏关。修复：守卫改为仅排除中键与修饰键（中键/Ctrl+点击是新标签页语义，不关窗）。

另外发现 **pagefind-ui 1.5.2 没有任何方向键导航**（源码无 ArrowDown/focus 管理），弹窗提示"↑↓ 选择"名不副实。组件自实现：↑↓ 在 `.pagefind-ui__result-link` 间循环移焦（↑ 首条回输入框），`scrollIntoView({block:'nearest'})`，Enter 走浏览器原生激活；配 `:focus-visible` 焦点环。closeModal 的 `ui.destroy()` 包 try/catch 抑制搜索在途竞态的 "worker terminated" 控制台噪音。

复测 6/6 PASS（真实鼠标坐标点击）：摘要区跨页+锚点（top=134）、主结果卡片区、同页锚点、ArrowDown×3→Enter 跨页导航+关窗+锚点、Esc/Ctrl+K、zh 首页 compact 入口。Ctrl+点击场景因 headless CDP 不透传 ctrlKey 无法断言，守卫代码静态核对无误。
