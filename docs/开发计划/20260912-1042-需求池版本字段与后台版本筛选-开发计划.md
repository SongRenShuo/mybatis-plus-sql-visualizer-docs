# 开发计划：需求池提交增加「IDE 版本 / 插件版本」与后台版本筛选

> 日期：2026-09-12 10:42
> 仓库：mybatis-plus-sql-visualizer-docs（提交表单 + i18n）、sql-visualizer-admin（选项接口 + 管理后台筛选）
> 性质：新功能 + 实施

## 一、需求

需求池提交反馈时，希望用户能顺带说明自己使用的环境，便于定位问题与统计版本分布：

1. 表单新增两个字段：**IDE 版本**（idea 版本）、**插件版本**；
2. 默认以**下拉框**形式呈现，用户可直接选择；
3. 选项**动态获取**，不允许前端硬编码；
4. 允许**用户自定义内容**：下拉框内可输入搜索，搜不到时就用用户自己输入的值（可创建选项）；
5. 两者**默认空**（不预选任何值）、**均非必填**；
6. **管理后台支持版本筛选**（按 IDE 版本 / 插件版本过滤反馈列表）。

## 二、现状与差距

| 项 | 现状 | 差距 |
| --- | --- | --- |
| 数据表 | `fb_posts` **已有** `ide_version`、`plugin_version` 两列（`0001_init.sql`） | 无表结构改动 |
| 写入链路 | `POST /api/v1/feedback/posts` 已接收并落库 `source / ideVersion / pluginVersion` | 仅 IDE 深链（`?source=ide&ideVersion=…&pluginVersion=…`）会带值，Web 端用户无法填写 |
| 表单 | `FeedbackForm.vue` 只把 IDE 上下文当**只读徽标**展示（`ide-badge`），没有可编辑控件 | 需新增两个可搜索、可自定义、可清空的下拉 |
| 选项来源 | 无任何版本选项接口 | 需新增动态选项接口 |
| 下拉组件 | `FilterSelect.vue` 无空态、无清空、无搜索，`currentLabel` 会回落 `options[0].label` | **不能直接复用**：非必填字段会误显示第一个选项为已选 |
| 后台列表 | `GET /api/v1/admin/posts` 只按 昵称/邮箱/状态/类型/关键词 过滤，`SELECT` 未返回版本列 | 需加筛选参数 + 返回字段 |
| 后台展示 | `admin/src/views/Posts.vue` **完全没有**渲染 `ideVersion / pluginVersion`（详情接口虽已返回，前端未用） | 需补列表列 + 详情行 |
| 存量统计 | `GET /api/v1/feedback/analytics`、`/admin/user-activity` 已有版本分布统计 | 可复用其聚合思路 |

结论：**零迁移**（列已存在），工作量集中在「动态选项接口 + 前端可创建下拉组件 + 后台筛选与展示」。

## 三、方案设计

### 3.1 交互设计

表单中「功能分类」下方新增一行两列（窄屏折行），均为**非必填**：

| 字段 | 控件 | 默认值 | 占位文案 |
| --- | --- | --- | --- |
| IDE 版本 | 可搜索 + 可自定义下拉 | 空 | `选择或输入 IDE 版本（选填）` |
| 插件版本 | 可搜索 + 可自定义下拉 | 空 | `选择或输入插件版本（选填）` |

行为细则：

- 点开下拉 → 面板顶部为搜索输入框，下方为过滤后的选项列表（选项已按新→旧排序）；
- 输入关键词 → 实时过滤（大小写不敏感、支持子串匹配）；
- 输入内容与任何选项都不完全相等 → 面板首行出现 `使用「<用户输入>」` 的创建项，点击即采用自定义值；
- 输入内容与某选项完全相等 → 直接选中该选项，不出现创建项；
- 已选值右侧提供清除按钮（`×`），清空后回到未选状态（提交时按空处理）；
- 支持键盘：`↑/↓` 移动、`Enter` 选中、`Esc` 关闭；
- **IDE 深链兼容**：URL 带 `?source=ide&ideVersion=…&pluginVersion=…` 时，把值**预填进两个下拉**（用户仍可改），同时保留现有 `ide-badge` 徽标提示。

### 3.2 选项动态来源（关键点）

新增公开接口 `GET /api/v1/feedback/version-options`，由**三段合并**得出，全部服务端计算、前端不硬编码：

| 来源 | 取法 | 作用 |
| --- | --- | --- |
| ① 库内沉淀 | `SELECT DISTINCT ide_version / plugin_version FROM fb_posts WHERE is_deleted = 0 AND 值非空` ∪ `sys_user_activity` | 社区真实使用过的值（**含用户自定义输入，形成「越用越准」的闭环**） |
| ② 插件版本基线 | Worker 端直连 `https://plugins.jetbrains.com/api/plugins/33633/updates`，取 `version` 列表（新→旧） | 保证首次提交前就有完整可选版本 |
| ③ IDE 版本基线 | 由 ② 的 `since` / `until` 构建号推导 IDE 大版本（`241`→`2024.1`、`233`→`2023.3`、`251`→`2025.1`…） | 同上，覆盖插件声明支持的 IDE 范围 |

补充与兜底：

- `sys_settings` 增加可选的 `feedback.version_options`（JSON：`{ ideVersions: [], pluginVersions: [] }`），作为**管理员可维护的追加/覆盖项**（补齐历史版本、屏蔽脏值）；
- 合并后**去重**（大小写不敏感，保留首次出现的原样大小写）→ **排序**（插件版本按语义化版本降序，IDE 版本按年份+序号降序）→ **截断**（各取前 50）；
- **脏值过滤**：入库聚合值需过白名单正则（`^v?\d{4}(\.\d+){0,2}([.-]\w+)?$` 之类的宽松版本格式 + 长度 ≤ 32），把误填的「不知道」「1」等噪声挡在选项池外；
- **缓存**：JetBrains 远端结果用 KV / `caches.default` 缓存 10 分钟（避免每次打开表单都打外部 API），库内聚合每次现查（D1 内网、量小）；
- **失败降级**：任何一段失败只跳过该段，接口仍返回 200 与已拿到的部分；全空时返回空数组，前端下拉为空但**不阻塞提交**（非必填）。

### 3.3 接口设计

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/feedback/version-options` | 公开。返回 `{ ideVersions: string[], pluginVersions: string[] }`，供提交表单下拉使用 |
| GET | `/api/v1/admin/version-options` | 管理端。返回带计数的 `{ ideVersions: [{ value, count }], pluginVersions: [{ value, count }] }`，供筛选下拉显示 `2026.1 (12)`，计数来自 `fb_posts GROUP BY` |
| GET | `/api/v1/admin/posts` | **改造**：新增 `ideVersion` / `pluginVersion` 查询参数 |

`/admin/posts` 筛选语义（与现有 `status` 多值风格保持一致）：

- 单值 → 精确匹配 `ide_version = ?`；
- 逗号多值 → `ide_version IN (?, ?)`；
- 特殊值 `__empty__` → `(ide_version IS NULL OR ide_version = '')`，用于筛「未填写」；
- 两个参数可同时生效（AND），并与既有 昵称/邮箱/状态/类型/关键词 条件叠加。

`POST /api/v1/feedback/posts`（**仅补校验，不改结构**）：

- `ideVersion` / `pluginVersion` 均 trim；空字符串 → 落 `NULL`；
- 长度上限 32（超长截断或 400，建议 400 并给出中文提示，与现有校验风格一致）；
- 拒绝控制字符 / `\uFFFD`；
- 保持「非必填、互不影响」；`source` 仍由链路决定（Web 提交仍为 `web`，仅当 `source=ide` 才记 `ide`），**版本字段不改变来源语义**。

### 3.4 数据模型

**无需迁移**：`fb_posts.ide_version` / `plugin_version` 已存在，`sys_settings` 为键值表，新增配置项不需 DDL。

可选（数据量上来后再加，非本需求阻塞项）：`migrations/0014_post_version_index.sql`

```sql
CREATE INDEX IF NOT EXISTS idx_fb_posts_ide_version ON fb_posts(ide_version);
CREATE INDEX IF NOT EXISTS idx_fb_posts_plugin_version ON fb_posts(plugin_version);
```

### 3.5 前端组件

`FilterSelect.vue` **不改造**（它的空值回落行为是既有分类筛选所依赖的），新增独立组件：

**`.vitepress/theme/components/feedback/VersionSelect.vue`**

```
props:  { modelValue: string; options: string[]; placeholder?: string; disabled?: boolean }
emits:  { 'update:modelValue': string }
```

- 结构沿用 `FilterSelect` 的 Teleport + fixed 定位方案（避免被提交弹窗 `overflow` 裁剪，z-index 压过 modal 的 1090）；

- 创建项：`keyword.trim() && !options.some(o => o === keyword.trim())` 时在列表首位渲染「使用「xxx」」；
- 触发器：未选时显示 `placeholder`（灰色），已选显示值 + 清除按钮；
- 复用现有 CSS 变量（`--vp-c-bg` / `--vp-c-border` / `--vp-c-brand-1`），浅色深色自动跟随；
- 无障碍：`role="combobox"` / `aria-expanded` / `aria-activedescendant`，键盘交互与 `FilterSelect` 对齐。

`FeedbackForm.vue` 改动：

- 提交成功后重置为空。

`i18n.ts` 新增文案键（zh / en 各一份）：

## 六、风险与备选

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| JetBrains Marketplace 接口不稳定/限流 | 基线选项拿不到 | KV 缓存 10min + 失败降级为「仅库内聚合」，不阻塞提交 |
| 构建号 → IDE 版本映射可能失真 | 选项列表不准 | 映射表集中维护 + `sys_settings` 覆盖项兜底 |
| 用户自定义值污染选项池 | 下拉里出现「不知道」等噪声 | 白名单正则 + 长度上限过滤；必要时后台可删（`sys_settings` 覆盖） |
| 版本写法不统一（`v2026.9.4` / `2026.9.4`） | 同一版本被拆成两个选项 | 去重时大小写不敏感；展示保留原样，不强制改写用户输入 |
| 新增筛选使 `/admin/posts` SQL 变复杂 | 查询变慢 | 现有索引覆盖 `status/type/category`；版本列按需加索引（0014） |

**备选方案**：

- **方案 B（最小实现）**：不做远端拉取，选项只来自「库内聚合 + 静态基线」，`sys_settings` 维护。实现最快、依赖最少，缺点是首次使用前选项较少。若希望先快速上线，可按方案 B 落地，接口形状不变，后续把远端基线接进同一接口即可（**接口契约不破坏**）。
- **方案 C（前端直连）**：前端直接请求 JetBrains API —— 存在跨域，需依赖现有 `/api/changelog` 代理，且选项聚合逻辑散落前端，不推荐。

## 八、修订一：数据源换源（2026-09-12 13:10）

### 8.1 上线后发现的问题

首版按 3.2 节把 IDE 版本**由 Marketplace 的 `since`/`until` 构建号推导**，实测线上返回：

```json
{
  "ideVersions": ["2024.3"],
  "pluginVersions": ["2026.9.11-dev","v2026.9.11","v2026.9.10","v2026.9.8","v2026.9.4","2026.9.3","v2026.8.21","v2026.8.20","v2026.8.19"]
}
```

三处硬伤：

| 问题 | 根因 |
| --- | --- |
| IDE 版本只有孤零零一个 `2024.3` | Marketplace updates **只返回最近 7 条**，且 `since` 全为 `243.0`、`until` 全为空 → 构建号区间推导退化成单点 |
| 插件版本前缀不一致（`v2026.9.11` 与 `2026.9.3` 并存） | 归一化只做「大小写不敏感去重」，没统一 `v` 前缀；基线补 `v`、库内沉淀保留原样，同一版本被拆成两条 |
| 混入 `2026.9.11-dev` | 旧白名单允许 `[.-][A-Za-z0-9]{1,10}` 后缀，把非发行版构建放进了候选池 |

### 8.2 换源方案（本节覆盖 3.2 节）

| 字段 | 主来源 | 补充来源 |
| --- | --- | --- |
| IDE 版本 | **JetBrains 官网发布数据**：`data.services.jetbrains.com/products/releases?code=IIU&type=release&latest=false`，取 `version` 压成**大版本线**（`2024.3`） | `sys_settings` 覆盖项 + 库内沉淀 |
| 插件版本 | **Gitee 仓库发行版**：`gitee.com/api/v5/repos/songrenshuo/mybatis-plus-sql-visualizer/releases`，取 `tag_name`（跳过 prerelease） | JetBrains Marketplace updates（Gitee 发行版会滞后一两天，补最新版）+ `sys_settings` 覆盖项 + 库内沉淀 |

关键决策与依据：

1. **只取 IIU 单产品**。IIU+IIC 一起拉响应 2.16MB、`JSON.parse` 实测 11.4ms，顶穿 Worker 免费版 10ms CPU 预算；IIU 单产品 1.12MB / 4.2ms 安全，且大版本线反而更全（Ultimate 到 `2026.2`，Community 只到 `2025.3`）。
2. **IDE 粒度选大版本线**。用户报 bug 时说的就是「我在 2024.3」；patch 级精确值仍可通过表单自定义输入落到选项池（下一人即可选到），不必让下拉塞进 282 条。
3. **年份段限定四位数字**，顺带把 2016 年以前的 `15.0` / `14.1` 老编号挡掉。
4. **统一规范形**：插件版本一律 `v` 前缀（与文档站 `usePluginVersion` 展示口径一致），IDE 版本一律不带前缀。`2026.9.3` / `v2026.9.3` / `V2026.9.3` 全部收敛成一条。
5. **白名单收紧为 `^\d{4}\.\d{1,2}(\.\d{1,2})?$`**：不接受任何后缀，`-dev` / `-beta` / `-RC1` 这类构建不再进候选池（提交侧仍不拦，用户想填就填，只是不作为下拉候选）。
6. **缓存改两层**：进程内 Map（10min，同 isolate 削峰）→ **KV 持久缓存（12h）**。只在至少一个来源成功时写 KV——把失败结果缓存半天会把「暂时拉不到」变成「半天拉不到」。

## 九、修订二：去掉「越用越准」（库内沉淀不再回灌候选池）

### 9.1 为什么去掉

8.2 节的方案里，候选池有一路是**库内沉淀**（`fb_posts` ∪ `sys_user_activity` 里出现过的版本值），
初衷是「用户填过的值下次能选到，越用越准」。上线后实测发现这个机制是负收益：

- **口径不可控**：用户随手填的值会混入官方列表。形状白名单再严也挡不住
  `2026.9.3` 这类「看着像版本、但并非官方发布」的写法——线上确实多出了一条
  `v2026.9.3`，它只来自某个用户的自定义输入。
- **列表随提交历史波动**：同一个版本列表会因为有没有人提交过而变，不稳定、
  也不便向用户解释「这个版本为什么在/不在列表里」。
- **降级语义错位**：外部源全挂时用库内值兜底，等于把「拉不到官方数据」掩盖成
  「好像有数据」，反而削弱了故障的可观测性。

### 9.2 现在的构成（本节覆盖 3.2 与 8.2）

候选池**只由权威来源构成**：

| 字段 | 来源 |
| --- | --- |
| IDE 版本 | JetBrains 官网（大版本线）∪ `sys_settings` 覆盖项 |
| 插件版本 | Gitee 发行版 ∪ Marketplace 补充 ∪ `sys_settings` 覆盖项 |

- 显式**移除** `fb_posts` / `sys_user_activity` 两路查询。
- 管理员需要加历史版本，走 `sys_settings.feedback.version_options` 覆盖项——
  这是人工维护的、有审计痕迹的入口，比回灌用户输入可靠。
- 降级行为相应调整：外部源全挂且无覆盖项时，**返回空数组 + 200**。
  下拉为空，但表单仍支持自定义输入（allow-create），功能不中断。

### 9.3 不受影响的部分

- **管理端 `/admin/version-options` 不变**：它统计的是「库里实际出现过的值 + 计数」，
  用于筛选器——筛选项当然要看真实数据，这与候选池是两回事。
- 提交侧仍不做形状校验：用户想填什么就填什么，照单入库，只是不进下拉候选。

### 9.4 验证

单测调整：库内沉淀相关断言改为「**不**回灌」的反向断言（库里 `2024.1` / `v2026.9.3`
及埋点里的 `2019.9` 均不出现在候选池）；`-dev` 过滤改在 `sys_settings` 覆盖项上验证；
50 条截断改用 Gitee 打桩构造；新增「全源失败返回空数组」。全量用例通过。
