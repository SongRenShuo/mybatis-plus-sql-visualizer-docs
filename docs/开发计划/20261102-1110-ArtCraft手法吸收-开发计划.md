## 一、背景与结论

用户提出分析 <https://getartcraft.com/> 并提取可吸收到当前官网的做法。调研已完成（见关联报告），结论是：

**目标页有 6 项手法值得吸收，其中 3 项是低成本高收益的样式层改动，3 项需要先做验证或用户决策；另有 7 项明确排除。**

核心判断：目标页是面向大众创意用户的产品展示页，当前官网是面向开发者评估与安装的工具页。目标页首屏纯文字零媒体（实测 8413 字节、`<img>`/`<video>`/`<canvas>` 计数均为 0），靠文字层级撑起首屏；当前官网首屏是一个代码对照块（Java Wrapper 链 ↔ 生成的 SQL），直接回答「我的 Wrapper 能不能预览」。**当前官网的首屏策略比目标页更适合本产品，不改。**

真正值得吸收的是目标页在**排版细节**上的四个手法：标题内的强调词、HUD 标签样式、发丝网格分隔、标题字重字距。它们的共同点是成本极低（多数只改一处 CSS）且与产品形态无关。

## 二、取舍原则

沿用上一轮的三条约束，并新增两条：

1. **只改样式层，不改信息架构**。本轮不动区块顺序、不动文案语义、不动 `homeContent.js` 的键结构。
2. **中文侧与英文侧分别定案**。目标页的斜体强调手法依赖拉丁字形，中文无斜体（浏览器合成倾斜观感差），中文侧必须换等价手法。
3. **不做无谓装饰**。目标页的 24 个 `.tick` 准星标记、15 色应用矩阵、社区影片墙一律排除（与 `20261029-1129` 的去 AI 味取向冲突）。
4. **改一处 CSS 能解决的不改组件结构**。优先用 CSS 变量 + 类覆盖，避免动 15 个 Vue 组件的结构。
5. **暗色模式必须同批验**。当前官网有完整的 `.dark` 变量集，任何颜色改动都要在两套模式下各验一次。

## 三、任务清单

### T1 标题强调词样式（P0，必做）

**对应调研 5.1**

在区块标题中选一个关键词，用主强调色 + 字重强调。目标页用 `<span class="font-serif italic">`，中文侧改为颜色 + 字重。

**候选位置**（需用户定夺，见第六节）：

| 区块 | 现标题 | 建议强调词 |
|------|--------|-----------|
| 核心能力 | 大幅提升您的 SQL 调试效率 | `SQL` |
| 更多特性 | 我们为您考虑周全 | `周全` |
| 数据事实 | 不靠形容词，靠可核验的数字 | `可核验` |
| CTA | 准备好告别繁琐的SQL 调试方式了吗？ | `告别` |

**关键前提：现有代码已有 accent span 机制，不需要 `v-html`。**

实测发现三个组件已经在用这个手法，模式统一为「前缀纯文本 + `<span class="xxx-title-accent">` 强调词」：

| 组件 | 现有 accent 类 | 数据来源 |
|------|---------------|---------|
| `Testimonials.vue:14` | `.testimonials-title-accent` | `titlePrefix` + `titleAccent` |
| `WelfareCard.vue:58` | `.welfare-title-accent` | `titleLine1` + `titleLine2` |
| `CtaSection.vue:15` | `.cta-title-accent` | `titleLine1` + `titleLine2` |
| `HeroSection.vue:17` | `.hero-title-highlight` | `titleLine2` |

所以本任务不是「引入 `v-html`」，而是**沿用既有约定**，给剩下 4 个纯文本标题补 accent 字段与 span。这同时消除了 XSS 面（不引入 `v-html`）。

**改动落点**：

- `.vitepress/theme/data/homeContent.js` — 为 4 个标题新增 `titlePrefix` + `titleAccent` 字段，中英各 4 处（共 8 组）
- 对应组件模板 — 改成与 `Testimonials.vue:14` 一致的写法：`{{ c.xxx.titlePrefix }}<span class="xxx-title-accent">{{ c.xxx.titleAccent }}</span>`
- 各组件 `<style>` — 新增 `.xxx-title-accent { color: var(--primary-color); }`，与既有三个 accent 类同构

**注意 `WelfareCard` 的 accent 用的是渐变文字**（`background: linear-gradient(135deg, var(--primary-color), #22d3ee)` + `background-clip: text`），而 `Testimonials` / `CtaSection` 用的是纯色。**本轮统一为纯色**，理由是渐变已在上一轮的去 AI 味审查中被标记为候选（见 `20261029-1129`），且与另外两处不一致。

**英文侧**：可以用衬线斜体（`font-family: Georgia, serif; font-style: italic; font-weight: 400`），与目标页手法一致。系统 Georgia 即可，**无需自托管字体**（目标页自托管 Archivo 是因为它要控制字重轴 100~900 与字宽轴 62%~125%，Georgia 没这个需求）。

**验收**：

- 亮暗两模式下强调词与正文有明确视觉区分
- 强调词不换行断裂（中文长词需 `white-space: nowrap` 或按词切分）
- 移动端 390×844 下标题不溢出
- 全页 accent 样式一致（不再有渐变与纯色混用）

### T2 HUD 标签样式统一（P1，必做）

**对应调研 5.2**

**侦察修正：`.section-eyebrow` 已经是 HUD 标签，不能改。**

实测 `style.css:912`，现有定义是：

```css
.section-eyebrow {
  font-size: clamp(1.25rem, 2.6vw, 2rem);
  font-weight: 700;
  letter-spacing: 0.2em;
  text-transform: uppercase;
  color: var(--text-secondary);
}
```

它已经具备「全大写 + 宽字距 + 加粗 + 次级色」的 HUD 特征，且**字号是主标题的 2/3**（源码注释明确写了这是刻意的层级设计）。原计划要把它改成 `11px` 会直接破坏这个层级，**该改动取消**。

目标页的 HUD 标签是 `text-[11px]` 级别（比正文还小），适用于它那种「标签是次要信息」的排版；当前官网的眉题是「章节信号」，两者定位不同。**这是调研报告的判断偏差，以实测为准。**

**本轮实际要做的**：把散落在各组件里、样式**不一致**的 meta 行统一到同一套 HUD 参数。实测现有 `letter-spacing` 用法已经出现 7 个不同值（`0.2em` / `0.12em` / `0.08em` / `0.5px` / `0.01em` / `-0.02em` / `-0.03em`），其中正字距就有 4 种。

**统一目标**：新增一个 `.hud-label` 工具类，参数取现有最大值（与 `.section-eyebrow` 对齐，不引入新字号）：

```css
.hud-label {
  font-size: 0.75rem;
  font-weight: 700;
  letter-spacing: 0.12em;
  text-transform: uppercase;
  color: var(--text-secondary);
  font-family: var(--vp-font-family-mono), ui-monospace, monospace;
}
```

**落点**（实测存在 meta 行的位置）：

- `.steps-num`（步骤编号）
- `.feature-card-tags`（功能卡标签行）
- `.pricing-headline-item` / `.pricing-group-caption`
- `.testimonial-meta` 类
- `.recent-updates-version` / `.recent-updates-date`

**注意**：`.section-eyebrow` 本身**不动**。

**验收**：

- 各 meta 行在亮暗两模式下与正文拉开层级
- 中文 meta 在 `letter-spacing: 0.12em` 下不拥挤
- 移动端不换行（`white-space: nowrap` + `overflow: hidden`）
- `.section-eyebrow` 的 `clamp(1.25rem, 2.6vw, 2rem)` 未被改动（用 git diff 确认）

### T3 发丝网格分隔（P1，必做）

**对应调研 5.4**

**侦察修正：只改 `FeaturesGrid`，`FeatureAlternate` 不改。**

实测 `FeatureAlternate.vue` 的 8 个能力块是**左右交替的图文行**（`media` 数组含 `imageSrc` / `poster` / `reverse`，每行一张 GIF + 一段文字），不是等宽卡片网格。给它套 `gap-px` 网格会破坏交替布局。**该组件保持原样。**

**目标页做法**（实测 HTML）：

```html
<div class="grid gap-px border-t border-line bg-line md:grid-cols-2">
  <article class="bg-bg">…</article>
</div>
```

**改动落点**：仅 `.vitepress/theme/components/home/FeaturesGrid.vue`

现状（实测 `FeaturesGrid.vue:108`）：

```css
.features-grid {
  display: grid;
  gap: 2rem;
  max-width: 72rem;
  margin: 0 auto;
}
@media (min-width: 768px) {
  .features-grid { grid-template-columns: repeat(3, 1fr); }
}
.feature-card {
  background-color: var(--bg-primary);
  border-radius: 1rem;
  padding: 10px 29px;
  transition: all 0.4s;
}
```

改为发丝网格：`gap: 2rem` → `gap: 1px`，容器加 `background-color: var(--border-color)`，卡片背景保持 `--bg-primary`。卡片圆角在网格中要归零（相邻卡片圆角会露缝），悬停的 `box-shadow` + `translateY(-2px)` 保留。

**注意**：卡片悬停有 `transform: translateY(-2px)`，在 1px 网格里会压住相邻卡片的边线。需要给卡片加 `position: relative` + `z-index`，或在悬停时改用 `box-shadow` 单边。

**新增 CSS 变量**（`style.css`）：

```css
--line-color: #e5e7eb;              /* 亮色，与 --border-color 一致 */
.dark { --line-color: #374151; }
```

**验收**：

- 网格线在亮暗两模式下均可见但不抢眼
- 8 张卡在 `md`（768px）换列时线条自动重排
- 390×844 单列时网格线正确
- 卡片悬停上浮时不压住相邻卡片边线
- `FeatureAlternate.vue` 的 8 行图文布局未被改动（用 git diff 确认）

### T4 标题字重与字距（P2，先验证再实施）

**对应调研 5.5**

**目标样式**（取自目标页实测 class）：

```css
.section-title {
  font-weight: 500;
  line-height: 1.1;
  letter-spacing: -0.02em;
}
```

**为什么标 P2**：调研第八节把「中文黑体 500 与 400 差异是否明显」列为待验证前提。中文系统黑体（微软雅黑 / PingFang / 思源黑体）的 500 字重可能回落到 400，导致改动无视觉效果；而紧字距对中文的作用也未经实测。

**先做的事**：在浏览器里对同一个中文标题分别渲染 `font-weight: 400 / 500 / 600 / 700` 与 `letter-spacing: 0 / -0.02em / -0.035em`，截图对比。**若有明显差异则实施，若无则放弃此项**。

**实验结果（2026-11-02 11:58 实测，Chrome headless 1440×1800 截图，微软雅黑）**：

- `font-weight` 400 / 500 / 600 / 700 **四档全部可辨**，中文黑体没有回落到 400 的问题（雅黑本身有 400/700 两档实体，中间档由合成加粗补足，视觉上连续）
- `letter-spacing: -0.02em` 相比 `0` **明显更紧**，`-0.035em` 进一步收紧但开始有轻微粘连感
- 结论：**T4 有视觉效果，可以实施**。字重取 `600`（介于 500 与 700 之间，比现状 bold 略轻但仍清晰），字距取 `-0.02em`（不用 -0.035em，避免长标题粘连）

产物：`tmp/t4-weight-test.png`（artcraft 工作树内，不提交）。

**侦察修正：`.section-title` 不是共用类，是 3 个组件各自的局部 scoped 定义。**

实测四处独立定义，内容完全相同（`font-size: 2.25rem; font-weight: bold; margin-bottom: 1.5rem` + `@media (min-width: 768px) { font-size: 3rem }`）：

| 文件 | 行号 |
|------|------|
| `FeatureAlternate.vue` | 122 |
| `FeaturesGrid.vue` | 93 |
| `PricingSection.vue` | 73 |
| `HeroSection.vue`（`.hero-title`） | 180 |

另有三个标题用**独立的类名**，不走 `.section-title`：`.docs-showcase-title`（135）、`.testimonials-title`、`.cta-title`（75）、`.welfare-title`（238）。

所以本任务要么改 7 处（3 个 `.section-title` + 4 个独立标题类），要么在 `style.css` 里把 `.section-title` 提升为全局类。**建议后者**：把 `.section-title` 提到 `style.css` 全局，各组件删掉局部定义——但这是结构性改动，**本轮改为只改 `font-weight` / `line-height` / `letter-spacing` 三个属性，且先在 3 个 `.section-title` 上验证**，独立标题类（`docs-showcase-title` / `cta-title` 等）留到确认有效后再统一。

**验收**：仅在验证有视觉效果时执行；执行后需全区块回归（3 个 `.section-title` + 4 个独立标题类）。

### T5 产品决策项（P2，需用户定夺）

**对应调研 5.6**

首屏信息分层调整。当前首屏有三级信息（CTA 组 / 亮点标签 / 统计数据），目标页有五级（主 CTA / 次 CTA / 跨产品引导 / 平台清单 / 信任标签）。

**不直接推荐的原因**：目标页首屏零媒体，靠文字层级就能撑起；当前首屏右侧是代码对照块，已承担「证明这东西能用」的职责，再加层级会挤压它。

**用户定夺后可做的方向**（三选一或都不做）：

1. 给现有三级信息加视觉层级（CTA 组放大、亮点标签改 HUD 样式、统计数据加分隔线）
2. 增加第四级「平台 / 环境清单」（如 `macOS · Windows · Linux` 的等价物 `IntelliJ IDEA 2024.3+`）
3. 保持现状

## 四、不做清单

以下为目标页中存在但**明确排除**的形态，理由是它们与本产品形态或既有取向冲突。

| 排除项 | 理由 |
|--------|------|
| 纯文字巨型首屏 | 丢掉代码对照块＝丢掉最强证据，详见调研报告 6.1 |
| 双产品线对比区块 | 单一产品无对比对象 |
| 社区影片墙 | 「数据事实」三条数字对开发者更有说服力 |
| 15 色应用矩阵 | 单一产品无承载对象 |
| 装饰性准星标记（24 个 `.tick`） | 纯装饰，与去 AI 味取向冲突 |
| 吸顶眉题条替换 SectionNav | 目标页眉题条不可点击，弱于现有 9 锚点导航 |
| 全站换字体（Archivo / Instrument Serif / Inter） | 不含中文字形，收益仅限英文；新增 3~5 个 woff2 拖慢首屏 |
| 跨产品引导（`Looking for ArtCraft Studio?`） | 单一产品无第二产品线 |
| 巨型逐字母字标 | 与「代码对照块」首屏策略冲突，且中文无逐字母排版基础 |

## 五、验收与部署

### 5.1 验收档位

按既有三档分层：

- **定向**：每个任务实施后由实施者自查（亮暗两模式 + 1440×900 / 390×844 两档视口）
- **统一全量门禁**：全部任务完成后单派一个只读收口代理跑一次权威全量（`npm run build`），主控同时写文档收尾，**并行不空等**
- **构建校验**：本轮改动涉及 `.vitepress/theme/` 样式与组件，属「大改动」判据中的「引入新平台 API 面或反射入口」之外，但动了 15 个组件中的 2 个结构，**建议跑一次 `npm run build` 门禁**

### 5.2 部署

- 部署命令：`npm run deploy`（Cloudflare Pages，见 `deployment-target` 记忆）
- 提交策略：测试通过即 commit（只 add 本次文件，不 push），部署按任务流程
- **禁止**在未做真机截图验收前部署

### 5.3 回归重点

| 改动 | 回归点 |
|------|--------|
| T1 标题强调词 | 4 个标题 × 2 语言 × 2 模式 = 16 种组合 |
| T2 HUD 标签 | 9 个区块眉题 × 2 模式 |
| T3 发丝网格 | `FeaturesGrid` 8 卡 + `FeatureAlternate` 8 块 × 2 模式 × 2 视口 |
| T4 标题字重 | 11 个区块标题 × 2 模式 |

### 9.5 两项遗留的处理（2026-11-02 第二轮）

**遗留 1：英文衬线斜体** — 已完成（`749b7c6`）。

关键发现：**VitePress 已把 locale 写在 `<html lang>` 上**（`zh-CN` / `en-US`），不需要在 `CoolHome` 根节点挂 `.en` 类。原计划担心的「类级联泄漏给整页」风险因此不存在：

```css
html[lang^='en'] .capability-title-accent, ... { font-family: Georgia, ...; font-style: italic; font-weight: 400; }
```

原计划在 `CoolHome` 挂 `.en` 类的建议**已废弃**——那会让 `.cool-home.en { font-family }` 级联给所有后代（导航、按钮、卡片正文），而 `html[lang]` 是纯 CSS 属性选择器，零泄漏。

验证：Georgia 本机可用（与 Times/Arial/serif 字宽互不相同）；应用后各标题高度变化 ≤1px；暗色代码块仍等宽（其自身写了 `font-family`，实测 `codeMono: true`）。

**遗留 2：HeroSection meta 行** — 已完成（`749b7c6`）。

`.hero-stat-label` ×3 与 `.hero-code__label` ×2 补 `.hud-label`。实测对比度 7.49:1（代码标签对窗栏底），两模式均成立。
