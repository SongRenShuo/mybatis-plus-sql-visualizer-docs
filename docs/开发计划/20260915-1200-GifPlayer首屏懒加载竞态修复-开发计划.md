## 一、生产实证（2026-09-15，生产站 wrapper-preview 页）

无头浏览器全新加载、视口 1280×720、完全不滚动，时间轴采样：

| 时刻 | 播图区位置 | GIF img | 说明 |
| --- | --- | --- | --- |
| 0ms | top=152, bottom=566（视口 720 内） | 未挂载 | only poster，`filter: blur(8px)` |
| 800ms | 同上 | 未挂载 | |
| 2300ms | 同上 | 未挂载 | |
| 5300ms | 同上 | 未挂载 | **IntersectionObserver 从未回调** |

关键事实：播图区**完整在首屏视口内**，`isIntersecting` 从一开始就该为 true，但观察器回调始终不触发。用户滚动一次后 GIF 立即挂载并正常播放（此前一轮排查已实证），所以现象呈现为「不滚动=永久静态、滚动=变动图」。

对照旧验收〔20260907-1138 计划修订十一的实施状态〕：验收口径里「冷/热缓存 GIF 动画」等项的实测路径都含滚动动作，滚动把卡住的门撞开了，**掩盖了本缺陷**。本计划同时修正该验收口径（§五）。

## 二、根因分析

[GifPlayer.vue](../../.vitepress/theme/components/GifPlayer.vue) 的渲染门是三段串联：

```
IntersectionObserver(isIntersecting) → loaded=true → GIF <img> 挂载 → gifReady=true → 淡入覆盖 poster
```

卡点在第一环：`onMounted` 里创建观察器并 `observe(container)`，但 **SPA 路由切换 / hydration 时序下，对「注册观察时已处于视口内」的元素，IntersectionObserver 不产生回调**（它只在「相交状态发生变化」时派发，元素加载时就已经相交，没有「从不相交到相交」的变化）。VitePress/ClearTimeout 时序竞态导致的这个已知行为模式，与 2026-09-12 修过的首页两组件 hydration 竞态（efda401，GIF 缓存命中时 `@load` 监听器就位前已 complete）是**同一家族**的时序缺陷——那次修的是第三环（complete 补位），这次是第一环（loaded 门），且都只在「页面初次渲染即满足条件」时发作。

触发条件：GifPlayer 出现在页面首屏且用户不滚动。功能详解 9 页全部是「标题下第一行就是 GifPlayer」的构型，**全部中招**；getting-started 嵌的 wrapper-preview 图也在页面上部，同样中招。

## 三、修复方案（已按推荐落地）

**方案：挂载后同步兜底判定（保留懒加载语义）**。GifPlayer 是全站共用组件，不按位置猜「哪个在首屏」，由组件自己判定——挂载时元素已near视口就直接放行，不依赖观察器回调。

改动点（`GifPlayer.vue` script 部分）：

1. 新增 `isNearViewport(el)`：`rect.top < innerHeight + 200 && rect.bottom > -200`，与观察器 `rootMargin: '200px'` 的余量口径一致——这样即使观察器正常工作，同步判定也只是提前几毫秒打开同一扇门，行为不会分叉；
2. `onMounted`：先做同步判定，命中则直接 `loaded.value = true` 并 return（**不再注册观察器**，元素本来就在视口内，观察器无意义还有再踩一次时序的风险）；未命中才走原观察器路径（真正在页面下方的图，懒加载行为完全保留）；
3. `togglePlay` 恢复播放路径补 `nextTick(syncGifState)`：暂停→恢复会重挂 GIF img，此时若观察器已 disconnect（首屏直接放行的实例根本没有观察器），恢复动画只能靠 complete 补位，原先该方法只在 video 分支处理，GIF 分支的恢复路径同样需要兜底。

样式、模板、props 零改动；多实例、poster 兜底、GIF 失败摘除叠层等既有机制全部不动。

## 五、验收口径修正（写入后续 GIF 任务的通用纪律）

原「冷/热缓存 GIF 动画」验收必含滚动操作，无法暴露本缺陷。修正为：

> **零滚动验收**：页面加载后不做任何滚动输入，等待 ≤3s，首屏 GifPlayer 必须进入播放态（GIF img 挂载 + opacity 1）。滚动相关验收项仅针对首屏之外的图。
