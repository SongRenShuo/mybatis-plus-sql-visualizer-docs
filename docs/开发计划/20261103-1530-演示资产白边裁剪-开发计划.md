## 一、背景与结论

用户要求裁掉演示资产的白边。实测后结论分三层，**与「站内很多图带白边」的直觉不完全一致，先摆事实**：

1. **源文件确实有白边，但只占 40%**：90 个栅格资产里 36 个（29 GIF + 7 PNG）带浅灰窗框，54 个已经是紧裁的边到边画面。白边不是「全部素材都脏」，而是**两代录制产物混用**。
2. **站内当前只剩 2 张图的底边可见**：三处组件（文档页 `GifPlayer`、首页 `FeatureAlternate`、首页 `DocsShowcase`）早已用 `clip-path: inset(0.15% 0.6% 0.85% 0.6%)` 按百分比盖住了。实测无头 Chrome 暗色模式下：文档页 GIF 盒四边白像素 0、首页卡片四边白像素 0；唯独 `guide/configuration.md` 里**用 markdown `![]()` 直插** 的 `settings-orm-capture.png` 与 `xml-syntax-highlight.gif` 没有 `clip-path`（computed `clipPath: none`），渲染后仍有 4~5px 浅灰带。
3. **但 `clip-path` 只是遮住，源文件还是脏的**：插件仓 README、Marketplace 截图、第三方转载拿到的仍是带框文件；同时那 54 个本来就干净的资产被这条规则**白白多裁了约 7.7px 真实画面**（右缘最明显，正好啃在 IDE 右侧工具窗栏上）。

所以本轮不是「补一条 CSS」那么简单，而是两件事分开做：**短期止血（2 个漏网资产）+ 根治（36 个资产裁源、撤掉补偿规则）**。裁剪本身实测**零画质损失**（全帧 PSNR = inf、SSIM = 1.000000），体积还略降 2.5%，代价主要在当前这一次性工作量与复验。

## 三、白边成因

证据链如下：

1. **录制窗口比例**：素材规格是「窗口 1370×984 @ (277,25)、导出宽 1280」（见 `docs/开发计划/20261021-2043-...-开发计划.md:91`、`20261008-1106-...:504`）。录制工具抓的是一块**包含窗口圆角外页面背景**的矩形区域，圆角外那一条就是浅灰页面底色。
2. **导出时的等比缩放把 1~2px 的边放大成 7px**：1370 → 1280 是 0.934 倍，但左/右实测稳定为 7px、上 1px、下 6~7px，说明不是纯等比——更像「按窗口外接矩形裁剪后再缩放到 1280」，窗口本身不是严格满宽，左右各留 ~7.5px 的页面底。
3. **顶部只有 1px 是窗口自带的 1px 高光描边**，不是页面背景（实测第 0 行是 161~236 的浅灰，第 1 行已是 IDE 标题栏深色）。这解释了为什么 `clip-path` 的 top 只取 0.15%。
4. **两代产物混用**：54 个资产四边全 0，说明后续某一批录制改用了紧裁（或录制窗口贴边）。同一份文档里新旧素材并排，所以观感上「有的有边有的没有」。
5. **poster 与 GIF 同源同构图**：带框资产的同名 `.png` 也带框，且四边读数与 GIF 完全一致（如 `crud-sql.png` 与 `crud-sql.gif` 同为 1/7/7/7），证明 poster 是从同一段录制里抽帧导出，不是独立截图。

## 四、可选方案对比

| 方案 | 做法 | 覆盖率 | 代价 | 主要缺陷 |

### 5.2 GIF 试裁结果（2 个真实资产）

裁剪矩形 `crop=1264:910:8:2`（与建议值 7/1 差 1px，属同一档）；编码用 `split[a][b];[a]palettegen=stats_mode=diff[p];[b][p]paletteuse=dither=sierra2_4a`。

| 资产 | 原尺寸/字节 | 裁后尺寸/字节 | 字节变化 | 帧数 | fps | 时长 |
|---|---|---|---|---|---|---|
| `crud-sql.gif` | 1280×920 / 896,020 | 1264×910 / 872,414 | **−23,606（−2.63%）** | 83 → 83 | 15/1 → 15/1 | 5.54s → 5.54s |
| `sql-to-java.gif` | 1280×920 / 338,021 | 1264×910 / 329,468 | **−8,553（−2.53%）** | 200 → 200 | 15/1 → 15/1 | 13.34s → 13.34s |

**画质：全帧比对（不是抽帧）`PSNR r:inf g:inf b:inf average:inf`、`SSIM All:1.000000`** —— 即重叠区**逐像素完全一致**，零损失。

**体积陷阱（必须记录）**：同一命令若省掉 `palettegen`，直接用 `-vf "crop=..."` 重编码：

| 资产 | 原字节 | 朴素裁后字节 | 倍数 |
|---|---|---|---|
| `crud-sql.gif` | 896,020 | 36,337,474 | **40.6×** |
| `sql-to-java.gif` | 338,021 | 93,627,454 | **277×** |

原因是 ffmpeg 默认对 GIF 用单帧局部调色板 + 抖动，产生大量无谓噪声。**实施时必须带 `palettegen/paletteuse`，且要在脚本里写死，不能留成参数。**

### 5.4 裁剪是否切到 IDE 内容

- **顶部**：只裁 1px（实测第 0 行是 1px 高光、第 1 行已是 IDE 标题栏深色），**IDE 顶栏完整保留**，满足用户「IDE 顶部完整入镜」的硬要求。裁剪后左上角放大 4× 目视核对：IDE 图标、汉堡菜单、项目名、分支控件全部在场。
- **左/右/下**：被裁的 7px 逐行中位亮度 ≥150（浅灰），而 IDE 内容行中位亮度 ≈40（`#26282C` 系 Islands Dark 底色），两者之间没有过渡带，裁剪边界不会咬到内容。
- **兜底校验**：实施了「裁剪前后重叠区 PSNR 必须为 inf」的硬校验（已在 2 GIF + 2 PNG 上通过），任何切到内容的资产都会在这个校验里立刻暴露。

## 六、推荐方案

**分两步走：先 B 止血，再 A 根治。**

1. **第一步（P0，止血）**：只裁 `settings-orm-capture.png`（左/右 7px）与 `xml-syntax-highlight.gif`（右 7px + 下 7px）。这两张是站内**当前唯一还能看见白边**的图，走 markdown 直插、不吃 `clip-path`。零 CSS 改动、零布局风险，2 个文件。
2. **第二步（P1，根治）**：按第二节的 36 行表批量裁源（脚本 measure-then-crop、幂等），裁完**删掉三处 `clip-path`**。收益有三：源文件干净（插件仓/Marketplace/第三方转载复用都不再带白边）、54 个干净资产不再被多裁 7.7px、markdown 路径不需要再补 CSS。
3. **配套（P1）**：新增 `scripts/check-demo-borders.mjs` 作为守卫，扫描 `public/demo` 并在发现任何浅灰窗框时非零退出，防止下一次录制的带框素材静默入库。**必须做反向验证**（造一张带框 fixture 必须变红），否则等于没装。

不做 D（重新录制）：录制链在插件仓，成本与收益严重不成比例，且 36 个资产都能无损裁掉白边。

## 八、验收标准

1. `node scripts/check-demo-borders.mjs public/demo` 退出码 0，输出「90 个资产 / 0 个带框」。
