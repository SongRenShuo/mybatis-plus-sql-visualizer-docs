# 沙盒数据源解析为空的根因调研报告（M36 runners=0）

> 调研对象：插件「执行 SQL / 执行计划」路径在录制沙盒里报「未找到可用数据源」；日志 `build/MPSV-GifFresh/mybatis-plus-sql-visualizer/IU-2026.2.1/log/idea.log` 出现 `[M36] runners=0` 与 `[M36] runners empty (execute=true)`
> 调研方式：平台 jar 反编译（javap -c/-v）+ 沙盒与真机配置目录只读比对 + 沙盒日志检索。全过程只读，未触碰运行中的沙盒 IDE，未改任何源码
> 调研时间：2026-10-11 21:30（报告生成）
> 结论分档：文中「坐实」= 反编译字节码或文件系统/日志实证；「推断」= 由坐实事实推导，尚未在运行态验证

## 一、结论

一句话根因：录制沙盒的 `<沙盒 config>/jdbc-drivers/` 里没有任何已下载的驱动产物（只有下载清单 `jdbc-drivers.xml`），而 `CAN_CONNECT_TO` 的判定体要求「该数据源的驱动文件确实落在盘上」；6 个数据源全部被这一条滤掉，`DatabaseRunners.getDataSourceRunners` 因而返回空列表，插件侧只能报「未找到可用数据源」。

原假设「沙盒缺 master key → 凭据解不出 → canConnectTo=false」**证伪**：`canConnectTo` 的字节码里没有任何凭据/密码/连通性代码路径（`javap -c` 全文可见）。凭据缺失是另一个真实但独立的问题（见第五节 B 条）。

## 二、CAN_CONNECT_TO 的判定体（反编译坐实）

### 2.1 它是什么

`com.intellij.database.util.DbImplUtil.CAN_CONNECT_TO` 是静态字段，声明类型 `com.intellij.openapi.util.Condition<com.intellij.database.psi.DbElement>`：

- jar 与类：`<distro>/plugins/DatabaseTools/lib/modules/intellij.database.connectivity.jar` → `com/intellij/database/util/DbImplUtil.class`
- 它的静态初始化块只有两条指令：

```
static {};
   0: invokedynamic #1294,  0    // InvokeDynamic #13:value:()Lcom/intellij/openapi/util/Condition;
   5: putstatic     #837         // Field CAN_CONNECT_TO:Lcom/intellij/openapi/util/Condition;
```

- `javap -v` 的 `BootstrapMethods` 表第 13 项把它绑到一个方法引用：

```
13: LambdaMetafactory.metafactory
    Method arguments:
      #1619 (Ljava/lang/Object;)Z
      #1657 REF_invokeStatic com/intellij/database/util/DbImplUtilCore.canConnectTo:(Lcom/intellij/database/psi/DbElement;)Z
      #1659 (Lcom/intellij/database/psi/DbElement;)Z
```

即 `CAN_CONNECT_TO == DbImplUtilCore::canConnectTo`（同名类在不同 jar：`DbImplUtilCore` 在 `intellij.database.core.impl.jar`）。

### 2.2 判定体逐条（三个条件，全过才 true）

`DbImplUtilCore.canConnectTo(DbElement)`：

```
ds = element != null ? element.getDataSource().getDelegate() : null     // 取数据源 delegate
return ds instanceof LocalDataSource
    && canConnectTo((LocalDataSource) ds, element.getProject())
```

`DbImplUtilCore.canConnectTo(LocalDataSource, Project)`（同一个类，字节码 18~78 号指令）：

1. `StringUtil.isEmptyOrSpaces(ds.getUrl())` 为真 → 返回 false（URL 空即否）
2. `DatabaseArtifactContext.Companion.getInstance(project, ds)` 取上下文后，`DatabaseDriverClasspathManager.getInstance(project).hasDriverFiles(ds.getDatabaseDriver(), ctx)` 为 false → 返回 false（**驱动文件不在盘上即否**）
3. `return !StringUtil.isEmptyOrSpaces(ds.getDriverClass())`（驱动类名非空）

注意判定体到此为止：**没有连接测试、没有凭据读取、没有 TCP 探测**。「能否连上数据库」与这个 Condition 无关，它只是「这个数据源有没有可用的驱动文件、能不能被拿来执行」。

### 2.3 hasDriverFiles 要什么

`com.intellij.database.dataSource.DatabaseDriverClasspathManagerImpl#hasDriverFiles`（`intellij.database.connectivity.jar`，Kotlin）：

```
hasDriverFiles = additionalClasspathElements(driver, ctx).isNotEmpty()
              || (driver.getArtifacts().any { it.hasElements(ctx) } && isValidFiles(driver, ctx))
```

- `getAdditionalClasspathElements`（非 Eel 分支）直接返回 `driver.getAdditionalClasspathElements()`，即用户在驱动设置里手工挂的目录/库。本项目数据源用的是内置驱动，没挂任何手工库，所以这一支为空。
- `DatabaseDriverImpl$ArtifactRefImpl.hasElements(ctx)`：

```
if (myVersion == null) return false;                      // 版本未定 → 直接 false
return DatabaseArtifactManager.hasClasspathElementsFast(myId, myVersion, ctx);
```

- `DatabaseArtifactManager.hasClasspathElementsFast` → `DatabaseArtifactLoaderImpl.hasClasspathElementsFast`（`intellij.database.connectivity.ex.jar`）→ `hasClassPathFast(item, artifactDir, ctx)`，里面是实打实的磁盘检查：

```
Files.notExists(artifactDir) → false            // 目录不在 → 无文件
否则 Files.walk(artifactDir) 找文件              // 目录在但空 → 仍无文件
```

- 落盘位置由 `DatabaseArtifactContext.getLocalDownloadPath()` → `DatabaseDriverManagerUtil.getDownloadPath()` 决定：未设 `-Ddatagrip.driver.path` 时 = `PathManager.getConfigPath()` + `File.separator` + `jdbc-drivers`（常量拼接；真机目录布局 `jdbc-drivers/MySQL ConnectorJ/9.7.0/com/mysql/...` 与此吻合）。

对照本例：`mysql.8` 是插件内置驱动（`intellij.database.dialects.mysql.jar` 里的 `databaseDrivers/mysql-drivers.xml`：`mysql.base` 声明 `<artifact id="MySQL ConnectorJ" use="true" rolling="true"/>`，`mysql.8` `based-on="mysql.base"`，都没有写死版本），所以判定链是「artifact 版本（真机由用户/下载流程落成 9.7.0）→ 该版本目录下必须有解包后的驱动文件」。

- `isValidFiles` 另外校验 additional classpath / native libs 里每个 path 的 `Files.exists`（空表视为通过），对本文场景是恒真。

## 三、调用链复核（反编译坐实，补两处细节）

`DatabaseRunners.getAttachDataSourceRunners(psiFile, sql, consumer)`（`intellij.database.impl.jar`）：

- 先看 `DbImplUtil.getForcedDataSourceForExec(psiFile)`：非空则直接 `Collections.singletonList(createDataSourceRunner(...))` 返回（此时 runners 必为 1，与日志的 0 不符，说明本案没有 forced 数据源）；
- 否则转 `getDataSourceRunners(psiFile, sql, session=null, consumer)`。

`getDataSourceRunners` 的两路枚举与去重：

```
appropriate = DbImplUtil.getAppropriateDataSourcesForExec(psiFile)   // 逐个建 runner（跳过 session 当前数据源）
all         = DbImplUtil.getAllDataSourcesForExec(psiFile)
if (appropriate.size() == all.take(appropriate.size() + 1).size()) return list;   // 没有"额外"数据源
else 追加一个 all.runner.title 的文件夹 runner（DatabaseRunners$3）
```

这条去重解释了为什么 runners=0 而不是 1：`all` 这一路过滤的是 `!(ds instanceof SqlDataSource) && ds.isValid()`，MySQL/达梦这类 SQL 数据源本来就被排除，沙盒里也没有 Mongo/Redis 之类，所以 `all` 恒为空；两者都空 → 返回空列表。（若 `all` 非空，插件会拿到 1 个「全部数据源」目录项，日志就不会是 `runners=0`。）

两个枚举的空集位置：

- `DbImplUtil.getAppropriateDataSourcesForExec`：`getDatabaseDialectForExec(psiFile)` 为 null → 直接 `JBIterable.empty()`；否则 `DbSqlUtilCore.getAppropriateDataSources(dialect, vf, project, false, false)` 之后 `.filter(CAN_CONNECT_TO)`。
- `DbSqlUtilCore.getAppropriateDataSources(dialect, vf, project, p3=false, p4=false)`：`DbPsiFacade.getDataSources()` → `filter(p3 ? !SqlDataSource : isValid())` → `filter(DbImplUtilCore.getDatabaseDialect(ds).similarTo(dialect))`；末段是 `if (!p4 && list8.isEmpty()) return list7; else return list8`。也就是说方言不匹配时它会退回「全部 isValid 数据源」，**方言这道不会把列表清空**；能把它清空的只有紧接着的 `CAN_CONNECT_TO`（前提是方言非 null）。

因此「runners=0」在逻辑上对应两种可能：方言解析为 null，或 `CAN_CONNECT_TO` 全否。日志里插件已打印 `[M36] dialect pre-mapped to MySQL for mpsql-exec.sql`（走的是 `DialectPreMapping.ensureMapped` + `mapDialectBeforePsi` 那条预映射），加上下一节的文件系统证据（驱动缺失 ⇒ `CAN_CONNECT_TO` 必为 false），两条合起来把根因钉在驱动缺失上。若要在运行态一击区分，见第六节验证步骤。

## 五、假设判定与遗留疑点

A. 「沙盒缺 master key → 凭据解不出 → canConnectTo=false」：**证伪**（坐实）。判定体全文无凭据代码路径（第二节）。

B. 「沙盒凭据库缺失」：作为独立风险**成立**（坐实部分 + 推断部分）。坐实：真机 config 有 `c.pwd`/`c.kdbx`，沙盒 config 没有，工程里也没有密文。推断（未验证）：驱动补齐之后真正建连接时，沙盒大概率取不到 `root` 的密码，需要重新输入一次；这不影响 `CAN_CONNECT_TO`，也不影响 runners 的数量。

C. `options/databaseDrivers.xml` 里沙盒没有 `mysql.8` 条目：由此**推断**（未验证）沙盒里 `mysql.8` 的 artifact ref 只有插件内置的 `rolling="true"`、`myVersion` 为 null，于是即使把驱动文件拷进去，`ArtifactRefImpl.hasElements` 仍会在第一步 `myVersion == null` 处返回 false。这一环决定「只拷文件能不能直接生效」，是第七节处置排序的关键前提，请优先验证。

D. 每次启动都出现的 `DataSourceStorageLocal - No state loaded` / `Attempting to load empty state`、`DataSourceStorageShared$App - No state loaded`：字符串来源已坐实 —— `DelegatingPersistentStateComponent.noStateLoaded()/loadState()`（`intellij.database.core.impl.jar`），而 `DataSourceStorageLocal` 绑定的就是工程里的 `dataSources.local.xml`（常量池里可见 `dataSources.local.xml` + `dataSourceStorageLocal`）。语义未验证：可能是应用级实例的正常初始化日志，也可能表示本地态未加载。若是后者，`user-name` 之类也不生效，会加重 B 的判断。与本次根因无关。

E. 达梦数据源：日志两处 `WARN - LocalDataSource - Data source "mpj_dm@114.66.55.245" ...: failed to guess driver`（沙盒没有它的自定义驱动产物，`databaseDrivers.xml` 里只有驱动类名、没有 artifact）。它同样过不了 `hasDriverFiles`，属于同一根因的另一个实例。

## 六、处置建议（按代价排序）

代价口径：是否需要重启沙盒 IDE 单列，主线程据此排期。重启 = 录制中断 + 沙盒重新打开 demo 工程与索引的时间。

### 1. 拷贝驱动文件到沙盒（最低代价，先试，目标是不重启）

把真机的驱动目录整份拷进沙盒：

```powershell
Copy-Item -Recurse -Force `
  "C:\Users\USER\AppData\Roaming\JetBrains\IntelliJIdea2026.2\jdbc-drivers\MySQL ConnectorJ" `
  "F:\code\Java\Gitee\SongRenShuo\mybatis-plus-sql-visualizer\build\MPSV-GifFresh\mybatis-plus-sql-visualizer\IU-2026.2.1\config\jdbc-drivers\"
```

依据（坐实）：`hasClasspathElementsFast`/`hasClassPathFast` 的文件判定发生在每次调用时，是对磁盘 `Files.notExists/Files.walk` 的即时读取，不看启动期缓存 —— 所以理论上不重启也可能让 `hasDriverFiles` 翻真。
风险（推断，见第五节 C）：若沙盒里 `mysql.8` 的 artifact 版本为 null，这一步会无效，需要配合第 2 条。
要求：只新增文件，不要改沙盒 `config/` 里正在被运行中 IDE 使用的 XML；拷完让主线程在沙盒里再触发一次执行，然后 grep 日志 `[M36] runners=`（预期 5 或 6）。
是否需要重启：**否（待实测）**。

### 2. 合并驱动状态 XML（第 1 条无效时的兜底，需要重启）

把真机 `options/databaseDrivers.xml` 的 `mysql.8`（以及需要的话 `postgresql`、`mysql`、`redis` 等）条目合并进沙盒同名文件，保留沙盒原有的达梦条目：

```xml
<driver id="dm.jdbc.driver.DmDriver" name="dm.jdbc.driver.DmDriver" driver-class="dm.jdbc.driver.DmDriver" />
```

合并后 `mysql.8` 会带上 `version="9.7.0"`，与第 1 条拷进去的目录对上。写文件前先备份；这是启动加载的持久状态，**需要重启沙盒 IDE**（代价：一次重启 + 工程重新索引）。
是否需要重启：**是**。

### 3. 在沙盒 UI 里给数据源下载一次驱动（无重启，但要交互与网络）

Database 工具窗 → 任一 MySQL 数据源 → Driver 页 → Download（或直接点 Test Connection 让它提示下载）。IDE 自己会把版本落进 `databaseDrivers.xml` 并把文件写进 `config/jdbc-drivers`。这条不依赖手工拷文件，也顺带把第五节 C 的版本问题一起解决。
代价：需要在沙盒里做 GUI 操作（会打断录制），且要能访问 catalog 里配置的 aliyun 镜像；主线程当前正在用这个 IDE，属于可执行但要排期。
是否需要重启：**否**（IDE 内存状态自己刷新）。
附带收益：Test Connection 的提示文案本身就是「驱动文件缺失」的最直接确认，可以放在第 1 条之前当五分钟验证。

### 4. 插件侧加固（改代码，装插件要重启；只治「选不到」和文案，不治连库）

`DataSourceSelector.getAttachDataSourceRunners` 返回空时，不再直接放弃：

- 兜底枚举：`DbPsiFacade.getInstance(project).getDataSources()`（本案实测项目里就是 6 条），按 `DbImplUtilCore.getDatabaseDialect(ds).similarTo(...)`（或退回 `ds.isValid()`）过滤；
- 兜底执行：对选中的数据源调用公开 API `DatabaseRunners.runInDataSource(DbDataSource, String, Consumer)`（javap 确认是 `public static`，内部 `DatabaseSessionManager.getSession(project, connectionPoint, sql)` 后回调 session），与既有 `attachConsole` 链路衔接；
- 文案分级：用 `DatabaseDriverClasspathManager.hasDriverFiles(driver, ctx)`（注意版本为 null 也会 false）区分「一个数据源都没有」与「有数据源但驱动文件缺失」，别再笼统报「未找到可用数据源。请先配置数据源」——这正是本次把排查方向带偏的地方。
必须同时说明：这条**不能让沙盒真正连库**（连接仍需驱动文件），只解决「枚举被 CAN_CONNECT_TO 卡死」和误报文案，应与 1/2/3 配合。
代价：改码 + 构建 + 沙盒里更新插件（runIde 沙盒的插件来自构建产物），**需要重启沙盒 IDE**。

### 5. （可选）复用真机凭据库

把真机 `config/c.pwd`、`config/c.kdbx` 拷进沙盒 config，期望直接复用已保存的数据库密码；能否在新环境解密未验证，失败就在沙盒里重输一次密码（第 3 条里有现成的 Test Connection 入口）。
是否需要重启：**是**（凭据库在启动时初始化）。

## 七、需要主线程动手验证的点

1. 五分钟零改动确认：在沙盒里对任一 MySQL 数据源点一次 Test Connection，看是否提示「驱动文件缺失 / 需要下载」。这能直接坐实驱动缺失，且不重启、不改文件。
2. 第 1 条执行后看日志：`grep "\[M36\] runners=" idea.log`，若由 0 变 5/6 → 根因确认，且第 2 条可省；若仍 0 → 看沙盒 `options/databaseDrivers.xml` 是否被 IDE 补出了 `mysql.8` 条目（有补说明走了下载路径，可继续观察；没补则做第 2 条并重启）。
3. 重启后若仍是 0，反向验证方言分支：需要插件侧临时加日志打印 `DbPsiFacade.getDataSources().size`、`getDatabaseDialectForExec(psiFile)`、以及逐个数据源的 `canConnectTo` 结果（有代码改动成本，仅在 1、2 都无解时才做）。
4. 驱动恢复后确认是否弹密码：这决定第 5 条要不要做。
