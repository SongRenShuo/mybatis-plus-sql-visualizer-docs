# 开发计划：KV 写额度优化——cron 清扫锁按需获取

> 日期：2026-09-13 08:50
> 仓库：sql-visualizer-admin（sweep 前置闸 + 回归测试）
> 性质：资源额度优化

## 一、背景

2026-09-13 早晨收到 Cloudflare 告警邮件：Workers KV 免费套餐日写入额度已用 50%（1000 次/天的一半）。排查结论：

- 当日所有人工操作（部署、D1 远程查询、GET 验证请求）**零 KV 写入**——限流中间件只对 POST 提交/投票/评论/登录失败四类路由写 KV 计数（`rate-limit.ts:9-17`），GET 不占额度；
- 大头是 Worker 自身常态消耗，其中最大的单项是**聚合通知 cron 兜底清扫**：`scheduled` 每 5 分钟触发一次 `sweepStaleAggBuffers`，无条件写清扫锁（`push:agg:sweep:lock`），哪怕库中没有任何待冲刷行——**空转也固定烧 288 次/天**（24h × 12 次/h），占免费额度的 29%。

次要消耗：每次真实投票最多 5 次写（限流主桶 + 网段桶 + 目标帖桶 + 两个刷票预警计数器），每次提交约 4 次（限流 + 预警 + 通知去重 + 邮件频控）。288 的保底加上当日投票/提交流量，正好落在 500 上下，与告警吻合。

## 二、方案

`sweepStaleAggBuffers` 增加前置闸：先查 D1 是否真有超窗缓冲行，没有直接返回；查到才走原有拿锁冲刷路径。

```sql
SELECT 1 FROM fb_notifications
WHERE status = 0 AND type IN ('admin_notify', 'comment_notify')
  AND created_at <= datetime('now', '-' || ? || ' minutes')
LIMIT 1
```

要点：

1. **预检谓词与冲刷条件严格同口径**（status=0、两组类型、超窗分钟数都来自 `getAggWindowMinutes`），不会漏扫；
2. **预检失败按「有行」兜底**落入原路径——D1 抖动时最多退回原行为（多写一把锁），清扫功能不受损；
3. 冲刷主体、锁语义、TTL 全部不动，行为只减不改：绝大多数 cron 触发（空转）从「1 次锁写 + 1 次锁删」变为**零 KV 访问**，一天省下 288 次写。

## 三、改动清单

| 文件 | 改动 |
| --- | --- |
| `src/services/push-agg.ts` | `sweepStaleAggBuffers` 前置 D1 预检 |
| `tests/push-agg.test.ts` | 新增 3 用例：空库零 KV 访问、仅窗口内新行零写入、有超窗行锁照常获取 |

## 四、验证

1. `npx vitest run` 12 文件 87 用例全绿（新增 3 用例用 `makeCountingKV` 的调用计数断言空转 `put/get` 均为 0）；
2. 预检 SQL 已在**生产 D1** 直接执行验证（语法与绑定拼接无误，当前返回空集，与新代码预期一致）；
3. `wrangler tail` 因本机网络（直连超时、代理下 WebSocket 不通）无法观测 cron 运行时，以「生产 SQL 验证 + 同源语义单测」替代，并在代码里保留了预检失败兜底，风险敞口可接受。

## 五、额度影响

修复后每日 KV 写预算大致为：投票数 × 5 + 提交数 × 4 + 偶发的冲刷锁/版本基线写。按当前流量估计日用量从 ~500 降到 <50（5% 以内），「总票数类统计页面」等 GET 流量依旧零消耗。

遗留（本次不做）：`rate-limit` 的 `kv.put` 无兜底仍是已知待修项——额度真打满时提交/投票会 500；清扫锁按需化后触发概率显著降低。
