## 一、问题实证（用户补充日志）

真机日志（同一毫秒、两个线程，`?` 语句与 named 语句交错）：

```
13:47:17.843 [TID: AE51C…] [http-nio-0.0.0.0-6608-exec-4] DEBUG org.springframework.jdbc.core.JdbcTemplate Line:643 - Executing prepared SQL statement [SELECT "deptId" FROM tableA WHERE "deleted" = 0 and paramA LIKE CONCAT('%',?,'%')]
13:47:17.843 [TID: C2897…] [http-nio-0.0.0.0-6608-exec-5] TRACE xxx.impl.dml.BizObjectRepositoryJdbcImpl Line:260 - sql = SELECT COUNT(*) as count FROM ipm_DeptLeadCfg  WHERE ( ("deleted" = :param1) AND ("paramA" LIKE :param2) ) , parameters = {param1=0, param2=%ff808xxxxx01975c7fe43200ba%}
```

预览弹窗现象：警告「存在未替换的 ? 占位符：未捕获到参数绑定日志（…descriptor.sql 设为 TRACE）」+ 参数区「无未解析参数」——即 `log.preview.unresolvedNoBinding` 分支（`?` 残留 + params 空）。

## 二、根因分析

### 问题一：并发交错下参数行错挂/丢失（主）+ 引导文案误导（次）

[JdbcTemplateLogParser.kt](../../../mybatis-plus-sql-visualizer/src/main/kotlin/cn/song/mybatisplus/visualizer/log/JdbcTemplateLogParser.kt) 是**每个控制台一个实例的串行状态机**：`pendingSql` + `pendingParams` 单槽位，隐含假设「SQL 行(DEBUG) → 参数行(TRACE×N) → 下一条」严格顺序。但 Tomcat 并发请求的日志按**到达序**混排，多条语句的行交错输出：

1. exec-4 的 `Executing prepared SQL statement [SELECT … ?]` 到达 → `pendingSql = stmtA`（Spring 在 execute 前打印此行，参数绑定行后到）；
2. exec-5 的 named 单行（`sql = … :param1 … , parameters = {…}`）到达 → feedIdle 分支 1 先 `closePending()`：**stmtA 带空 params 强制产出**，named 条目本身正常；
3. exec-4 的参数绑定行（`Setting SQL statement parameter value…`）随后到达 → 此时 `pendingSql == null`，分支 3 第 107 行**静默丢弃**（「无 SQL 上下文，忽略」）。

结果：stmtA 条目 `?` 数 > 0 且 params 空 → 预览走 `unresolvedNoBinding` 分支。只有交错发生时才触发，与用户「**有些**参数没识别」吻合。另一交错形态（两条 `?` 语句的参数行在第二条 Executing 行之后到达）会把 A 的参数挂到 B 上，触发数量不匹配警告（`unresolvedWarning`），同根因的姊妹症状。

次级问题：`log.preview.unresolvedNoBinding` 文案是 **Hibernate 专用引导**（`org.hibernate.type.descriptor.sql` 设 TRACE），对 JDBC source 条目误导——JdbcTemplate 取参数的正确引导是 `org.springframework.jdbc.core`（StatementCreatorUtils）开 TRACE。两处警告出口（`LogEntryPreviewRecognizer` 与 `EntrySourceMatcher` 的 M37.1 反查预览）都未按 `SqlSource` 分流。

注：地在语句内的 `CONCAT('%',?,'%')` 占位符计数无坑（`countPlaceholders` 为 string-aware，函数实参内 `?` 正常计数）；named 行本身解析（`NAMED_PARAM_PATTERN` + `renderUntyped` 值启发式）本例无缺陷。

### 问题二：历史 tab 时间戳硬编码，从未读设置

- SQL 日志页：`SqlLogPanel.kt:1480` `formatTimestampFragment()` 读 `state.logTimestampFormat`（非法 pattern 回退默认，`logTimestampEnabled=false` 返回 null 隐藏）→ 跟随设置，正常。
- SQL 历史 tab 二级列表：[HistorySqlLogPanel.kt:668](../../../mybatis-plus-sql-visualizer/src/main/kotlin/cn/song/mybatisplus/visualizer/log/HistorySqlLogPanel.kt) `HistoryCellRenderer` 硬编码 `SimpleDateFormat("yyyy-MM-dd HH:mm:ss", Locale.ENGLISH)` → 改设置无效，正是用户看到的默认格式。
- 历史原始文件正常的原因：`.idea/sql-visualizer/sql-history/*.sql` 文件头时间戳由 `SqlLogAutoSaver.TIMESTAMP_FORMATTER` 固定 `yyyy-MM-dd HH:mm:ss.SSS` 写入（文件自治格式，本就不跟随设置）；用户设置格式恰与其视觉一致，故「文件正常」。**文件头格式保持不动**（Reader/头部正则/条数判据均锚定现行格式，变更收益低）。
- 另：history 包 `SqlHistoryPanel.kt:210` 亦硬编码 `"HH:mm:ss"`（T-Perf-24 未注册死代码，按既有「接线保持一致防复活分叉」惯例顺手对齐）。

## 三、修复方案

### F1（问题一主修复）：JdbcTemplateLogParser 线程分桶

日志行自带线程 token（`[http-nio-0.0.0.0-6608-exec-4]`，SkyWalking 场景行首另有 `[TID: xxx]` 段须排除）。解析器内部按线程键维护独立状态机，行到达先路由、再进该桶 FSM：

- 新增 `extractThreadToken(line)`：提取行内全部 `[...]` 段，过滤 `TID: ` 前缀段与日期段后取命中线程形态（`-exec-`/`-nio-` 等，或取 level 前最后一个方括号段）的最后一个；提取失败回退单一共享桶（现行行为 fail-open）。
- 桶结构 = 现 `pendingSql/pendingParams/collecting/multilineBuffer/multilineNet/multilineInString` 打包为 `ThreadBucket`；`entries` 保持解析器级共享列表（feed 时逐条 append，产出序≈到达序不变），`enabled/maxParseLength` 全局沿袭。
- `closePending()`（面板强制冲刷）遍历所有桶；桶状态机产出后归零复用。桶上限保护（如 64 桶 LRU，防异常膨胀）。
- `takeEntries` 不变。对外 API 形态（feed/closePending/takeEntries）零变化，SqlLogConsoleBridge / LogToSqlPanel 接线不动。

二期候选（计划内不做，避免回归面扩大）：MyBatisLogParser（Preparing/Parameters 相邻行同样可交错）与 HibernateLogParser 同构分桶——MyBatis 两行通常背靠背输出、实证风险低于 JdbcTemplate，待用户反馈或日志佐证后再立项。

### F2（问题一文案分流）：NoBinding 警告按 SqlSource 选 key

- 新增 bundle key `log.preview.unresolvedNoBinding.jdbc`（zh：存在未替换的 ? 占位符：未捕获到参数绑定日志（JdbcTemplate 需将 org.springframework.jdbc.core 设为 TRACE）；en 对应）。
- `LogEntryPreviewRecognizer.toPreviewResult` 与 `EntrySourceMatcher` 的反查预览两处按 `entry.source == SqlSource.JDBC` 分流；`unresolvedWarning`（数量不匹配）不必分流。
- `BundleParityGuardTest` 自动覆盖 parity。

### F3（问题二）：历史页时间戳统一走 formatTimestampFragment

- `HistorySqlLogPanel` 的 `HistoryCellRenderer`：`SimpleDateFormat("yyyy-MM-dd HH:mm:ss")` 硬编码 → 调用同包 internal `formatTimestampFragment(entry.timestamp)`（含非法格式回退与 `logTimestampEnabled` 开关语义，null 时跳过时间戳片段）。历史页自带尾空格与灰属性的片段形态与日志页一致，顺带消除一处分叉。
- history 包死代码 `SqlHistoryPanel.kt:210`：改读 `state.logTimestampFormat`（该死面板无开关 UI，不加开关分支）。
- 性能面不动（列表渲染每条 new SimpleDateFormat 与日志页现状同范式；T-Perf-12 的 DateTimeFormatter 常量化如后续要做应两页一起做，不在本次范围）。

改动规模：JdbcTemplateLogParser 内部重构（约 +90 行，对外形态不变）+ 2 处渲染小改 + 1 个新 bundle key，测试新增约 5 例。
