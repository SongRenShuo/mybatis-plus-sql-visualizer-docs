## 二、录制规范

统一约定一次到位，避免录完返工：

### 2.1 工具选型：Recordly（用户指定，已确认本机安装）

用 **Recordly** 替代最初设想的 PixPin。理由：

- 原生 GIF 导出（mp4 / looping GIF 二选一），省去外部转码环节
- 内置自动缩放（auto-zoom）、动态模糊光标、循环光标路径，成片演示力明显强于 PixPin 裸录
- 免费开源，本机已装（用户 2026-09-07 确认）

分工约定：

- **Recordly**：负责 T1~T8 八个 GIF 的录制与导出
- **PixPin**：仍保留，负责补镜头级别的截图与快速局部捕捉（例如分镜首尾帧核对、突发异常取证），不做主录制
- 首次使用注意：确认 Recordly 的自动缩放效果在文档站容器里观感是否合适，不合适则关掉该项，用固定区域录制兜底

### 2.2 站点实际显示宽度与清晰度基准（硬性）

清晰度以「页面上的真实显示宽度」为准。已核实两处投放位的显示尺寸：

| 投放位 | 显示宽度 |
|--------|---------|
| 功能页 GifPlayer（正文列，VitePress 默认，含右侧 aside） | 约 688px |
| 首页 DocsShowcase（max-width 90rem 双栏，视频列约 60% 宽） | 约 1000~1100px，object-fit: cover（16:10 裁切） |
| 首页 FeatureAlternate（object-fit: cover, min-height 300px） | 约 550~600px |

由此定两条铁律：

- **录制源宽 1600px 左右**（源码区缩放后换算到站点显示有约 1.6~2.3 倍余量），GIF 导出统一 **缩放到宽 1280px**——覆盖最宽的 DocsShowcase，在功能页 688px 列里是超采样，文字必然锐利。**唯一例外：wrapper-preview 因首页 DocsShowcase 共用，导出宽度升到 1440px**（见 2.7 的超采样结论），其余七张维持 1280
- **缩放比不低于 0.85 且导出后逐张人眼核对**：文字像素感重或发虚即调大 UI 重录，不以「能看清」为最低线，以「像原生截图一样锐利」为验收线

### 2.3 环境：2026.2 沙盒（硬性）+ 清晰度三件套

**沙盒版本（硬性）**：录制（Recordly）与截图（PixPin 补拍、poster 抽帧源画面）一律在插件仓库的 **2026.2 runIde 沙盒**里做，不用日常 IDE，也不用 2024.3 默认沙盒。切换按插件仓库 `docs/架构设计/03-开发与测试指南.md` 2.1 执行：临时改插件仓库 `build.gradle.kts:64` 为 `intellijIdeaUltimate("2026.2.1")` → `./gradlew runIde`（跑前先查并行登记表）→ 全部录制结束 `git checkout build.gradle.kts` 还原。三个注意：

1. 2026.2 沙盒**首次启动**要登录 JetBrains 账号激活 Ultimate，并下载约 2GB 发行版（gradle.properties 已配代理）——这笔一次性成本放在 T0 前置完成，不拖到录制当天；
2. `-PplatformVersion` 命令行参数当前未接线，不可用，只能改 build.gradle.kts；
3. 本任务不跑 testDatabase，无 jdbc-drivers 版本耦合，无需关心该任务的 2024.3 路径写死问题。

沙盒按版本分目录、与日常 IDE 完全隔离，但设置全新——下述三件套参数要在 2026.2 沙盒里重新设一遍。

**主题**：不手动指定 Light，**用 2026.2 沙盒默认主题**，即 IDEA 官网 whatsnew 演示视频同款（官方样片抽帧实测就是 New UI 浅色，沙盒全新默认设置与其天然一致）。

清晰度靠「窗口构图 + IDE 缩放 + 字号」三者配合，不是单一开关：

1. **IDEA UI 缩放（首选手段）**：`Settings > Appearance & Behavior > Appearance`，Windows 下调到 **150%**（大显示器可试 175%）。UI 缩放等比放大全部界面（含 gutter 图标、弹窗、面板），是提高「每像素信息密度」最直接的方式
2. **编辑器字号 18pt 起**：`Settings > Editor > Font`。录制分镜里出现整段 Wrapper 链 + 弹窗 SQL 的场景较多，18pt 保证代码区在 150% 缩放下依然读得清

### 2.4 画面与节奏

本节各项约定以「对齐 JetBrains 官方 whatsnew 演示视频风格」为总纲，2.7 是逐帧分析得出的官方风格基准，两者对照执行：

- 只录编辑器加相关弹窗/工具窗口，不要带桌面杂项；Recordly 录制区域按 2.3 的构图框选（对应官方「全窗口构图、主体内容占 70%+、留白少而均匀」）
- 节奏模拟真实用户，鼠标移动与点击之间留自然停顿，关键结果（SQL 出现、代码生成）停留 1~2 秒再动（对应官方「动静反差节奏」：长静止 + 动作瞬间爆发，静止是常态不必抢节奏）
- 操作演示以单条主线走完为限，不做多轮反复操作（官方每支视频只演示一个功能点）
- 光标仅在有操作时出现/移动，移动平滑带动态模糊（Recordly 光标选项开启），静止段光标不乱晃
- 时长单个 6~15 秒，首尾帧尽量一致，循环不跳（对应官方 mp4 loop 无缝循环、无淡入淡出）
- 主题一律官网演示示例同款（2026.2 沙盒默认，见 2.3），录制中不手动改主题；与站点默认浅色一致，不做暗色双版本
- auto-zoom 按需开启：官方表现力主要来自操作时局部自动放大；GIF 12fps 下若缩放过渡动画卡顿明显，改瞬切或固定区域录制

### 2.5 体积控制与静态兜底（强制）

GIF 体积随画面复杂度波动大，规范如下：

- 目标单文件 3MB 以内；超出先降帧重压（ffmpeg fps=12, lanczos），**缩放不许低于 1280 宽**（2.2 的清晰度底线优先于体积，压不进 3MB 宁可接受 4~5MB，靠 poster 兜底 + Recordly 导出优化体积）
- **每个 GIF 必须配套一张静态兜底图**（poster）：取 GIF 关键内容帧（如 SQL 已渲染完成的弹窗画面，即各分镜里「停 2 秒」的那一帧），通过 ffmpeg 抽帧或 Recordly 时间线导出，命名为 `/demo/<功能名>.png`，与 GIF 同名不同后缀
- 抽帧后如需微调，用 PixPin 补拍同角度静态图也可
- 兜底图是硬性要求，不是可选项——弱网、动图加载失败、低性能设备三种场景都靠它

### 2.6 命名

沿用现有约定 `/demo/<功能名>.gif` 与 `/demo/<功能名>.png`，与 features/*.md 一一对应。

GifPlayer.vue 需小幅改造：props 增加 `poster`（已存在，无需加）之外，img 分支默认渲染逻辑改为「GIF 加载完成前优先展示 poster，加载后切 GIF」，并接受 poster 可选（兼容旧调用）。具体改造见 T9 前置任务 T9a。

### 2.7 官方演示视频调研结论（JetBrains whatsnew 2026.2）

为回答「官方录制效果好在哪、有什么可吸收」，抽取了 IDEA 2026.2 whatsnew 页 8 支官方功能演示视频中的 2 支完整样本逐帧分析：DB_migration（66s）与 Spring_Security（91s），均为 h264 1920×1080@30fps、码率 4.8~5.5Mbps、单支 45~54MB；页面 video 元素显示 732×412，即官方以约 2.6 倍超采样投放（其余样本因网络多次截断下载损坏，样本量足够，不再补下）。

**可直接吸收（已并入本计划各处）**：

1. **官网示例主题 + 超大编辑器字号**：官方帧里代码字号观感达 20px+（1080p 下），主题即 2026.2 沙盒默认的 New UI 浅色——本计划的主题约定（2.3）与官方完全同源；印证 2.3 三件套的 150% 缩放 + 18pt 方向正确，可再试 20pt 对比
2. **全窗口构图但不塞满**：官方保留完整 IDE 窗口（项目树 + 编辑器 + 工具窗），主体内容占画面 70% 以上，四周留白少而均匀——与 2.3「框选紧致区域」同构，录制时保持该比例
3. **动静反差节奏**：场景检测显示官方视频静动分布极不均匀——Spring_Security 91 秒里仅 9 个画面突变点（8~53 秒连续 45 秒近乎静止），静止段画面零变化、动作瞬间集中爆发。印证 2.4 的「关键结果停留 1~2 秒」，且静止是演示的常态，不必抢节奏
4. **首尾帧一致、无缝循环**：官方 mp4 带 loop 属性直接循环，无淡入淡出，与 2.4 约定一致
5. **视频 + 同帧 poster 结构**：官方每支视频配同帧 PNG poster，「动图 + 静态兜底」方案得到官方背书，2.5 的强制兜底要求维持

**Recordly 能力项（录制时按需开启）**：auto-zoom（官方表现力的主要来源，操作时自动放大局部区域）、平滑光标移动、点击涟漪。首条 GIF 先验证 auto-zoom 观感（风险备注已有此约定），生硬则关掉用固定区域兜底。

**坚持 GIF 导出相对官方 mp4 的损失（确认接受，不再纠结）**：

- 帧率 30fps → 12fps：auto-zoom 的缩放过渡动画会略卡顿（官方是 30fps 平滑动画）。缓解：关闭 auto-zoom 的动画过渡（瞬切），或用固定区域录制避开过渡帧
- 256 色调色板：IDE 界面抗锯齿边缘有轻微色带风险。缓解：浅色低饱和主题下基本不可见，无需特殊处理
- 无法 mp4/webm 双源自适应、无 h264 压缩效率：由 2.5 的同名 PNG 兜底承担加载风险，这正是兜底图存在的意义

**规格确认**：官方 1920 源 / 732 显示 = 2.6 倍超采样；本计划功能页 1280 / 688 = 1.86 倍、FeatureAlternate 1280 / 550 = 2.3 倍，均在官方同量级；唯一低于量级的是首页 DocsShowcase（1280 / 1100 ≈ 1.16 倍），故 wrapper-preview（首页共用）导出宽度升到 **1440**（1.31 倍），该张体积预算同步放宽到 4MB，其余七张维持 1280 / 3MB。T11 清晰度抽查时 DocsShowcase 处重点核对该张。

## 五、风险与备注

- 沙盒渲染异常：录制前先肉眼确认 gutter 图标与弹窗在沙盒里渲染正常；若沙盒有问题改用真机录制，同样遵守官网示例主题与清晰度三件套约定
- 2026.2 沙盒首次启动需激活 Ultimate（登录 JetBrains 账号）并下载约 2GB 发行版，放在 T0 一次性完成；版本切换是临时改 build.gradle.kts:64，全部录制结束后务必 `git checkout build.gradle.kts` 还原，避免污染其他并行任务
- Recordly 自动缩放成片在站点容器内观感未验证：官方视频的表现力主要来自 auto-zoom（见 2.7），首条 GIF（建议用 T7 annotation-preview，最短）先小规模验证清晰度与观感两项；auto-zoom 开启时若 GIF 里缩放过渡动画在 12fps 下卡顿感明显，改瞬切或固定区域录制
- UI 缩放 150% 下沙盒若出现控件错位/渲染毛刺（高 DPI 兼容问题），退到 125% 并把编辑器字号补到 20pt 补偿，验收线不变
- GIF 体积随画面复杂度波动大：优先录小区域（Recordly 框选紧致构图本身就在省体积）、必要时降帧重压
- Recordly 若输出 mp4：用 ffmpeg 转 GIF（fps=12，宽度按 2.2 各张规格，默认 1280、wrapper-preview 1440），poster 抽帧逻辑不变
- 官方风格吸收清单随 2.7 一次成文，后续官方推出新版本演示视频不再追加调研——本计划的基准已够用，避免调研无限滚动
- 演示数据全部用 demo 工程真实数据，不摆拍假结果；截图内容与文档描述如有出入，以插件实际表现优先，文档文字纠偏走单独任务
