# 开发计划：需求池统计票数误含已删反馈的票

> 日期：2026-09-13 07:10
> 仓库：sql-visualizer-admin（统计接口 + 回归测试）
> 性质：缺陷修复

## 一、需求

需求池页面底部统计显示「共 5 条反馈 共 711 票」，其中票数把已删除反馈的投票也算了进去，数字严重失真。要求统计口径与页面可见内容一致：只统计当前可见反馈的票数。

## 二、现状与根因

### 2.1 现象与数据佐证

生产 D1 实测（2026-09-13 上午，只读查询）：

| 查询 | 结果 |
| --- | --- |
| `COUNT(*) FROM fb_votes`（当前接口口径） | 711 |
| `SUM(vote_count) FROM fb_posts WHERE is_deleted=0 AND is_hidden=0`（可见帖口径） | 0 |
| 已删除帖数 / 这些帖携带的票数 | 11 条 / 710 票 |
| 隐藏帖数 | 1 条 |

即全站 711 条投票记录里，710 条属于 11 条已删除的反馈，当前可见的 5 条反馈实际票数合计为 0。页面「共 5 条反馈 共 711 票」两个数字完全对不上。

### 2.2 根因

`GET /api/v1/feedback/stats`（`src/modules/feedback/routes.ts`）里，`totalPosts` 和各分组统计都带了 `is_deleted = 0 AND is_hidden = 0` 过滤，唯独 `totalVotes` 是裸的全表计数：

```sql
SELECT COUNT(*) as count FROM fb_votes
```

而管理后台删除反馈是软删除（`UPDATE fb_posts SET is_deleted = 1`，admin 模块），**不清理 `fb_votes` 表**。被删帖的投票记录全部留在库里，被这行 COUNT 全数计入。

其余接口口径核查结论：`/feedback/posts` 列表与 `/feedback/analytics`、`/feedback/activity` 的所有统计均已正确过滤，本缺陷只涉及 `/stats` 一处。

## 三、方案设计

### 3.1 口径选择

两个候选：

| 候选 | SQL | 评价 |
| --- | --- | --- |
| A. 按投票记录实算 | `SELECT COUNT(*) FROM fb_votes v JOIN fb_posts p ON v.post_id = p.id WHERE p.is_deleted = 0 AND p.is_hidden = 0` | 需 JOIN，且与页面展示口径可能不一致 |
| B. 按帖子冗余列求和（采用） | `SELECT COALESCE(SUM(vote_count), 0) FROM fb_posts WHERE is_deleted = 0 AND is_hidden = 0` | 不 JOIN，与列表页恒等 |

采用 B，理由：

1. 列表页每张卡片的票数就是 `fb_posts.vote_count`，「共 N 票」取这批行 vote_count 之和，数学上与页面可见内容严格恒等；
2. `vote_count` 的所有写路径都同步维护：用户投票/取消投票与 `fb_votes` 增删在同一 batch 原子执行，管理员撤销刷票按删除行数回减（MAX 防负），合并帖把源帖票数并入目标帖——活帖上 `vote_count` 与投票记录行数本就同步，不存在漂移场景；
3. 与 `totalPosts` 同表同条件，一条 SQL 不增加 D1 往返。

### 3.2 改动内容

`routes.ts` 的 `/stats` 接口，`totalVotes` 一条 SQL 改口径，响应结构不变。

连带受益：管理后台 Dashboard 与统计页的「总投票」卡片读同一接口，一并修正。

前端（文档站 `FeedbackPool.vue`）零改动——它只展示接口返回值；投票成功后的本地 ±1 逻辑也不受影响。

### 3.3 回归测试

新增 `tests/feedback-stats.test.ts`（复用 `makeFakeD1` + 真实 migrations 的既有测试基建）：

- 造数：可见帖 2 条（分别 3 票、2 票）、已删除帖 1 条（5 票）、隐藏帖 1 条（7 票），`fb_votes` 同步插入对应记录；
- 断言 `totalPosts = 2`、`totalVotes = 5`（可见帖票数之和），已删帖与隐藏帖的票不计入；
- 断言 `statusStats` / `typeStats` 只含可见帖（防止口径再次分叉）。

## 五、验证

1. `npx vitest run` 全绿；
2. 部署 Worker（`npx wrangler deploy`，认证走仓库根 `.cf-token`）；
3. 线上验收：`GET /api/v1/feedback/stats` 的 `totalVotes` 应为 0（当前可见 5 帖实际票数合计），`totalPosts` 仍为 5；文档站需求池页脚显示「共 5 条反馈 共 0 票」，与列表卡片票数合计一致；
4. 后台 Dashboard「总投票」同步显示 0。

## 六、风险

- 部署后「总票数」从 711 骤降为 0 视觉上变化明显，属预期修正（历史 710 票本就挂在已删帖上）；
- 若未来新增绕过 `vote_count` 的写路径（如直接批量改 `fb_votes`），口径 B 需同步维护，测试用例即护栏。

## 七、修订一：线上孤儿投票数据清理（2026-09-13 上午）

接口修复只保证统计不再误计，`fb_votes` 里那 710 条挂在已删帖上的记录仍在库中。为免后续按投票记录做分析（如刷票审查、指纹分析）时被脏数据干扰，做一次性清理：

1. **干跑核对**：`fb_votes` 全表 711 条，其中 JOIN `is_deleted=1` 的帖恰为 710 条，无指向不存在帖子的孤儿记录，另有 1 条挂在隐藏帖上；
2. **备份**：710 条记录全量导出至 `sql-visualizer-admin/.local/votes-on-deleted-posts-backup-20260913.json`（含 id/post_id/fingerprint/ip/user_agent，本地留存，不进 git）；
3. **删除**：`DELETE FROM fb_votes WHERE post_id IN (SELECT id FROM fb_posts WHERE is_deleted = 1)`；
4. **复核**：全表 711 → 1（仅剩隐藏帖那条），已删帖投票清零，`/stats` 线上返回 `totalPosts: 5, totalVotes: 0` 不变。

隐藏帖的投票记录**保留**：隐藏是可逆操作，帖可能恢复显示，其票数应随之回来；已删帖不可逆，记录才清。若未来出现「删帖同步清投票」的需求，应在管理后台删除接口的 batch 里加一条 `DELETE FROM fb_votes`，与本次口径呼应。
