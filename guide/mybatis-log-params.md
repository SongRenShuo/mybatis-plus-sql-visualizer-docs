# MyBatis 日志里的问号怎么变成真实参数

MyBatis 打印 SQL 时，语句和参数是分开的：`Preparing:` 行是一串 `?`，参数值在其后的 `Parameters:` 行。想复制一条能直接跑的 SQL，就得自己把参数按顺序填回去——字符串要加引号、日期要转格式、值一多就容易错位。这篇把常见做法列一遍，最后给出插件里的一键方案。

## 为什么日志里只有 ? 和 Parameters

这是 MyBatis 的日志设计：开启 SQL 日志后，`Preparing:` 行输出的是预编译语句（占位符形态），实参按顺序列在 `Parameters:` 行，后面还跟着类型说明。日志框架拿到的本来就是两段分离的文本，所以日志里永远不会出现一句拼好的完整 SQL。

两个常见的连带问题：

- 参数行通常要求日志级别开到 `TRACE`，级别不够时只有 `Preparing:` 没有 `Parameters:`
- 主流形态带箭头前缀（`==> Preparing:`），部分封装输出裸 `Preparing:`，两种形态不能混用一套解析规则

## 通用解法有哪些

**MyBatis 日志配置**：零成本，参数就写在日志里。局限是参数与语句分离、要人工拼接；批量执行时多个参数行对应一条语句，肉眼对齐很容易错；日志级别放开后，生产环境的日志量与敏感值暴露也需要权衡。

**p6spy**：以 JDBC 代理驱动的身份介入。应用把数据源的驱动类换成 p6spy 的实现，它在真实 JDBC 调用外面包一层，把语句与实参拼成单行完整 SQL 输出，输出格式可通过 `spy.properties` 定制。能看到每条 SQL 的最终执行形态，接入成本在工程侧：引入依赖、改驱动配置，多数据源时每处都要换。

**自定义 MyBatis 拦截器**：实现 `Interceptor` 拦截执行器，从 `BoundSql` 取语句与参数绑定自己渲染。灵活度最高（例如只处理特定 mapper），但字符串加引号、日期格式、null 这些类型细节都要自己处理，代码随工程常驻维护。

## 各方案怎么选

| 方案 | 改工程吗 | 出完整 SQL 吗 | 适合场景 |
|------|---------|--------------|----------|
| 日志配置 | 不改（调日志级别） | 否，人工拼 | 临时排查一两条 |
| p6spy | 引依赖、换驱动 | 是 | 工程需要长期在日志侧输出完整 SQL |
| 自定义拦截器 | 加代码 | 自己拼 | 有定制诉求、愿意维护 |
| SQL Visualizer | 不改 | 是，自动还原 | 开发时在 IDE 里随跑随看 |

这些方式并不互斥：日志配置与插件、p6spy 与插件都可以并存，按需组合。

## 用插件直接还原

SQL Visualizer 的 [SQL 日志工具窗口](/features/sql-log) 把这件事搬进 IDE，两条通道：

- **增强捕获**（默认开启）：应用启动后插件在本机应用 JVM 内挂载采集点，执行的 SQL 连同真实参数、耗时、影响行数直接入列，条目自带调用栈、可精确跳回触发它的源码行
- **控制台捕获**（回落通道）：解析运行控制台里的 `Preparing:` / `Parameters:` 日志（含 `==> Preparing:` 混合前缀形态），自动把参数拼回语句，不要求改工程
