# 不用 p6spy，怎么看到带真实参数的完整 SQL

p6spy 是常见的 SQL 观测方案，但它要求把数据源的 JDBC 驱动换成代理实现。依赖审计过不了、多数据源改不动，或者只是偶尔查一条 SQL——这些时候不想动工程，还有别的路。这篇先说清 p6spy 的工作方式与接入成本，再列替代做法。

## p6spy 是怎么工作的

p6spy 以 JDBC 代理驱动的身份介入：应用把驱动类换成 p6spy 的实现（连接串加对应前缀），真实的 JDBC 调用被它包一层，语句与实参被拼成单行完整 SQL 输出到日志，输出格式可用 `spy.properties` 定制。因为它工作在 JDBC 层，看到的已经是带实参的最终调用，参数自然齐全——这也是它比裸日志方便的根本原因。

## 接入 p6spy 要改哪些东西

- 引入 p6spy 依赖
- 数据源配置里换驱动类、连接串加前缀
- 加 `spy.properties` 定制输出格式
- 多数据源 / 多环境时，每处数据源都要换一遍

单看每一步都不大，但改动都落在工程里：依赖要过安全审计，配置随环境漂移，团队里每个人的工程都要同步这一套。

## 不改工程有哪些替代

- **开 MyBatis 日志**：`Preparing:` / `Parameters:` 两行里有全部信息，零改动；缺点是参数要自己拼，成因与局限见[MyBatis 日志里的问号怎么变成真实参数](./mybatis-log-params.md)
- **自定义拦截器**：从 `BoundSql` 取语句与参数自己渲染，适合有定制诉求、愿意维护代码的场景
- **SQL Visualizer 的日志还原**：IDE 插件形态，装好即用，工程零改动

## 用插件直接还原

SQL Visualizer 的 [SQL 日志工具窗口](/features/sql-log) 不动你的工程就能看到完整 SQL：

- **增强捕获**（默认开启）：应用启动后插件在本机应用 JVM 内挂载采集点，执行的 SQL 连同真实参数、耗时、影响行数直接入列，条目自带调用栈、可精确跳回触发它的源码行
- **控制台捕获**（回落通道）：解析运行控制台里的 `Preparing:` / `Parameters:` 日志（含 `==> Preparing:` 混合前缀形态），自动把参数拼回语句

已经在用 p6spy 也不冲突：它输出在应用日志里，插件的控制台通道解析的是 MyBatis 形态的日志，两者各走各的通道。

还原出的 SQL 即拿即用——开发时在 IDE 里随跑随看，不必为了看一条 SQL 给工程加代理驱动。
