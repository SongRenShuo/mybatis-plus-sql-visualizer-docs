### 4.2 正文已补（2026-10-08 落地，本计划只留录制信息）

「性能建议」与 N+1 徽章此前**站内无专节**（只在 wrapper-preview 的 EXPLAIN 段被顺带提一句），正文已随本轮补齐：`features/sql-log.md` 新增一节 **「慢查询与性能建议 / Slow Queries & Performance Advice」**（位于「SQL 高亮与耗时显示」之后），承载慢查询标红与计数、耗时排序定位、**预览面板 meta 行的静态性能建议**、**N+1 同结构徽章**；EXPLAIN 仍留在 wrapper-preview，从新节链过去（功能页唯一权威、不重复）。中英同构。

正文落笔时按源码校正了三处易写错的地方（**已避免写成不存在/不准的形态**）：

- 性能建议的**呈现形态**不是独立面板或分节，而是**预览面板 meta 行后的分段**：每条以 `⚠`（ERROR/WARN，红）/`ℹ`（INFO，蓝）开头、`；` 分隔、超宽截断加省略号、悬停看全文（`SqlPreviewPanel.buildPerfSegments` 亲证；bundle 里的 `panel.perf.section/warning/info` 三个键在源码中**无引用**，未据其描述「性能建议面板」）。
- **不写规则条数**：三处口径不一——bundle `perf.*` 文案键 24 个、规则注册处实测 **19 条**（`PerfRulesBatch1/2/3` 的 `messageKey` 去重计数）、`SqlVisualizerPerfAdviceTool` KDoc 写「20 条规则引擎」。数量无法单点确证，正文只列举规则形态、不给数字。
- N+1 徽章**阈值为 3**（`TEMPLATE_BADGE_MIN_COUNT`），文案是 `同结构 {0} 条`（bundle `log.panel.templateBadge`，非 KDoc 里的「×N 同模板」）；字面量不同算同一结构。

## 九、决策点与推荐（2026-10-08 答复）

### D1 录制启动 —— 已定：**暂不启动**（用户 2026-10-08 明确）

计划留在册，随时可开。批次 1 的两张（A1 跳转到源码、A2 调用栈跳转）是开录后第一件事。

### D2 模块位置 —— 推荐：**紧跟「日志还原」之后**（成为第 3 个模块）

理由：现有 7 个模块的叙事顺序是「写代码时预览 → 跑起来之后看日志 → 反向往回写 → 代码生成 → 多框架 → 跨生态 → AI 生态」。**「日志还原」讲的是从运行态拿到 SQL，「日志溯源」讲的是从 SQL 回到代码**——是同一叙事的下一步（拿到数据 → 找到出处），挨着读最顺。放末尾（第 8）会被 MCP / AI 生态模块隔断，容易被读成附属小功能。

代价（须写进实施）：`reverse` 是逐项布尔，控制 ≥768px 下图文左右交替与列宽配比（`1.3fr 1fr` ↔ `1fr 1.3fr`），**窄屏为单列堆叠、不受 `reverse` 影响**。插入中间位置需把它后面 5 个模块的 `reverse` **一并翻转**才能保持交替节奏——5 个布尔值，风险低，但改完必须在真机（桌面端）过一遍每屏的图文交替观感，并复测 375px。

### D3 「精确落点」怎么用 —— 推荐：放在模块内 `features` 的**第一条**

不要放进 `title`。分工建议：`title` 回答「这是什么」（`SQL 溯源 · 日志直达源码`）、`description` 回答「一句话价值」、`features` 三条承载「差异点 / 体验点 / 兼容面」。而「精确落点」是这里**唯一的竞品差异点**（同类工具多为表名或正则近似；本插件的落点取自真实调用栈，且明确不做表名猜测回退），放第一条最容易被读到。

三条 `features` 定稿建议：

1. **精确落点** — `日志条目右键直达执行 SQL 的那一行；真实调用栈定位，不做表名猜测`
2. **调用栈逐帧** — `预览面板悬停展开完整调用链，点哪一帧跳哪一帧；帧数 12~64 可配`
3. **两种通道都能用** — `增强捕获免配置直达；控制台通道配拦截器后同样精确`

### D4 模块是否可点、落点指哪 —— 推荐：**加「了解详情」链接，落点精确到小节**
