## 一、需求理解

### 1.1 用户要求

1. **方案 2**：把奖励金额整体下调，单笔上限从 ¥18.88 降到 **¥9.88**，四档区间同步下调。
2. **方案 3**：增加**每月预算上限**，控制累计支出。
3. **预算上限对用户不可见**：悬赏页面不能出现具体金额、已用额度或剩余额度，只能出现状态文字，例如「即将达到上限」「已达到上限」。
4. **达到上限后不阻断提交**：悬赏仍可正常提交、正常审核，只是提示用户「不再发放金额奖励」。
5. 两项同时实施。

### 1.2 结论

| 项 | 新值 |
|----|------|
| 单笔硬上限 `maxReward` | **988 分 = ¥9.88** |
| 严重（P0） | **¥6.88–¥9.88**（688–988 分） |
| 高（P1） | **¥4.88–¥6.88**（488–688 分） |
| 中（P2） | **¥2.88–¥4.88**（288–488 分） |
| 低（P3） | **¥0.88–¥2.88**（88–288 分） |
| 月度预算 `monthlyBudget` | **默认 2000 分 = ¥20.00/月**，超管可在后台改 |
| 接近上限阈值 | 已用 ≥ 月预算的 **80%** 且未达 100% |
| 达到上限 | 已用 ≥ 月预算 |
| 达到上限后的行为 | **提交仍正常受理**；页面提示「不再发放金额奖励」；审核只能按 0 元通过/驳回 |

建议金额仍按「区间中值 × 有效性系数，取整到角」：

| 等级 | 有效 | 部分有效 |
|------|------|----------|
| 严重 ¥6.88–9.88 | ¥8.38 | ¥4.20 |
| 高 ¥4.88–6.88 | ¥5.88 | ¥2.90 |
| 中 ¥2.88–4.88 | ¥3.88 | ¥1.90 |
| 低 ¥0.88–2.88 | ¥1.88 | ¥0.90 |

## 三、预算口径（先定清楚，避免月底对不上）

### 3.1 预算按「核定月」占用，不按「打款月」

- 审核通过（状态 3 待发放）时，写入 `budget_month = 当前月（UTC+8，YYYY-MM）`，立即占用当月预算；
- 已发放（状态 4）保留原 `budget_month`，不重复占用新月份；
- 重新打开（5/6→1）、撤回（→7）、撤销通过（3→2）时清空 `budget_month`，释放占用；
- 无效/重复/金额 0 不占用预算；
- 因此：本月预算 = 本月**核定通过**的金额（含待发放 + 已发放），不是本月实际转账金额。这样避免管理员先批量通过、月底才发现超额。

### 3.2 已用额度查询

```sql
SELECT COALESCE(SUM(reward_amount), 0)
FROM bb_submissions
WHERE is_deleted = 0
  AND status IN (3, 4)
  AND budget_month = ?   -- 当前月 YYYY-MM（UTC+8）
```

- 预算全局共享，不按 `site` 拆分（当前只有插件站；将来工具站接入再议）；
- 状态 4 的历史记录如果 `budget_month` 是旧月份，不计入本月；
- 审核中的状态 1/2 不占用，只有审核通过才占。

### 3.3 预算状态

| 状态 | 条件 | 公开页面文案 |
|------|------|--------------|
| `normal` | 已用 < 80% | 不显示 |
| `near_limit` | 80% ≤ 已用 < 100% | 「本月悬赏额度即将达到上限，后续提交的报告可能不再发放金额奖励。」 |
| `reached` | 已用 ≥ 100% | 「本月悬赏额度已达到上限，后续提交的报告将不再发放金额奖励，但仍会正常受理。」 |

- 公开接口只返回 `budgetStatus`，**不返回** `monthlyBudget`、`monthUsed`、`monthRemaining`；
- 公开提交**不因预算拒绝**：达到 `reached` 仍正常受理，只是页面提示不再发放金额奖励；
- 管理端可以看到具体金额、已用/剩余，便于决策；审核时只有 `rewardAmount > 0` 才受预算限制。

## 四、数据模型

### 4.1 迁移 `0023_bounty_budget.sql`

```sql
-- 0023: 悬赏月度预算（20261028-2355 计划）
-- budget_month：审核通过时写入的核定月（UTC+8，YYYY-MM），用于月度预算占用。

ALTER TABLE bb_submissions ADD COLUMN budget_month TEXT;
CREATE INDEX IF NOT EXISTS idx_bb_budget_month ON bb_submissions(budget_month, status);

-- 历史已核定/已发放记录回填核定月（按审核时间，缺审核时间再退到发放/创建时间）
UPDATE bb_submissions
SET budget_month = strftime('%Y-%m', datetime(COALESCE(reviewed_at, paid_at, created_at), '+8 hours'))
WHERE status IN (3, 4) AND budget_month IS NULL;

-- 默认策略下调：仅在仍是旧默认（maxReward=1888）时更新，避免覆盖管理员自定义
UPDATE sys_settings
SET value = json_set(
  value,
  '$.maxReward', 988,
  '$.monthlyBudget', 2000,
  '$.tiers[0].min', 688, '$.tiers[0].max', 988,
  '$.tiers[1].min', 488, '$.tiers[1].max', 688,
  '$.tiers[2].min', 288, '$.tiers[2].max', 488,
  '$.tiers[3].min', 88,  '$.tiers[3].max', 288
)
WHERE key = 'bounty.policy'
  AND json_extract(value, '$.maxReward') = 1888;
```

说明：

- `json_set` 的数组路径 `$.tiers[0].min` 已在本地 SQLite 验证可用；D1 使用同源 SQLite JSON1，实施时仍需在远端执行前用 `SELECT json_set(...)` 复核一次。
- 迁移保留 `enabled`、`validityFactors`、`currency`、`reviewSlaHours`，只改金额和新增预算字段。
- 如果生产策略已被管理员改成非 1888，迁移不会覆盖；需在后台手动把档位/预算改到新值（本计划默认值见 §1.2）。
- 生产当前 0 条悬赏记录，回填无实际数据；迁移仍保留回填逻辑供将来环境使用。

## 五、后端设计

### 5.1 预算服务 `src/services/bounty-budget.ts`

新增纯函数/查询，供公开与管理端共用：

```ts
export type BudgetStatus = 'normal' | 'near_limit' | 'reached'

export function currentBudgetMonth(): string          // dayCN().slice(0,7)
export async function getMonthUsed(db, month): Promise<number>
export function budgetStatus(used: number, cap: number): BudgetStatus
export async function getBudgetSnapshot(db, policy): Promise<{
  month: string; used: number; remaining: number; status: BudgetStatus

```

- `budgetStatus`：`cap<=0` 视为 `reached`（防御；策略校验要求 >0）；`used >= cap` → reached；`used >= ceil(cap*0.8)` → near_limit；否则 normal。
- `getMonthUsed` 只算 `is_deleted=0 AND status IN (3,4) AND budget_month=?`。
- 金额全部整数分。

### 5.2 公开接口

#### `GET /api/v1/bounty/policy`

返回白名单字段 + 预算状态：

```json
{
  "enabled": true,
  "currency": "CNY",
  "reviewSlaHours": 72,
  "maxReward": 988,
  "tiers": [ ... ],
  "validityFactors": { ... },
  "budgetStatus": "normal"
}
```

- **绝不返回** `monthlyBudget`、`monthUsed`、`monthRemaining`；
- 建议把 `Cache-Control` 从 `max-age=300` 改为 `no-store`（预算状态会随审核变化，5 分钟缓存会让「已达到上限」滞后）；
- 测试用 `Object.keys` 断言不存在预算字段。

#### `POST /api/v1/bounty/submissions`

- 现有校验顺序不变；`enabled=false` 仍然拒绝；
- **预算状态不参与拒绝**：`reached` 时照常受理、照常写库，只在页面提示不再发放金额奖励；
- 成功响应不返回预算状态/金额；页面状态来自 `/policy` 的 `budgetStatus`；
- 如果将来产品改为「达到上限暂停收报告」，再单独加开关，本次不做。

#### `GET /api/v1/bounty/stats`

- 保持现有字段，不增加任何预算金额；公开页面从 `/policy` 的 `budgetStatus` 获取状态即可。

### 5.3 管理接口

#### `GET /admin/bounty/policy`

- 返回完整策略（含 `monthlyBudget`），仅登录管理员可见；
- 前端用它渲染预算字段和档位。

#### `PUT /admin/bounty/policy`（超管）

- 校验 `monthlyBudget`、`maxReward<=988`、四档齐全、`min<=max<=maxReward`；
- 保存后写审计（旧值/新值），公开接口下一次请求即生效（`no-store`）。

#### `GET /admin/bounty/stats`

新增字段：

```json
{
  "monthBudget": 2000,
  "monthUsed": 1576,
  "monthRemaining": 424,
  "budgetStatus": "near_limit"
}
```

- 保留现有 `monthPaidAmount`（本月实际已发放）作为对账口径，和 `monthUsed`（本月核定占用）分开展示；
- `site=all/plugin/tools` 时预算仍是全局（不按站点拆），在字段说明里注明。

#### `PATCH /admin/bounty/submissions/:no/review`

- 只有 `targetStatus === 3`（有效/部分有效且金额 > 0）时检查预算；
- **`rewardAmount = 0` 始终允许**：达到上限后，管理员仍可把报告标为有效/部分有效但金额 0，状态进入 5（未通过）并在审核说明写「本月预算已满，不发放金额奖励」；
- 金额 > 0 但超过本月剩余 → 409「本月悬赏预算不足」，管理员可改为 0 元或等下月；
- 预检查给友好提示，最终用**原子条件更新**防并发：

```sql
UPDATE bb_submissions
SET status = ?, validity = ?, severity_final = ?, reward_amount = ?,
    review_note = ?, internal_note = ?, reviewer = ?, reviewed_at = datetime('now'),
    budget_month = ?, updated_at = datetime('now')
WHERE id = ? AND is_deleted = 0 AND status IN (1, 2)
  AND (
    SELECT COALESCE(SUM(reward_amount), 0) FROM bb_submissions
    WHERE is_deleted = 0 AND status IN (3, 4) AND budget_month = ?
  ) + ? <= ?
```

- 绑定：`budget_month=currentMonth`、`rewardAmount`、`policy.monthlyBudget`；
- `changes=0` 时重读状态：状态已变 → 409「状态已变化」；否则 → 409「本月悬赏预算不足」；
- 无效/重复/金额 0：`budget_month=NULL`，不占预算；
- 审核说明、状态日志、审计、邮件逻辑不变。

#### 发放 `POST /admin/bounty/submissions/:no/payout`

- 不重复检查当月预算：记录在审核通过时已占用 `budget_month`，打款月份变化不改变占用；
- 保留状态 3、金额 >0、超管权限、`paid_*` 写入；
- 如果历史记录 `budget_month` 为空（迁移前数据），打款时补写为审核月（`reviewed_at`）或当前月，并记审计。

#### 重新打开 / 撤回 / 撤销通过

- `reopen`（5/6→1）、`withdraw`（→7）、`revoke-approval`（3→2）都要 `budget_month = NULL`，释放预算；
- 现有状态机与审计不变，补一个测试断言。

### 5.4 审计与通知

- 审核、发放、策略修改、预算守卫失败都写现有审计；
- 通知文案不变；如果后续要「预算接近/达到上限通知管理员」，可复用 `bounty_notify`，本次不做硬性要求；
- 公开邮件/页面不出现预算金额。

## 十、验收标准

### 10.1 公开面

1. `GET /api/v1/bounty/policy` 返回 `budgetStatus`，**不包含** `monthlyBudget/monthUsed/monthRemaining`。
2. `normal` 无提示；`near_limit` 显示「即将达到上限」；`reached` 显示「已达到上限、不再发放金额奖励」，**提交按钮仍可用**。
3. 页面任何位置不出现月度预算金额/已用/剩余。
4. `reached` 时提交接口**仍成功**，页面提示不再发放金额；响应不含预算金额。
5. 版本下拉、需求池联动等既有功能不回归。

### 10.2 管理面

1. 策略弹窗可改月预算与档位，最大奖励上限 9.88；保存后公开页档位即时更新。
2. 统计卡显示本月预算已用/上限/剩余；与「本月已发放」区分。
3. 审核金额超过本月剩余 → 前端提示 + 后端 409；额度内可正常通过。
4. 达到上限或金额超过剩余时，金额 0 仍可正常审核（状态 5 + 审核说明）；正数金额被拦下。
5. 重新打开/撤回/撤销通过后，本月已用额度下降。
6. 发放不重复占用当月预算；旧月份核定记录打款不影响本月。

### 10.3 门禁

- admin 定向测试（含新增 budget 用例）全绿；
- `check:doc` 通过（0023 登记）；
- admin typecheck/build、docs build 通过；
- 生产公开接口冒烟与页面状态验证通过。

## 十二、待验证前提（实施者先证伪再动手）

1. **`json_set` 数组路径**：`$.tiers[0].min` 在远端 D1 可用；本地 SQLite 已验证，远端执行前用 `SELECT json_set(...)` 复核；不可用则改为整段 JSON 替换（保留 `enabled`）。
